# 第十九阶段线上联调：请求读取与连接池拥塞修复

日期：2026-10-15。

修复已以 `f4cf8611` 发布至 Zeabur API 和三个 worker；本机回归与线上双浏览器复测均已执行。完整联调记录原见 `STAGE19_CLOUD_VALIDATION.md`，该文档随独立 OCR 服务一并移除。

线上联调发现：Zeabur API 位于首尔，Supabase 位于加拿大，数据库单次往返约 192 ms。多个浏览器首页同时加载时，默认四连接池的五秒等待窗口可能用尽，原实现将该异常包装成未处理的 `RuntimeError`，最终返回 500。

## 本次改动

- 业务请求的 `actor` 不再加载完整 `/api/me`。在受限只读事务中用一条查询验证有效用户及可用事务所，保持“事务所成员优先、客户企业成员其次，各自按名称及 ID 排序”的默认选择规则；指定未获授权工作空间仍返回 403。
- 员工业务上下文一次读取账套归属与提交策略，再按已获授权企业批量读取部门、审批关系。领域查询最多六条，不再随可见企业数量逐家增长。仅有账套权限的会计仍不能查看员工部门目录；部门审批与企业财务权限继续分别计算。
- 仅 `psycopg_pool.PoolTimeout` 和 `TooManyRequests` 转成专用容量异常，HTTP 返回 `503`、`code=database_busy` 和 `Retry-After: 2`。身份、授权及其他配置错误不归入容量异常。不对失败写请求自动重放。

没有新增迁移，没有扩大连接池上限，没有增加跨请求身份或授权缓存，没有改变 RLS、会计审核与导出规则。完整 `/api/me` 仍保留原身份同步与资料投影行为。事务初始化、连接检查和提交的协议往返未在本次合并；不使用 Supabase 当前连接方式不兼容的 pipeline。

## 验证

- SQLite：新增请求读取/过载回归、既有提交策略与 Supabase 鉴权测试共 122 项通过；业务事项/API、池管理相关另 46 项通过。新增测试覆盖 1、10、100 家额外企业的固定查询数、默认工作空间顺序、员工与仅账套角色的不同目录范围、立即撤权、停用账号、503 与脱敏、其他连接错误分类。
- PostgreSQL：使用本机新建的 PostgreSQL 18 实例，迁移至 082，受限 app/worker 账号运行 65 项测试全部通过，覆盖受限 RLS、同一登录会话撤权、部门/企业隔离、池复用、并发与容量释放、提交策略、管理后台权限。
- Ruff 静态检查、生产代码与新增测试文件的格式检查、`git diff --check` 通过；两个既有测试文件保留原格式，避免混入无关重排。测试环境出现既有 Starlette/httpx 弃用提示，没有测试失败。
- 线上同时打开两个合成账号的员工/会计首页，启动所需五个业务接口全部返回 200，无 JavaScript 错误或 500/503。页面就绪分别为 22.4 秒、23.4 秒，证明该次启动成功，不能视为性能已达标。API 等待窗口配置为 15 秒、最大连接数仍为 4；三个 worker 未扩大连接池。

查询数指业务服务发出的领域 SQL，不包含事务初始化、提交及 RLS 内部查询。此记录证明协议与权限回归通过，不代表跨地域延迟已经消除。实际后台联调还观察到全局写锁排队、续期告警和较长的移交事务；不能单靠增大连接池解决。数据库与 API 同地域部署、减少写事务内顺序查询和队列维护扫描是后续优先优化事项，改动仍须保持租约、幂等与发布前校验。
