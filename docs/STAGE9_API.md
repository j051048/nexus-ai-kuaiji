# 第九阶段：流水身份、业务匹配与人工交付回执

本阶段仍面向 2–3 家真实企业试点，币种为人民币。处理链路是“保留银行来源 → 辨别疑似重复 → 确认业务与实际收付关系 → 处理异常 → 会计复核 → 导出 → 导入客户软件回执并核对内容”。

流水匹配采用确定性校验，无需打开企业 AI 开关，也无需配置模型供应商。交付回执目前来自人工提供的中性 JSON / CSV，系统没有连接客户财务软件的认证接口。“回执数据一致”表示提供的回执事实与冻结导出清单一致，**不证明客户软件已经真实过账**。未知、缺项或差异不会触发自动重发。

所有接口使用现有登录和当前事务所工作空间。每次操作重新核对企业关系、账套授权与账号有效状态；历史幂等回执也不能绕过撤权。

## 1. 银行导入的稳定身份

沿用 `POST /api/books/{book_id}/imports`，新增可选的导入身份字段：

```json
{
  "source_name": "银行十月流水.csv",
  "namespace": "bank-statement-v1",
  "bank_account": "operating-account-001",
  "rows": [
    {
      "external_id": "statement-row-20261003-001",
      "stable_transaction_id": "bank-transaction-20261003-001",
      "date": "2026-10-03",
      "description": "采购办公耗材付款",
      "counterparty": "供应商完整名称",
      "amount": "100.00",
      "direction": "expense",
      "evidence_ref": "付款回单归档编号"
    }
  ]
}
```

- `namespace` 与 `bank_account` 必须一起填写。指定 `stable_transaction_id` 时，二者必须存在。
- 稳定交易编号应来自银行或来源系统，不能使用本次文件中的行序号。未提供稳定编号时使用该行的 `external_id`。
- 同一事务所、企业、来源、银行账户和稳定编号绑定同一笔交易。重复导入相同事实不创建第二笔来源；同一身份对应不同事实时整批拒绝。
- 同一企业的相同稳定交易不能通过导入第二个账套再次建立。无权读取其他账套时，只返回需要会计核对的提示，不返回其他账套资料。
- 来源的内部 `external_id` 与原始导入编号分开保存。界面和查询中的人类可读编号来自 `original_external_id`；业务关联使用服务器返回的 `source_id`，不要自行解析内部编号。
- 不填写来源和银行账户时保留旧导入契约。真实试点应使用明确、持续稳定的身份字段。

相同银行账户下，日期、金额、方向和交易对方都一致的不同来源会进入疑似重复核对。改变 `namespace` 不会隐藏同账户的相似记录。系统保留全部原始来源，不能通过删除或静默合并来解决疑似重复。

旧格式来源没有银行身份时，若与同账套的新身份来源在日期、金额、方向和交易对方上一致，也必须人工核对账号和真实交易。检测是双向的，旧来源已审核或已关联也不能让新来源绕过阻断。双方都有明确且不同的银行账户时，不按这条规则判为同账户重复；双方都是旧格式时保留原有导入行为。

### 疑似重复核对

| 接口 | 用途 |
| --- | --- |
| `GET /api/books/{book_id}/sources/{source_id}/duplicate-check` | 查询当前来源身份、事实指纹及相似来源；返回 `total`、`has_more`，当前明细最多 50 项 |
| `POST /api/books/{book_id}/sources/{source_id}/duplicates/{other_id}/distinguish` | 会计依据回单确认这两笔是独立交易，追加不可变核验记录 |

核验请求包含：

```json
{
  "source_fingerprint": "从查询响应取得的当前来源指纹",
  "other_fingerprint": "从查询响应取得的对方来源指纹",
  "expected_version": 1,
  "reason": "已核对两份独立付款回单及银行交易编号，确认是不同交易"
}
```

实际指纹为服务器返回的 64 字符值，版本取当前待审凭证版本。需要当前账套复核权限和开放期间；来源、草稿变化或原核验说明冲突时拒绝。未核验的相似记录阻断匹配、审核和导出，核验不删除来源、不自动审核凭证。

## 2. 业务事项与银行流水匹配

界面入口为账套中的“流水与业务匹配”。

| 接口 | 参数与返回 |
| --- | --- |
| `GET /api/reconciliation/books/{book_id}/events` | `status=unmatched\|matched\|all`，`limit=1..100`，`offset>=0`；返回账套信息、已移交且实际收付的业务事项及分页 |
| `GET /api/reconciliation/books/{book_id}/events/{event_id}/candidates` | `limit=1..100`，`offset>=0`；返回当前业务版本、银行候选、核对理由、风险和分页 |
| `POST /api/reconciliation/confirm` | 确认一批业务与银行来源关联，保存不可变回执 |

列表与候选查询要求当前账套读取权限；确认要求当前账套编辑权限。员工业务录入账号没有账套授权时，不能读取银行候选或确认关联。

候选在数据库中按同一账套、收付方向、交易对方精确一致、日期相差最多 7 天、金额不超过业务总额筛选和分页。尚无草稿、疑似重复未辨别或异常补件未关闭的银行来源不可确认。若存在多笔同金额候选，界面明确显示歧义，系统不自动选中。

确认请求的结构如下，全部 ID、版本和指纹应从当前候选响应取得：

```json
{
  "idempotency_key": "match-command-202610-001",
  "reason": "已对照业务合同与两份付款回单，确认分笔付款关系",
  "items": [
    {
      "book_id": "当前账套ID",
      "event_id": "当前业务事项ID",
      "event_version": 6,
      "fact_version": 2,
      "business_draft_version": 1,
      "business_source_fingerprint": "当前业务来源指纹",
      "banks": [
        {
          "source_id": "第一笔银行来源ID",
          "source_fingerprint": "第一笔当前来源指纹",
          "draft_version": 1
        },
        {
          "source_id": "第二笔银行来源ID",
          "source_fingerprint": "第二笔当前来源指纹",
          "draft_version": 1
        }
      ]
    }
  ]
}
```

上例为结构示意，不能用示意 ID 或指纹提交真实确认。

### 确认条件与结果

- 每批最多 20 个业务事项，每个事项最多 20 笔银行流水。可以多笔银行流水对应一个已收付事项；**银行合计必须精确等于该事项金额**。
- 所有事项须完成审批并移交到对应企业账套；业务来源、业务事实和本次版本一致，期间开放，两侧凭证都未审核、未导出。
- 一笔银行来源只能关联一个业务事项。整批不能重复选择同一来源或事项；不能静默替换已存在的关联，选择必须包含该事项已关联的全部银行来源。
- 确认先检查整批当前授权，再在一个事务中核对事实、金额和异常并写入关联与回执；一项失败不留下半批关联。
- PostgreSQL 受限确认函数同样检查当前授权、版本、来源、交易对方、日期、合计和异常。运行账号不能直接插入伪关联回执。
- 返回 `review_required=true`。每项的 `links_current` 表示当前关联是否仍与该回执一致；重复请求恢复回执，关联后来变化时不会重新建立旧关联。
- 匹配不生成新的收付事实，不修改原始流水，不自动审核凭证。已关联的银行来源禁止再单独审核入账，业务凭证由会计复核后导出。
- 银行来源关联后出现的新异常、补件或待辨别重复，仍向业务凭证传播，阻断其审核、导出及自动采用建议。企业 AI 开关关闭也不能绕过这些校验。

交易对方不同、日期超出范围或金额不能对应的事项进入人工处理，不通过提高模型置信度放行。

## 3. 冻结导出清单与人工回执

每次正式导出在同一事务中保留冻结清单，绑定导出、企业、账套、期间、源指纹、审批与导出版本、分录和辅助值。清单、回执和差异说明均追加保存，不能修改已导出的凭证。

| 接口 | 用途 |
| --- | --- |
| `GET /api/books/{book_id}/delivery` | 分页读取该账套导出记录、历史清单状态及回执数量 |
| `GET /api/books/{book_id}/delivery/exports/{export_id}` | 冻结清单、分页回执和当前内容核对结果 |
| `GET /api/books/{book_id}/delivery/exports/{export_id}/template?format=json\|csv` | 下载中性回执模板，默认状态为 `unknown`，外部凭证号留空 |
| `POST /api/books/{book_id}/delivery/exports/{export_id}/backfill` | 尝试从原始导出和不可变审计证明恢复旧清单；证明不足保留 `pending_legacy` |
| `POST /api/books/{book_id}/delivery/exports/{export_id}/receipts` | 追加结构化人工回执 |
| `POST /api/books/{book_id}/delivery/exports/{export_id}/receipts/import` | 导入中性 UTF-8 JSON / CSV 回执，内容最多 2 MB |
| `POST /api/books/{book_id}/delivery/discrepancies/notes` | 对当前真实差异或缺失字段追加处理依据 |

读取需要当前账套读取权限；导入、回填和追加处理依据需要当前复核权限。目标 `export_id` 必须属于 URL 指定账套；回执中自称的企业、账套、期间与币种作为待核对事实，不会扩大访问权限。

文件导入请求：

```json
{
  "format": "json",
  "content": "此处是按下载模板填写的UTF-8回执文本",
  "idempotency_key": "delivery-receipt-202610-001",
  "reason": "客户财务提供的导入记录，已对照凭证编号和分录明细"
}
```

结构化回执包含 `book_id`、`company_id`、`period`、`currency`、`items`，并附 `idempotency_key` 和 `reason`。每项记录 `draft_id`、真实 `external_voucher_id`、`status=accepted|rejected|unknown`，以及日期、金额、摘要和分录事实。分录使用 `ordinal`、`account_code`、精确字符串 `debit/credit` 和 `auxiliary_values`。建议使用下载模板，保留字段，按客户提供的事实填写。

### 回执状态的含义

| 状态 | 界面名称 | 依据 |
| --- | --- | --- |
| `verified` | 回执数据一致 | 人工提供的接受结果、外部凭证号、来源范围、金额及完整分录事实与冻结清单一致 |
| `received_unverified` | 已收到 · 待核验 | 状态未知、字段或分录事实缺失、本次回执未列出某项凭证 |
| `discrepancy` | 存在交付差异 | 内容不同、拒绝结果、重复凭证、外部凭证号冲突或不属于本次导出的凭证 |

状态在查询时由不可变事实计算，不接受写入“已核验”标志。部分回执不能让缺失凭证变为成功；外部系统结果不确定时保留 `unknown`。不同账套、企业、期间或币种的回执声明会形成差异，不会改绑导出。

差异说明只记录核对和处理依据，不改写原事实、不消除差异、不解冻凭证。系统不会因收到部分或未知回执自动再次发送凭证。需要继续核实时追加新的客户记录，保留全部历史。

旧导出缺少可证明的历史清单或科目快照时，保持未知，不拿当前科目配置冒充历史配置。即使通过原导出恢复了冻结分录，历史科目快照仍可为未知。

## 4. 试点操作顺序

1. 固定每个银行账户的来源和稳定交易编号规则，导入流水并生成待审草稿。
2. 对相似来源逐对核对回单；未辨别前保持阻断。
3. 企业财务移交已收付业务事项，会计在匹配页面核对单笔或分笔付款关系。
4. 处理原件、补件、金额等异常，集中复核凭证；关联银行来源不重复审核入账。
5. 导出已复核凭证，保留冻结清单；按照客户软件实际流程导入。
6. 取得客户提供的真实回执或凭证记录，填入中性模板后核对；未知与差异交给人工继续处理。

本阶段没有创建外部付款、税务申报或独立正式总账，也没有自动连接客户财务软件进行过账。企业试点应对照真实月份的银行、业务单据与客户软件凭证，确认重复导入、异常阻断、独立复核及交付差异均按预期运行。
