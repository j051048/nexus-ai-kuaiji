## 本次定位到的等待

首页已经使用上一阶段的 `workspace/bootstrap` 聚合接口。这次正式域名两种虚构角色的单轮浏览器观察中，Supabase 登录约 2.1 秒，核心接口约 1.1 秒，运行摘要约 0.7 秒；另外一次首页测量出现 5 秒以上等待。它们包含本机网络、浏览器调度及云端波动，不能代表 p95，也不能全部归因于数据库。

助手存在两种不同耗时：打开已有会话需要读取当前资料与历史；发送新问题还需要排队、构造及校验事实、模型生成和发布后刷新。只有前一类在本轮做了可复现的代码优化。

相同已有会话、相同返回 SHA 的线上只读对照中，稳定样本网关比直连增加约 140–190 ms，个别请求有更大的长尾。重型会话详情直连仍约 1.3 秒，冷首条约 3.3 秒。实际网关函数地域为 `iad1`，Zeabur 与 Supabase 已位于首尔；不能把 CDN 边缘入口或 Sandbox 地域当成函数地域。

## 已实现

- 新增 `GET /api/assistant/conversations/{id}/workspace`，同时返回当前会话详情、消息页和操作页。前端一次读取替代三个独立请求，活跃轮询同样使用聚合接口。
- 三部分在同一个受限只读事务中实时核权、读取当前证据与任务进度，不缓存授权，不跨请求复用资料快照。旧接口保留，只有新路由不存在且返回 `404 / Not Found` 才兼容回退；资源不存在、撤权和服务错误不回退。
- 历史列表只在用户打开“查看我的会话”时加载，移除隐藏预取和重复读取，保留加载状态与分页。切换企业、身份、分页和关闭助手时，旧响应不能覆盖新范围；发送、取消及确认操作后继续强制重新读取。
- `vercel.json` 将 `api_gateway` 的 `main.py` 函数地域设为 `icn1`，部署后才生效。服务名、公开路由、后端地址和已有流量路径不变；外部 Zeabur 后端通过原有环境变量连接，无新增内部服务 binding。
- 企业详情的“人员与权限 → 开通账号”增加“设置初始密码”。管理员填写姓名、登录邮箱、企业角色、部门与两次密码，完成后员工可用邮箱和初始密码登录；仍支持本人激活模式及添加已有成员。
- 企业角色预览直接说明登录后工作台与权限边界。部门审批模式下，新员工密码开户必须选择本企业部门；没有部门时引导先配置部门和审批人。财务角色不会自动获得账套复核或其他企业权限。
- 开通结果可复制不含密码的登录说明。密码只在本次请求内存中存在，提交后清空，不写入请求记录、审计、业务数据库、指纹或浏览器存储。

## 开户与权限边界

| 人员 | 默认登录后入口 | 授权边界 |
| --- | --- | --- |
| 企业员工 | 部门审批模式为“我的工作台”、快速录入 | 本人业务事项和附件；集中提交模式下普通员工不能填报，开户预览会明确提示 |
| 部门审批人 | 审批工作台 | 由“部门与审批”单独指定，处理获授权部门的事项 |
| 企业财务 | 财务工作台 | 本企业资料核验、补件及移交；凭证经办、复核需另授账套权限 |
| 企业管理员 | 本企业业务与管理工作空间，按兼任能力显示首页 | 本企业人员、部门和协作；不隐含跨企业或凭证复核权 |
| 事务所会计负责人 | 会计工作台及管理后台 | 管理本事务所全部企业与人员；不增加跨事务所全局权限 |

密码开户沿用持久化请求、派发租约、幂等、审计和管理员 MFA。新密码模式仅用于企业新邮箱；已有账号不能被重新设置密码或抢绑，应走“添加已有成员”。若上游已创建账号但回执丢失，重试通过仅服务端可写的请求标记恢复，并明确提示沿用首次密码，不把重试输入冒充为新密码。

试点企业配置顺序：在 `/admin` 进入企业，先建立部门，再开通员工与审批人员账号；在“部门与审批”指定独立审批人，在“账套分工”分别授予经办与复核能力。员工从普通登录页使用邮箱和初始密码进入工作台。部门存在但未配置有效独立审批人时，可以录入草稿，提交仍会明确阻断，不能自动跳过审批链。

PostgreSQL 新增 `083_employee_password_accounts.sql`，SQLite 新增 `066_employee_password_accounts.sql`，只持久化不可变开户方式及数据库约束，密码不进入该结构。正式发布需先运行迁移再更新应用。角色、企业停用、账号停用、请求创建人权限及部门范围在派发前和完成授权前重新校验；撤销请求不能因企业后续审批策略变化而失效。

企业隔离、后台生成草稿、异常人工处理、会计审核后导出保持原有流程。创建员工账号不赋予过账、自动审核或直接导出权限。

### 实际写入发现的迁移遗留问题

虚构开户首个新建企业请求因审计自增序列落后返回 409，事务整体回滚，未产生公司或账号。只读确认会计领域仅两个 owned 序列：审计表已有 127 行但序列仍为 1，原件证据表为空且序列初始状态正常。已在应用同一全局写锁保护下，仅将审计序列向前推进至 127，保持空表序列，不改历史行或迁移文件，然后恢复同一验收 run。

恢复流程已补充“序列状态检查及实际写入验收”，避免把读取成功当成完整恢复成功。旧版代码会拒绝未知 083 迁移，回滚时必须保留 083 兼容代码，不能直接重启 82 版容器。

### 实际开户、隔离、审核与清理

在原有虚构事务所下新建两家独立标记的 Stage23 企业、三个部门、六个随机初始密码账号；真实超级管理员与真实客户资料未参与。密码和恢复状态只保存在仓库外 DPAPI，真实 MFA 管理账号通过生产开户 API 创建人员，没有发送邮件。重复创建/完成后重试均沿用首次密码，新的重试密码不能登录。

新员工随后用真实初始密码在正式前端登录：落到“我的工作台”，只有本企业范围及报销、采购费用、日常收支三种录入入口，无管理、账务、复核或导出入口；390 px 无横向溢出，直接进入 `/admin` 被拒绝。浏览器只打开空表单，没有自动保存或提交。

独立使用真实受限 `accounting_api` 登录、`accounting_app` 角色及 `READ ONLY` 事务检查员工 RLS：本人企业/成员可见，其他企业/成员、未授权账套、事务所权限、账套权限与开户请求不可见；检查前先确认目标记录存在，避免空数据导致假通过。

主流程实测为员工录入虚构 123.45 元报销及上传模拟附件 → 独立部门审批 → 财务核验 → 确定性凭证草稿 → 独立会计审核 → 导出。未审导出返回 409；给虚构申请人实际复核能力后，其自审仍返回 403，恢复普通员工角色后账套立即不可见。独立复核成功后，两次导出返回同一 ID、单张金额一致，导出凭证冻结，原件 SHA-256 保留。

同企业其他部门、另一企业员工均不能读主事项或原件，审批人不能读取另一部门事项。对照部门故意不设独立审批人，其提交被明确以 422 阻断，验证具体原因为审批链缺失后保留草稿，没有扩大审批覆盖来让测试通过。新测试企业关闭自动模型，仅验证本轮开户与人工审核链，其模型费用、助手轮次与 OCR 任务均为零；本轮唯一真实模型问答单独记录在上一节。

完成后撤销六个新账号的企业授权并在 Auth 停用，原密码不能再次登录；员工旧令牌在撤权后立即返回 403，停用后 `/api/me` 返回 401。两家新企业归档，冻结凭证、导出、原件与审计继续保留，没有硬删账务。原始验收记录保留了最初序列 409 和对照审批链 422 的历史，最终恢复流程与清理均成功。

正式域名和 Zeabur 直连分别 64 项只读验收通过，验证原账号、角色与 bootstrap 契约、错误事务所/企业范围拒绝、历史原件、冻结凭证、审核后导出和管理员 MFA；检查前后业务哈希一致。五个既有服务均 RUNNING / READY，识别/分录和助手 worker 有最新心跳。

完整写入与清理后，独立复核再次精确排除本次新账套及新记录，对发布前八类业务表的原有行比对数量和哈希，全部一致：导出 4、凭证 4、分录 8、业务事项 8、附件 6、复核确认 0、复核回执 0、旧助手轮次 1。原有记录没有因本轮模型、开户或业务流程改变；本轮新增冻结凭证及问答继续保留。
