## 助手慢响应修复

真实会话后端已经成功回答，但详情请求约 44–60 秒，而前端每 15 秒启动的新轮询使此前响应失效，页面等待 90 秒仍不能显示结果。这是本轮发现的前端故障，不能以 API 成功代替浏览器通过。

`bb6691d6` 合并同一授权范围、同一会话与同一分页的在途读取；企业/会话/分页切换、撤权、关闭和卸载会取消旧读取，迟到响应不能恢复已清除资料。发送问题、取消、创建/确认任务和显式刷新仍会废弃写前快照。历史计划页创建新预览后回到第一页，避免新预览被旧页覆盖。

本机验证：291 项前端单测通过；新增七项浏览器回归与既有两项助手流程全部通过，覆盖响应延迟跨越两次轮询、focus 合并、范围切换、分页、写后刷新、撤权及关闭。构建（含类型检查）、ESLint、相关文件 Prettier 和 `git diff --check` 通过。仅保留既有主包体积警告。

浏览器回归保留早期失败记录：既有长流程先遇到本地冷 Vite 的五秒等待、随后触及整项三十秒时限，最后只增加该用例等待预算并保留全部断言，完整流程约 35.6 秒通过。撤权测试最初期待局部提示，实际全局应用会关闭助手；修正为验证立即关闭、迟到响应不恢复及四十五秒不再请求后通过。本地受控响应测试没有调用云端模型。

修复已发布到 Vercel 并从正式域名复验：五项断言通过，已有真实 DeepSeek 回答、四个保存的证据引用、资料更新提示及仍需会计复核的说明正常显示；390px 手机无横向溢出，无 HTTP/JavaScript 错误，没有新增助手 POST 或行动。会话详情本次仍耗时约 42.6 秒，但单次在途读取能够完成并显示，未再被十五秒轮询持续覆盖。此次页面复验共约 77 秒，功能恢复不代表延迟已经达标。

## 已知限制

Zeabur 在首尔，Supabase 在加拿大，单次数据库往返实测约 192ms。并发首页就绪仍约 22–23 秒，部分详情加载约 15–19 秒，一次移交约 47 秒。后台联调还观察到全局写锁排队与续期告警；当时 worker 池仍有空闲连接，不能简单归因为池满。本轮减少领域查询和修正拥塞错误，不宣称已经消除跨地域延迟。API、worker、数据库与原件存储同地域部署，以及减少持锁事务中的往返，是后续优先优化，不能用放宽授权或会计校验换取响应速度。

合成样本证明集成路径和控制边界可用，不构成真实客户票据准确率、完整月结、200–500 家企业吞吐量或正式财务软件接口验收。实际试点仍需经会计确认的真实样本、批量负载、恢复演练和外部软件版本联调。

验收保留了有意义的待办：B 的未知费用仍需结合供应商实际账单核对，1 元是预留而非确认消费；A 的旧人工样例待处理项、B 的上一轮草稿异常和未关闭期间没有为了报表清零而删除。企业组织归档、凭证冻结、期末关账是不同控制，本轮只有空的 C 企业完成组织归档。

本次模型把未付款、辅助项依据、仍须复核等说明也放进 `warnings`，当前系统统一按阻断项处理。后续应以明确的结构化风险类型区分普通说明与真正阻断，并经回归验证；本轮没有通过忽略警告来提高表面自动化率。

助手回答及辅助项展示仍会带内部 ID 或 `handed_off` 等状态术语，后续需收敛为面向会计的中文表达；该体验问题不影响本次只读及企业范围隔离验证。测试账套与科目只用于合成流程验收，真实企业的科目和辅助项映射仍需逐一确认。
