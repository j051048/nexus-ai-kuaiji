## 2. 修改归属、允许范围与禁止事项

### 允许范围

- package.json、package-lock.json：只更新本次必要的 React 运行时、类型包及确有证据的兼容依赖。
- src 下确实受 React 19 影响的入口、错误边界、ref、组件类型和生命周期处理；按复现结果列出文件白名单，做最小修改。
- 相应组件测试、浏览器测试和必要的验收脚本适配；复用现有测试工具和本地环境。
- 本批基线、检查点、验收、机器可读证据与回退说明文档。

### 协作与执行边界

1. 记录 HEAD、已跟踪和未跟踪改动、自己的文件白名单及修改前摘要。共享文件每次编辑前重读；依赖文件也可能属于其他智能体，不能用旧副本覆盖。并行变化无法安全合并时，只阻断冲突项，继续独立验证。
2. 不 reset、clean、stash，不回退他人修改，不删除他人 node_modules、测试库或目录，不整仓格式化，不重建整个锁文件以顺带更新所有依赖。不提交、不推送、不部署。
3. 不改后端业务、数据库模式、SQL 迁移、历史 checksum、权限政策、C01、复核或费用规则。发现后端既有失败应记录并转交，不能为了本次兼容验收削弱服务端校验。
4. 不安装 Astryx，不引入 React Compiler、Next.js、SSR、Server Components、Server Functions、全局状态库或新的 UI/表单库。React 19 的升级不自动授权这些工作。
5. 不把现有表单全面改为 Actions/useActionState/useOptimistic，不重写路由、查询层、审批状态机。新能力只记录为独立后续建议。
6. 不顺带升级 Node、Vite、TypeScript、测试框架等整个工具链。若现有依赖确有最小兼容要求，先用官方说明和失败复现证明，记入白名单；超出兼容所需的改造留作后续。
7. 不使用 --force、--legacy-peer-deps、忽略类型错误、关闭 StrictMode、增加 any/@ts-ignore、删除测试或放宽门禁换取通过。当前已有 skipLibCheck 配置应如实记录；不得把其存在误写成本轮新缺陷，也不得通过进一步放宽配置隐藏兼容问题。
8. 仅用隔离本地环境和虚构/获准脱敏数据；不接真实模型、通知、OA、出管或 T+，不操作线上。允许核对官方文档和下载已核验的公共依赖，不能因此读取生产凭据。

## 3. 必须保留的产品契约

- 企业、账套、期间、对象 ID、来源版本与当前授权继续绑定；所属单位与主要身份可见。前端按钮不能替代服务端授权。
- 切换企业/期间、退出或撤权后，旧数据、原件、选中集合和办理动作不能被迟到响应或延迟渲染重新带回。
- 制单责任、独立复核、会计复核后导出保持不变。内部记账、导出、外部接收/过账和客户签收仍是不同状态。
- 金额继续来自已验证服务或确定性计算，不借升级改变精度、舍入或口径。
- 正式复核、过账、导出、签收、通知不得乐观展示为已完成。结果未知时保留 unknown 与既有核查入口，不自动重发、不更换幂等键来重试。
- StrictMode、渲染重试、重复挂载和用户双击不能多产生一次业务写入、模型调用、扣费或 attempt。合理取消的只读请求与重复业务提交应分别判断，不要求开发环境中所有 GET 都只能出现一次。
- 保留已有草稿、防丢失提示、中文输入、焦点管理、返回来源及版本化深链接。不能为了兼容升级改变用户的办理顺序。

## 4. 执行顺序

### M0：冻结可复现的升级前基线

1. 先完成现有能力盘点：已有且通过、已有但未验、真实兼容缺口。记录依赖版本、Node/npm、锁文件摘要、当前候选指纹及其他智能体文件摘要。
2. 跑现有前端类型、单测、lint、构建、体积门禁和核心 dev/preview 浏览器用例，保存原始输出。现有红项必须定位归属，不能挪到升级后统一归因 React 19。
3. 用同一组数据记录升级前主要路由的 JS/CSS 体积、首屏请求、加载/解析耗时和关键交互。保留浏览器/硬件/缓存条件，避免冷启动与热缓存互比。
4. 阅读执行时官方版本、升级指南、安全公告及实际 peerDependencies。选择一个依赖兼容且没有适用已知未修复安全问题的 React 19 稳定版本；写明具体版本、选择理由、来源和核对时间。禁止 canary/RC，也不盲选最早的 19.0 或不固定的 latest。
5. 核对 react-router、lucide-react、SWC/Vite、测试渲染器及类型工具的实际兼容性。不能仅因版本字符串出现 rc 就判定稳定版不兼容；以实际 semver 解析、官方支持和运行验证为准。

### M1：先建立行为测试，再复现升级问题

遵循以下顺序，避免“为凑先红后绿故意造错”：

1. 现有测试覆盖不足时，先补关键行为的刻画测试，并在当前稳定版本上确认通过，例如企业切换清理、取消提交、弹层焦点与错误边界。
2. 在归属明确的本地候选中，最小更新 React、react-dom 和必要类型包；react/react-dom 固定为同一个具体稳定版本，类型包采用验证兼容的 19 系版本并锁定。只发生必要的依赖变化。
3. 运行类型、组件和浏览器测试，捕捉真实兼容失败。已有失败测试可直接复用；新发现运行时缺陷先补能复现的测试，再修产品代码。类型检查失败也应保留具体位置与错误作为迁移证据。
4. 如果依赖更新后某项直接通过，就标“无须修复，回归通过”；不能人为破坏旧实现制造红测。任何断言调整必须说明原契约是否仍成立，并保留同等或更强的行为验证。

禁止把 npm install 成功、静态源码扫描无命中或 build 成功等同于升级验收。自动迁移工具若确有必要，固定版本、限定文件、检查每处差异；不直接执行未审核的一键全仓改写。

### M2：最小兼容修复

依实际失败逐项处理，而非机械改写所有组件：

- ref 回调隐式返回、清理函数、useRef 和 ReactElement/JSX 类型变化；验证卸载与重新挂载时资源清理正确。
- 错误边界、路由错误页、懒加载失败和资源版本恢复。保留可定位的受控错误记录，不吞异常，不重复上报；不把 token、客户原文或财务载荷写入日志。root 错误回调仅在需要时接入。
- StrictMode、effect 清理、定时器、监听器、请求取消与组件卸载；尤其核对重复 effect 不会自动触发业务提交。
- Suspense/lazy 切换与加载占位：保留现有代码分割、范围清理和旧响应丢弃机制，不让加载中的旧页泄露数据。
- 弹窗/抽屉、表单受控值、中文输入法、键盘与焦点；复用已有组件，不借机重做视觉方案。

每修一项立即跑针对性验证，随后更新检查点。没有真实兼容问题的组件保持不动。
