## 本轮真实失败

- 浏览器复现：原事项读取 503 后只有刷新列表，不能原地重读详情；错企业的 200 响应可被显示；切换已读取事项后地址仍是旧事项，刷新无法保留当前位置。
- 列表 503 时两视口都复现错误的“0 件事项”。修复后区分未知与真实零值；手机验收先返回列表再验证不可翻页，不能在隐藏的列表上做可访问性断言。
- SMTP 六项初始失败：布尔端口/时限被当成整数；复合地址、换行和非字符串未稳定归类；本地报头构造异常被当作未知传输异常。修复后补业务状态机验证，非法地址进入 failed，未建立连接、未发送、不会自动补发。
- 撤权清空、独立复核、发送后 unknown 不重发等已有行为保持，通过正负向回归确认，不将其记为本轮新增能力。
- 浏览器夹具最初未展开退回区域、标题选择器过宽，以及一次回调接线位置的类型错误，均属于本轮实施问题，已纠正，不作为产品原有缺陷证据。

## 验收解释与限制

普通浏览器流程使用本地身份、真实 API、SQLite 和虚构原件；少数网络错误/错范围响应由浏览器注入。PG16/17 由固定清单的数据库专项验收，不能把两种证据说成同一条 PG 浏览器端到端。

Windows 共享临时目录曾导致 esbuild 删除临时文件被拒绝。复用既有任务验收入口的独立临时目录，并对普通构建设置本轮独立 TEMP/TMP 后验证，不删除别人的临时文件、不放宽预算。开发模式关闭文件监听，修改源码后必须重启验收服务；中间候选结果不计入最终结果。

通知专项最初在复用库中遇到其他套件的历史通知，导致全局领取测试选到非当前夹具；该次失败保留，不算通过。最终各业务门槛复用现有 `prepare()` 创建各自独立的新数据库，C01 入口也自行创建新库；没有删除旧库数据、过滤领取结果、放宽角色权限或修改并发断言。源码在门槛运行中变化时按既有检查判失败，最终重新冻结后复跑。

上一轮记录的零星浏览器/本机网络超时不能仅凭一次通过宣称永不再发生；本轮只对有确定性复现的读取和定位缺陷宣布修复。远端 CI、真实通知/模型、真实客户两期试点、多节点容量及生产恢复仍未在本轮执行。既有恢复/容量报告不拼入本候选的通过结论。

后续 Agent/UI 工作应以真实办理数据为依据：先量化每户工时、退回率和操作路径，再决定助手取证覆盖与页面信息压缩；本轮不扩大自动写账、复核、导出或发送权限。
