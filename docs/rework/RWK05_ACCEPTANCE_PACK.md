## RWK05-A  验收脚本覆盖每个模块

**现状。** `scripts/opt_acceptance.py` 每个 OPT 批次只跑一条命令（汇总里是"OPT01 1/1""OPT09 1/1"）。原要求是把**每个模块**"验收"小节里的命令都整理进去。OPT09-D、E 没做而脚本仍报通过，正是因为它没有检查这两个模块。

**做法。**

1. 逐个打开 `docs/fsc_opt/OPT01`–`OPT10`，把每个模块（OPT01-A、OPT01-B……）的验收命令和可机器判断的断言整理进脚本的清单表。每行注明模块号与来源。
2. 文本类断言也要进脚本，例如：
   - OPT09-E：`src/` 业务代码中无 `window.confirm`。
   - OPT08-A：`src/` 中除白名单外无 `parseFloat(` 的金额用法。
   - OPT02-C：`ruff check nexus_backend/app` 零错误。
   - 体积预算通过。
3. 把 `docs/rework/` 各模块的验收命令也加入，作为 RWK 分组。
4. 脚本开头先运行 `scripts/check_test_env.py`；环境与锁文件不一致时直接以失败退出，不继续。
5. 汇总按模块输出：命令数、通过、失败、跳过（PG）、无自动检查（并说明为什么只能人工判断）。**没有任何自动检查的模块不得显示为通过。**
6. 脚本保持只读：不改库、不改源文件，输出到 `tmp_test/rework/RWK05-A/<运行标识>/`。

**验收。** 运行两次结果一致；汇总表贴入状态文件。为证明脚本确实在检查：临时在 `src/` 某业务文件加一行 `window.confirm('x')`，脚本对应项失败，撤掉后通过，把失败输出贴入状态文件。

## RWK05-B  有数据的审计链验证

**现状。** `scripts/verify_audit_chain.py` 只在空库上跑过，只能证明脚本能运行。

**做法。** 新增一个测试（SQLite；PG 有环境则同样做）：

1. 通过**真实服务流程**产生审计记录：两个事务所，各自建单位、导入、制单、复核、过账、冲销、授权变更、下载原件。每个事务所不少于 50 条审计行。不直接往审计表插行。
2. 运行校验：返回 0。
3. 复制该库，在副本上分别做三种破坏（绕过触发器：测试内临时移除触发器或直接操作副本文件）：改一行内容、删中间一行、交换两行。每种破坏后校验返回非零，并报出断点的主键。
4. 确认仓库中现有的全部审计写入路径都被覆盖到：搜索 `INSERT INTO audit` 的位置，列出每条路径对应的动作名，核对步骤 1 产生的记录中出现了哪些动作名、哪些没出现。没出现的列入状态文件，并尽量补进步骤 1。

**验收。** 新增用例通过；状态文件贴出覆盖到的动作名数量与未覆盖清单。
