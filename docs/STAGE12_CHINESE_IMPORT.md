# 第十二阶段：中文流水导入向导

面向少数真实企业试点的文件导入。原件保留、字段转换与去重均由确定性代码完成；导入不会自动审核或导出凭证。

## 操作路径

1. 在目标企业月份选择“导入流水”，上传CSV或单工作表.xlsx；也可粘贴中文或原英文CSV。
2. 填写固定来源与脱敏银行账号。同一银行的同一账号应一直使用相同标识。
3. 人工确认中文字段与原表列的对应，选择日期顺序以及金额/收支模式。
4. 逐行查看转换结果、错误、相似交易提醒及新增收入/支出合计。
5. 确认目标企业、月份、账号及合计后导入。任一错误阻止整批，重复交易跳过，身份内容冲突整批回滚。

手机使用同样的三个步骤，预览采用卡片而非宽表；每页20条，错误可单独筛选。格式记忆保存在服务端当前事务所、账套、固定来源、银行账号范围内，读取和确认均重新检查当前账号授权；没有全局浏览器缓存。

## 文件与转换边界

- 文件最大2MB、每次1,000条流水、64列、单元格2,000字。
- CSV先严格UTF-8解码，失败后尝试GB18030（兼容GBK）；表头必须非空且唯一。
- .xlsx使用受限ZIP/XML解析，不执行公式；公式、宏、外部链接、实体定义、UTF-16/32 XML、异常压缩比和超限解压内容拒绝。多工作表请单独另存目标流水表。旧.xls请另存为.xlsx或CSV。
- Excel读取原始数字文本，不先转成浮点数；日期序号须显式选择Excel日期格式。1904日期制需先转成文本。
- 默认年/月/日；日/月/年和月/日/年须显式选择。模糊日期、科学计数法、多于两位小数不猜测、不四舍五入。
- 金额支持明确收入/支出列、收入/支出双金额列、显式正负模式。千位逗号只有用户确认后才转换；借/贷标志不能直接推断收入支出。
- 总计使用整数分精确计算。每笔金额沿用领域范围，批次合计允许超过单笔上限。

银行原始交易号优先，其次原流水编号。两者均缺失时使用文件SHA与逻辑记录位置作为幂等身份；只能保证同一文件同一行重复导入可识别。换文件、排序或改动文件后仍须会计检查相似流水，不能将生成编号解释为银行交易的绝对身份。

## 原件、追溯与权限

原始文件存于现有私有原件目录，采用相同的安全存储键。`bank_import_files`进入数据库与原件一致快照备份。预览保留原始单元格、实际原表行位置、字段映射、转换规则和规范化流水；确认同事务写入来源、冻结回执及来源-原件关系。确认时重新读取并核验原件SHA与大小，并再次检测交易身份冲突。

预览、确认、格式版本及原件元数据不可覆盖；已有英文CSV导入API和原有fingerprint规则不变。银行原表用于来源追溯，其本身不代替发票、合同或补件的人工业务核验。未填凭据引用的来源仍按原流程提示会计补证。

所有读取与写入依赖当前账套授权；PostgreSQL五个新表均FORCE RLS，worker无表读取权限。下载无公开URL，先重新授权，再核验原件完整性，以attachment形式返回；同屏证据仅以安全文本展示原表和转换依据。

## API

- `POST /api/books/{book_id}/import-wizard/files`：multipart `file`，返回表头、样本、编码和建议映射。
- `POST .../paste`：`{filename?,content}`，保留粘贴原文为CSV原件。
- `GET .../profiles`：当前获编辑授权账套保存格式的最新版本，最多50个。
- `POST .../previews`：`{file_id,namespace,bank_account,mapping:{columns,date_format,amount_mode,allow_grouping}}`。
- `POST .../previews/{preview_id}/confirm`：`{remember_mapping?}`；同预览重复确认返回冻结回执。
- `GET .../files/{file_id}`：受保护原件下载。
- `GET .../sources/{source_id}/evidence`：`{originals:[{file_id,filename,sha256,row_number,original_position,headers,raw,normalized,mapping}]}`；没有关联文件时返回空列表。

`row_number`是冻结的逻辑记录位置（表头算1），`original_position`是CSV记录开始行或Excel工作表真实行，用于界面定位。真实T+接口与原生导入格式不在本向导范围，继续使用已审核后导出的既有交付流程。
