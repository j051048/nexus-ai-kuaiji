# 第四阶段票据识别与记账建议数据库

第四阶段的模型结果保存在独立证据表。OCR 不直接改员工表单，记账建议只有经授权人员应用后才改凭证草稿；原有会计复核和导出仍是独立步骤。

## 迁移与部署

SQLite 的 `005_intelligence.sql` 由本地迁移器应用；PostgreSQL 的 `010_intelligence.sql`、`011_intelligence_open_event.sql` 和 `012_intelligence_open_period.sql` 由管理员显式应用。`011` 向已有事项访问权限的人员提供是否仍可处理的布尔值；凭证审核后，即使员工不能读取账套映射，仍能正确阻止继续识别。`012` 将已关闭或缺失的映射会计期间纳入冻结判断。函数不提供账套或凭证 ID。现有已应用迁移的原文及校验和保持不变。使用管理员数据库连接执行 `python scripts/migrate_accounting.py migrate`，再用受限运行账号启动后端。Supabase 采用同一流程，`accounting` schema 仍由后端私有访问，不开放到浏览器 PostgREST。

新增表全部启用并强制 RLS。运行角色 `accounting_app` 是 `NOLOGIN / NOSUPERUSER / NOBYPASSRLS`；`accounting_system` 只有身份同步职责，没有任何新增 AI 业务表读取权。安全函数固定 `search_path`，撤销 `PUBLIC` 执行权，只有受限会计运行角色获得必要调用权。

## 数据契约

| 表 | 用途与关键约束 |
| --- | --- |
| `ai_company_settings` | 每个事务所与企业的外部识别开关；默认关闭，由企业或事务所管理员维护 |
| `ai_runs` | OCR 或记账建议请求的认领、输入指纹、版本、模型与提示词版本、输出、用量及终态 |
| `ai_findings` | 确定性核对产生的异常；按事项、代码和事实指纹去重，只能追加 |
| `ai_finding_reviews` | 独立财务或会计对异常的人工处理依据，只能追加 |
| `ai_proposal_applications` | 建议应用到草稿的唯一回执；同时绑定事项、企业、账套、草稿和识别运行 |
| `ai_bank_links` | 银行来源到业务事项的核对关联；每条银行来源最多关联一个事项 |

所有 AI 原件、运行、异常、处理记录都有 `(event_id, firm_id, company_id)` 复合外键。OCR 运行的附件还须属于同一事项；建议运行的账套须属于同一企业，其草稿须属于同一账套。建议应用回执进一步绑定既有 `business_mappings`，防止同账套内错误地修改另一事项的凭证。

运行认领只允许 `running` 状态。原始身份、输入版本、输入指纹、幂等键、模型及提示词版本不可改；运行只能一次从 `running` 变为 `succeeded / failed / stale`，终态输出不可改。成功结果是 JSON 对象，失败及过期结果不保存模型正文。终态必须保存完成时间。事务所、事项、种类和幂等键唯一，网络重试不得重复认领。

模型网络调用应在认领事务提交后执行，完成时重新核对当前业务访问和处理权限。失权时不发布模型正文。有限清理函数 `abandon_ai_run(run_id)` 只允许原请求人在原事务所内将自己的运行置为 `stale`，清空结果，返回 `VOID`；即使业务权限已撤销也不会遗留永久运行状态。该函数不返回事项、附件、模型正文或其他运行信息。

异常事实与人工处理依据不可修改或删除。新事实产生新的异常指纹，历史确认不会自动确认同类新异常。人工确认理由不得为空白。凭证建议应用回执不可修改、删除或重复应用同一运行。

## 权限边界

企业识别开关可由企业、事务所管理员维护，企业成员和授权账套人员可读这一开关。管理配置不会打开员工原件。

OCR、异常及异常人工处理记录沿用现有业务事项可见范围：本人、明确授权的部门审批人、企业财务，以及事项移交后授权账套的人员。未移交事项的原件不会因为事务所管理身份或企业管理身份自动开放。

实际触发识别要求业务处理身份：申请人、明确部门审批人、企业财务，或移交后有账套编辑权的会计。账套查看人员可查看已经移交的相关证据，不能触发外部模型费用。运行结束仍由原请求人提交，并重新核对其处理权限。

人工异常确认要求企业财务或授权账套复核身份，并禁止确认本人申请的事项。部门审批权不等同于会计异常复核权。应用记账建议要求账套编辑权；应用行为不授予凭证审核或导出权。

银行关联的账套与来源 ID 仅向企业财务或有账套读取权的人员开放，员工及部门审批人不能凭业务事项访问全企业流水。新增或撤销关联要求账套复核权，或企业财务同时拥有账套编辑权。数据库结构同时要求关联到已移交事项、同企业账套、同账套银行来源；创建关联要求事项已支付，银行和业务凭证都仍为未审核草稿。业务凭证审核后不允许撤销关联。银行来源永久保留，撤销关联的理由应另外追加到既有审计表。

会计服务在凭证审核和导出事务中重新计算当前确定性核对结果，阻止未解决的 `blocking` 异常。该读取不会新建异常，也不会调用模型；必须先通过人工核对流程登记当前异常并保留独立处理依据。企业识别政策默认关闭时，既有人工审核与导出流程继续可用。已关联到业务事项的银行来源，在政策关闭时仍禁止重复审核或导出为另一张流水凭证。

SQLite 保持这些外键、JSON、不可变和关联状态约束，但不具备 RLS，权限仍通过同一应用服务验证。真实企业部署采用受限 PostgreSQL 运行账号。

## 独立数据库验证

`nexus_backend/tests/test_intelligence_postgres.py` 直接操作受限 SQL，使用随机测试事务所、企业和账号 ID，不截断既有表。2026-10-11 在专用本机 PostgreSQL 完成基础 25 项及新增的事项冻结布尔函数测试，累计 26 项通过；SQLite 的新库全迁移也已验证成功。测试需要明确指定专用管理员及受限运行连接：`ACCOUNTING_TEST_POSTGRES_URL` 与 `ACCOUNTING_TEST_DATABASE_URL`。

覆盖本人、部门、企业与账套可见范围；管理员配置不开放员工原件；查看人员不能认领模型调用；运行请求人和附件归属校验；幂等认领与终态不可变；撤权后不能发布、仅可有限清理；禁止申请人及部门审批人确认会计异常；异常新事实不沿用旧确认；银行关联隔离、跨企业错配、未支付和已审核状态阻断；建议应用回执绑定正确事项和草稿，应用后仍需会计复核。

`nexus_backend/tests/test_intelligence_ledger.py` 另外完成 23 项审核/导出服务验证，其中 11 项使用真实 PostgreSQL；覆盖默认关闭政策、缺失 OCR、金额差异、审核后才开启政策的导出复核、人工确认及新事实失效、模型配置损坏时纯读取不受影响、共享与独立服务实例行为一致、关联银行来源重复入账阻断，以及关闭期间时员工仍不能继续处理。连同原会计流程 41 项测试，64 项通过；仅一个 PostgreSQL 专用案例的 SQLite 参数按设计跳过。

`nexus_backend/tests/test_intelligence_workflow_postgres.py` 使用完整业务服务 payload、真实私有图片附件和合成模型输出，另外 17 项真实 PostgreSQL 测试通过。覆盖 OCR 到模型建议、幂等采用、独立会计复核及导出全流程；员工及部门看不到分录正文及账套 ID；调用中撤销成员、停用账号、暂停企业或关闭期间后不发布结果；会计编辑或撤销账套授权使晚建议失效；无效科目、借贷和来源引用拒绝；并发采用只创建一份回执；模型调用不持有数据库写锁；其他人员不能清理原请求人的运行；银行关联理由与原件留存；已应用模型警示不会因普通凭证编辑而消失；原始 SQL 也无法跨企业读取识别、异常及人工处理记录。

本机 PostgreSQL 与合成测试记录验证数据库及服务边界，不替代真实票据 OCR 准确率、供应商接口兼容性或真实企业月份验证。试点仍按 2–3 家企业分别授权，并保留会计复核后导出。
