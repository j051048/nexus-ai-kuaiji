# OPT06：不相容职务分离与断号巡检

先读 `OPT00_MASTER.md`。前置：OPT03（策略变更需要可靠审计）。本批对应 FSC03 的追加项，不改变 FSC03 "指派不授权"的原则。

## OPT06-A  集团策略可禁用单人模式

**问题。** `nexus_backend/app/accounting/review_policy.py` 支持 `single_operator` 模式：制单人填写不少于 3 个字符的理由即可自己复核。默认是 `independent`，切换需事务所管理员加多因素认证并留痕。国企场景需要能在更高层级彻底禁用。

**做法。**

1. 读懂现有模式存储、切换接口、`firm_review_evidence` 冻结方式。
2. 增加事务所级策略项"禁止单人模式"。开启后：
   - 任何账套切换到 `single_operator` 返回 403。
   - 已处于 `single_operator` 的账套，新的自我复核被拒绝；历史复核证据不动。
   - 该策略项自身的开启和关闭都要求多因素认证并写审计。
3. 关闭该策略项的门槛高于开启：除多因素认证外须填写理由。是否还需要第二人批准，属于业务决定，本模块不实现，在状态文件"待业务决定"中列出。
4. 数据库层同步加约束或触发器，使绕过服务直接写库也无法在策略开启时把账套设为单人模式。
5. 前端在审核策略页面显示当前策略状态，策略开启时禁用单人模式选项并说明原因。先搜索 `single_operator` 的前端使用点。

**先失败测试。**

- 策略开启后切换单人模式返回 403，审计中有拒绝记录。
- 策略开启后，原本处于单人模式的账套里制单人自我复核被拒。
- 直接以业务角色写库设置单人模式被数据库拒绝（PG）。
- 未通过多因素认证时不能修改策略项。

**验收。** 新增用例 SQLite 与 PG16、PG17 通过；现有 `review_policy` 相关测试全过。

## OPT06-B  人员权限管理与账务复核分离

**问题。** `nexus_backend/app/accounting/access.py` 中事务所 owner 和 admin（代码里的 manager）直接拥有编辑、复核、导出、管理全部权限。管理账号的人同时能复核账务。

**设计约束。**

1. 这是高风险改动。**先只读分析，把方案写进状态文件，再动手**。方案须包含：manager 短路出现的所有位置、每个位置改动后的行为、受影响的现有测试清单。
2. 做成事务所级可选策略"管理与复核分离"，默认关闭，保持现有部署行为不变。开启后：
   - owner 和 admin 不再因角色自动获得复核权和编辑权，须像其他成员一样被显式授予账套角色。
   - 拥有"管理成员与授权"能力的人，不能复核任何凭证、不能批准关账、不能批准税务底稿。
   - 管理员不能给自己授予复核角色。
3. 开启策略前检查：每个账套至少有一名非管理员的复核人，否则拒绝开启并列出缺口账套。
4. Postgres 的 RLS 策略和 `require_review_authority` 等数据库函数若也有 manager 短路，同步处理。先搜索迁移中的相关函数。
5. 策略开关要求多因素认证并写审计。

**先失败测试。**

- 策略开启后，admin 调用复核、关账批准、税务底稿批准接口均返回 403。
- admin 给自己授予复核角色被拒。
- 存在无复核人的账套时开启策略被拒，响应中列出账套。
- 策略关闭时所有现有行为不变（现有测试不改动即通过）。
- PG：策略开启后 admin 身份直接写复核证据表被数据库拒绝。

**验收。** 新增用例通过；全量后端测试在策略默认关闭下无新增失败。

## OPT06-C  授权替补

**问题。** 复核人请假时没有受控替补路径，现实中容易变成共享账号或自审。

**做法。** 先查 `nexus_backend/app/execution/`、`nexus_backend/app/handoff/`、`nexus_backend/app/fsc/organization.py` 是否已有代办或指派机制。已有则在其上补齐以下约束，不另造：

1. 替补授权有明确的起止时间、范围（哪些账套、哪种职责）、发起人、批准人。发起人与批准人不同。
2. 到期自动失效，每次权限判断时按当前时间计算，不依赖定时任务清理。
3. 替补人仍受"不能复核自己制的单"约束。
4. 授予、使用、到期、提前撤销都有审计。

**先失败测试。** 生效期内替补人可复核；到期后同一请求返回 403；替补人不能复核自己制的单；发起人自己批准被拒。

**验收。** 新增用例 SQLite 与 PG 通过。

## OPT06-D  凭证断号巡检

**问题。** 编号在过账事务内分配并有唯一约束，正常不会断号，但没有检测手段。审计会问"怎么证明没有断号"。

**做法。**

1. 在 `nexus_backend/app/posting/` 或 `ledgers/` 增加只读检查：按账套、凭证字、期间，检查编号是否从 1 连续到最大值，返回缺失编号清单。
2. 把它接入 `b04_close` 的月结预检，作为一个检查项。有断号时预检不通过并显示缺失编号。
3. 用 SQL 完成检查，不把全部凭证读进内存。

**先失败测试。** 绕过服务构造一个断号的账套（测试内直接插入，注意凭证表是追加型，只能插不能删）：检查返回缺失编号，月结预检不通过。连续编号的账套通过。

**验收。** `python -m pytest nexus_backend/tests -q -k "close or posting"`。
