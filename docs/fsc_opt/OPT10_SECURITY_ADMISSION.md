# OPT10：备份加密、敏感字段脱敏、接口限流

先读 `OPT00_MASTER.md`。前置：OPT03。本批是内部医院准入清单中软件侧能做的部分。部署形态（是否允许云端和外部模型）、核算制度、数据分级是客户决定的事，本批不涉及，也不要在代码或文档里假设结论。

## OPT10-A  备份加密

**问题。** `scripts/backup_accounting.py` 生成数据库导出和原件副本，设置 `0o600` 权限并写 SHA-256 清单，没有加密。

**做法。**

1. 读完整个脚本及其测试，弄清备份产物结构、清单格式、恢复校验和恢复保持标志。
2. 增加可选加密，由配置开启；生产环境配置下未开启则拒绝运行并说明原因。
3. 算法用经过认证的加密（AES-256-GCM 或同等），用成熟库实现。先查 `nexus_backend/requirements.lock` 中是否已有 `cryptography`；没有则在状态文件提出依赖新增请求并停下本模块，不自己实现加密算法，不用无认证的模式。
4. 密钥来自环境变量指向的密钥文件或外部提供，不写入备份目录、不写日志、不进清单。清单记录密钥标识（如密钥摘要前若干位）以便恢复时选对密钥。
5. 大文件流式加密，不整体读入内存。
6. 清单同时记录明文摘要和密文摘要。恢复时先验密文完整性，解密后再验明文摘要。
7. 恢复流程支持加密备份；密钥错误、密文被改、清单被改，都明确失败且不留下半恢复状态。

**先失败测试。**

- 加密备份后产物中搜不到已知明文片段（数据库中的一个特征字符串）。
- 正确密钥可恢复且恢复后数据一致；错误密钥失败；篡改密文一个字节失败。
- 生产配置下未开启加密时拒绝运行。
- 现有未加密备份的恢复测试不改动即通过。

**验收。** `python -m pytest nexus_backend/tests -q -k "backup or restore or recovery"`。

## OPT10-B  敏感字段脱敏展示

**问题。** 银行账号、纳税人识别号等在接口和界面上完整显示，没有脱敏能力。

**做法。**

1. 盘点：搜索迁移和模型中的银行账号、纳税人识别号、手机号、证件号类字段（关键词 `bank_account`、`account_no`、`tax_id`、`phone`、`mobile`、`id_card`、`证件`）。在状态文件列表：表、字段、出现在哪些接口响应中。
2. 后端新增一个脱敏工具模块：按字段类型给出规则（如银行账号保留后四位，纳税人识别号保留前二后四）。纯函数，可测试。
3. 接口默认返回脱敏值。需要完整值的场景（如导出给银行、报税底稿）走单独的显式接口或参数，要求相应权限，并按 OPT03-C 写审计。
4. 前端显示脱敏值；有权限的用户点击"显示完整"时调用上述接口。
5. 用于匹配、对账、去重的后端内部逻辑继续使用完整值，不受影响。逐个确认没有哪处逻辑误用了脱敏后的值。
6. 日志和错误信息中不出现完整敏感值。搜索日志调用点确认。
7. 字段级加密存储不在本模块范围，列入状态文件"未做"。

**先失败测试。**

- 列表和详情接口响应中不含完整银行账号（修改前包含）。
- 无权限用户请求完整值返回 403；有权限用户成功且产生审计行。
- 对账和别名匹配的现有测试不改动即通过。

**验收。** 新增用例通过；全量后端测试无新增失败；类型检查通过。

## OPT10-C  接口限流

**问题。** 除导入向导每小时 20 个文件和模型配额计量外，没有通用限流。两个无登录的回调入口（`nexus_backend/app/ingestion/router.py`、`nexus_backend/app/delivery/callback_router.py`）只靠令牌和签名。

**做法。**

1. 读 `nexus_backend/app/main.py` 现有中间件的顺序和写法。
2. 加一个限流中间件，不引入新依赖：
   - 已登录请求按用户限流；未登录入口按来源地址限流。来源地址的取法要与现有可信代理配置一致，先查现有代码如何取客户端地址，不直接信任 `X-Forwarded-For`。
   - 分三档额度：读、写、高成本（登录相关、导出、下载、回调）。额度从配置读取，有默认值。
   - 超限返回 429 和 `Retry-After`，错误体沿用统一的 `{detail: "中文信息"}`。
3. 计数存储：多进程部署下进程内计数不准。先用数据库或现有共享存储实现一个简单的固定窗口计数；若评估后对每个请求写库代价过高，可以做"进程内计数加明确文档说明其为单进程近似"，并在状态文件写明这一局限。选哪种写明理由。
4. 健康检查和公开配置接口不限流。
5. 被限流事件按用户或来源汇总记录，不逐条写审计。

**先失败测试。**

- 超过写额度后返回 429 且带 `Retry-After`；窗口过后恢复。
- 一个用户超限不影响另一个用户。
- 回调入口按来源限流；签名错误的请求同样计数。
- 健康检查不受影响。

**验收。** 新增用例通过；全量后端测试无新增失败（测试中大量请求触发限流的，通过测试配置提高额度解决，不关闭中间件）。
