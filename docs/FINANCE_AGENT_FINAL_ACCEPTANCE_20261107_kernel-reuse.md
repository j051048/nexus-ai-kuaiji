## 结论与采用范围

原任务书中“复用现有能力、确定性金额、可执行入口、证据与版本绑定”的方向有价值。本轮采用现有核算内核的修补和接线：往来账龄、资产卡片、期末草稿独立复核及正式记账。没有把 13 个包全部标成完成，也不是发布验收报告。

新增企业费标、差旅审批、语音和发票验真有潜在业务价值，但属于新的产品政策与供应商契约。当前没有已确认的企业城市/职级/住宿标准、例外批准责任和外部查验结果口径；不宜把这些假设写成默认拦截规则。FakeProvider 可以验证协议，却不能让实际业务记录显示已经验真。未开账也不应阻止员工保存、提交真实资料，已有交接准备检查继续保留。

本轮选择的新增路径已完成本地专项；扩展 SQLite 回归仍有一条历史夹具失败，故不能宣称全仓通过或当前候选可发布。

使用入口：打开有权限的账套 → 正式账簿 → 展开“往来与期末办理”。账龄页按四类往来查看；资产页按“登记卡片 → 生成草稿 → 另一位会计复核 → 确认记账”办理。默认折叠，不增加首页模块。查看账龄、建卡、生成草稿均不会自动导出或正式记账。

`test_c01_closure.py::test_legacy_unresolved_adjustments_cannot_cancel_each_other` 只应用 `<96` 的 SQLite 历史迁移，却用当前 `business` 开户夹具。当前开户权限查询依赖 `effective_book_access`，在旧库不存在，因而尚未进入银行调整断言便失败。

已单独复跑，见 `legacy-diagnostic.xml`；调用链涉及的测试、开户与权限源码逐一确认与本轮开始前相同，见 `legacy-failure-classification.json`。本轮没有改旧 SQL、伪造权限视图或删除断言。后续应使用真实历史结构的原生种子或版本化历史快照，再走前向升级，修复夹具；该失败使全量集成结论保持“未通过”。

## 发布边界与收尾

后续按价值排序：

1. 修历史夹具：在真实旧结构中原生种入两笔相抵但未解决的调整，再应用前向迁移；断言净额为零仍不能关账，不能用当前开户服务创建旧历史，也不能补一张假权限视图掩盖缺口。
2. 在现有服务上继续接通往来事项登记、部分核销和反核销办理；先明确来源凭证与项目维度，再扩展 UI，不重建核销模型。
3. 若确有业务需求，再定义资产跨期承接、处置/减值的凭证与复核契约。当前卡片入口不等于完整资产管理系统。
4. 费用标准应由企业确认、版本化并显式启用；缺少可信职级/城市/夜数时显示待核对，不虚构标准，也不阻止保存真实业务资料。发票验真则先确认供应商证据、状态和人工例外口径，再实现本地适配器及独立验收。
5. 差旅/语音排在真实复核与交付链跑顺之后；真实试点沿用现有人工分钟、退回率、未知值和独立复核分类，不新增一套好看的平均分。

本轮未重跑完整恢复与容量。上一轮 `66eb1619…` 的恢复、50 并发及 200 家数据仍是历史候选证据，不继承为本轮通过。没有本轮生产容量、真实模型准确率、发票查验、通知送达、真人真机或客户试点结论。
