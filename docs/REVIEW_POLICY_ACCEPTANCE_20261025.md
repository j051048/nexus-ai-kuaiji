# 独立复核政策与执行一致性：本地验收记录

日期：2026-10-25。基线：`3fc1ab6e11761ba36490f1858b85fcff356441cc`。

本轮在独立工作副本中实现；不操作线上、不连接真实模型、不提交、不推送。企业隔离、会计复核后导出、C01 原有核验规则均为保留约束。本文件记录产品政策与本地工程证据，不是法规合规认证或上线批准。

## 本轮行为

1. 长期账套默认采用独立复核。当前待审内容绑定制单责任人、业务版本、逐次内容修订号；制单人不能独立审核该版本。原件、分录和辅助项修改后，旧版本不能继续审核。
2. 事务所管理者可以显式选择单人办理，须具备原有管理权限、二次验证、当前政策版本和理由。每次单人审核另留理由，冻结凭据显示“单人办理，非独立复核”。已有客户申请人与审核人分离、期末独立审核规则继续有效，不因该政策被豁免。
3. 开通检查、单笔/批量预览与确认共用政策。预览包含制单责任和政策版本；政策变化或撤权后须重新校验。批量重试保持原命令及原理由。
4. 手工凭证先保存完整待审内容，再由具备资格的人员审核，最后凭审核记录正式记账。重复命令不重复入账；同一复核凭据不能授权不同分录、账户、原凭证或账套。
5. 尚未审核的手工凭证可由仍有编辑权的制单人填写原因撤回，保留原内容及独立撤回历史。已审核内容不能按此入口撤回；需走原冲销/调整流程。未记账的有效手工请求纳入月结阻断项。
6. PostgreSQL 使用 RLS、最小授权、可信触发器及事务内完整性约束重复执行上述边界；SQLite 运行连接保护内部证据表、触发器及关键约束设置。应用角色不能直接伪造审核凭据或完成证明。
7. 历史记录不猜测制单人，不补造独立复核。无法确认责任的旧待审版本须显式认领；既有已审历史显示独立性未核定，缺乏当前责任凭据时禁止新的正式记账/导出。

## 版本契约与迁移候选

业务版本继续遵循“完整改稿一次加一”，逐行变化用 `content_revision` 与历史表记录。SQLite 连接提供不可由 SQL 自报的事务标识；PostgreSQL 标识包含数据库、服务启动时间和事务 ID。原生 SQL 在新的事务中改分录也会使旧业务版本失效，空操作不能占用变更标识。

早期未发布候选曾对每条分录分别提升业务版本，实际回归发现它破坏历史核销的 `expected_version + 1` 契约。先保留失败证据，再修正本轮新增迁移；没有修改历史核销的守卫、旧迁移或已应用数据库的校验和。

- 新 PostgreSQL 迁移：162–166；SQLite：100–103。
- 旧候选字节、哈希及中间证据保留于本地 `.codex/review-responsibility/`。
- 最终候选在新空的 PostgreSQL 16/17 隔离库重新从 1 迁移，不复用旧候选数据库。
- 本次为含数据库约束变化的发布，不能混用旧 API/worker 与新数据库。实际部署仍须另行授权及迁移前备份核验。

## 红—绿与兼容性证据

- 默认自审、手工直接记账、政策权限与版本、不可变责任凭据：先失败后实现服务及数据库保护。
- 批量预览包含本人改稿、过期政策；保留原错误、部分成功和幂等测试，并改用真实不同制单/审核身份。
- SQLite 运行 SQL 关闭外键/校验的三项负向测试先失败，随后限制运行连接；迁移使用独立连接。
- 人工改稿/采纳 AI 建议的保护标记曾落在中间版本，已复现并绑定完整内容最终版本。
- 事务标识先以缺少函数失败；随后验证同连接缓存 BEGIN、隐式事务、嵌套保存点、回滚、外部追踪回调均不能复用旧事务身份。
- 月结增加手工待办后，数据库原六项完整性守卫与七项结果不一致产生真实 409；新迁移保留原六项并强制第七项，不删减校验。
- 历史核销整文件 18 项在逻辑版本修正后通过，原金额、分配、冲销和 `+1` 断言保留。
- 新月结测试曾将检查行正常值误写为 `passed`；实际标准为 `pass`（整体为 `preflight_passed`），只修正新增测试的拼写，不改服务协议。
- 额外历史核销 PostgreSQL 原七项测试暴露旧锁域不一致：服务已采用企业事务，旧 `legacy_clearance_guard` 仍要求全局锁。166 仅将该函数锁入口接入既有企业锁兼容函数，保持原金额、引用、版本、权限和原子完整性校验；不修改已应用的 162–165。
