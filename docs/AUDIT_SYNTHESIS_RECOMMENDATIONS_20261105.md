**衡账后续改良建议报告：三份审计与当前代码交叉核对版**

日期：2026-11-05。基线：HEAD `47488e0a9c1c723622597d654337f626316b6b14` 与当前未提交工作区。

本报告用于规划，不是发布验收、生产认证或真实用户评价。核对范围为用户提供的三份报告、当前相关代码和已有验收记录；本轮没有重新进行生产巡检、全量测试、真实模型调用或真人真机试用。新增此独立报告，不覆盖既有 `POST_AUDIT_IMPROVEMENT_REPORT_20261105.md`，不修改业务代码。

**核心判断**

最有价值的主线是：让员工更容易交齐资料，让财务更容易找出问题，让会计更容易连续办理，让负责人更容易发现需要协调的客户。把控制放在可靠的后端，把当前任务、必要证据和一个清楚的下一步留在前端。

现阶段应先继续减轻高频工作界面，再用真实使用和固定评测证明收益。AI 分析和数据库职责整理值得做，但不应抢在员工提交、财务核验、会计复核的最后一段体验之前。现有功能应先接好、用好，不再新建一套导航、状态系统、任务系统或回放框架。

三份报告的评分、所谓“Google 内部评级”“L4”“彻底杜绝幻觉”“免疫提示注入”均不能作为证明。报告未提供对应评级标准或全面攻击证据。代码中的确定性校验和权限约束值得保留，但只能声称在明确测试范围内成立。

**01．当前候选与验证状态统一**

- 核清本地修改归属，区分身份展示、CI 修复、其他并行成果和报告文件。
- 将测试结果绑定可复现的代码、配置、迁移与数据夹具版本。报告补记可以注明“不改变运行代码”，但不能冒充旧的全树候选指纹。
- 本地通过、远端 CI 通过、生产健康、真实模型、通知通道、真人试点分别列状态；部分完成不升级为整体验收。
- 发布前执行对应 PG16/17、联合恢复与关键业务门禁；获授权推送后才能核验远端，不自动触发部署。
- 不因 UI 改动无关而机械重跑全部容量；但复核、权限、持久化或发送链变化必须触发相应动态测试。

验收：任何“已通过”能找到准确候选与原始结果；必需测试没有静默跳过；没有将历史不同候选的结果拼成当前发布通过。

**02．岗位外壳与首屏压缩**

- 延续现有视觉基调，不重做品牌。减少装饰英文、重复页名、常驻岗位说明和无用的环境信息。
- 所属单位和当前身份保持直接可见。事务所会计的“所属事务所”不能随着当前客户切换而变成客户公司。
- 办理时明确当前企业、账套和期间；跨客户列表明确“全部已授权客户”或当前筛选，不能任取第一家公司当默认上下文。
- 员工只显示完成任务需要的信息，不把账套权限、数据库术语堆到他面前。权限详情仍可展开，加载失败与撤权不得留下旧的能力宣称。
- 员工首页重点是提交和退回补件；财务是待核验；会计是待复核与阻断；负责人是逾期客户和待协调事项。不要让四种岗位变成同一张密集表格。
- 可尝试一条紧凑全局栏加必要上下文，不能把“全部塞进固定 56px”当硬指标。

验收：桌面和手机上无需打开个人菜单就能辨认所属单位与身份；关键业务操作前范围明确；切换企业、刷新、后退、撤权不显示旧范围；主任务与第一条可办理事项在常用初始视口内。高度收益与基线比较，不预先承诺节省 200px。

**03．待办列表与业务文案减负**

- 将“待我处理／办理进度”的重复统计收敛到一个紧凑切换区，数字不重复出现；保留已有分页和员工短清单。
- 常规行只需：摘要、客户或申请人、金额、状态或期限、主操作。常规复核不逐行重复整段安全说明。
- 退回、冲突、缺资料、权限不足、结果未知必须保留具体原因和下一步。若所有事项隐藏“处理说明”，新手仍会不知道怎么做。
- 同一异常多位负责人分别呈现，不按第一条原因替其他人作结论。待处理和等待他人必须由任务类型、当前负责人和有效权限推导。
- 复用 task-presentation、workflow-guidance 和现有格式化函数，不再建立覆盖所有领域的巨大文案模块。
- 系统生成标题优先采用业务摘要；没有摘要时，使用已有的业务类型、日期、金额形成可读名称，缺失信息不编造。原始摘要和原文件名完整保留；不能为去 UUID 而破坏合法发票号码或用户填写内容。
- 哈希、技术 ID、请求编号放在可展开且能复制的追溯区。需要报障时保留请求编号入口，不能为“零机器码”牺牲定位能力。
- 未知计数与真实零分开。可不显示数字并显示“查看清单”，加载失败给恢复入口；不能显示 0 或虚构“已完成”。
- “确认当前事实版本”可按具体动作改成“资料已更新，请重新核对”或“核对这版凭证”；不能统一改成“确认入账”，因为复核与正式记账并非同一动作。

验收：常规列表明显缩短；所有异常仍能回答“哪里有问题、谁处理、下一步”；返回保留搜索、分页与位置。可用同一组数据测桌面首屏完整条数与滚动距离，不能为了 64px 行高截掉重要内容，也不强求手机展示 8–10 条。

**04．手机录入与核验操作重排**

- 员工继续使用现有拍照/上传、预填确认、草稿恢复和同事项补件；更多字段保持折叠，必填和问题字段自动显露。
- 财务详情优先展示金额、申请人/事由、当前状态、原件入口或缩略图以及关键差异；常规长说明置后。
- 操作区保持可达，试验吸底布局时处理 safe-area、键盘、横屏、长企业名和浏览器缩放。只保留一套主操作区域，不与底部主导航叠加占高。
- 底部导航是待验证方案，不是必须全量替换。先比较一个岗位、同一任务的两个原型，再决定。
- 原件打不开、授权变化、版本过期时，按钮位置再明显也不能通过审核；不因打开图片就自动标成已核对。
- 不追求“秒批”。减少找按钮的时间，保留核验需要的证据与判断时间。

验收：正常核验首屏可辨认事项和金额，原件与动作入口易发现；阻断先于动作结果；键盘与操作栏不互相遮挡。桌面模拟之外，单独记录 iOS Safari、Android 浏览器和微信内置浏览器的真实测试结果，未测就保留未验证。

**05．真实使用与协同闭环验证**

- 立即复用 WORKBENCH_USABILITY_TRIAL：先请 3–5 位非技术员工和一线会计做形成性试用，使用虚构业务，观察员不教按钮位置。小样本用于找问题，不能推出“大家都好用”。
- 六项任务：提交、退回补件、中断恢复、财务核验与交接、会计复核返回、负责人找卡点。测试需包括不同公司与不同岗位，关注错范围和职责误解。
- 记录完成率、耗时、错路、求助、重复提交、丢失填写和状态理解；除平均耗时，也查看失败用户和长尾。
- 改前改后使用可比较的数据；保留真实异常，不只测空列表和顺畅成功路径。
- 邀请、消息、通知、资料交接和月度包签收也纳入协同任务。站内已读、通道接受、送达和客户签收分别计量，界面不得合成“已完成”。
- 真实企业、真实通知或真实模型另按授权范围开展。少量标准化客户连续两个完整月可作为试点方案，客户数量由支持人力和实际业务决定，不包装成容量上限。

验收：没有错企业、越权、绕过复核或重复业务写入；主要任务能独立完成，失败有可执行恢复路径。效率目标根据第一轮真实基线冻结，不从浏览器脚本用时推算人均产能。

**06．关键页面可读性与设计规范**

- 当前静态扫描结果为 67 个 CSS、25,444 行、2,062 处十六进制颜色文本、1,560 种写法、457 处字面量小于 12px 的字号声明。这些说明样式债务存在，但不是 457 处当前用户可见缺陷。
- 先测员工首页、录入、财务核验、同屏复核、客户工作台的最终计算样式与真实长文本，再删除被覆盖或不再使用的规则。
- 沿用 tokens.css：正文及表单以现有 14px 基准为主，手机输入沿用 16px，辅助信息至少保持现有 12px 标准。触控沿用 44px 相关 token，不用缩字和缩点击区换取密度。
- 数字等宽和金额右对齐有用；币种、负号和小数位仍须清楚。状态必须配文字，不只靠红绿颜色。
- 统一按钮、输入框、焦点、错误关联与帮助展开方式。帮助支持点击、键盘和触屏，不只 hover。
- 高频样式逐步改用已有语义 token；断点按实际内容需要收敛，不能批量正则替换全部像素值。
- 巨型组件先拆纯展示区块，保留一个状态与权限来源。不要同时重写路由、数据层和整套样式。

验收：关键页面文字与控制可读，放大、长名称和键盘访问不丢内容；局部截图与流程回归通过；新增样式不再扩大无规则取值。治理成功以实际问题减少衡量，不以 CSS 文件数减少衡量。

**07．困难票据与任务级评测补强**

- 复用 H01、AG05、RSI 和现有 FakeProvider；请求、来源、候选、费用与 attempt 的约束继续沿用，不搭第二套实验平台。
- 先建规模可管理、问题分布清楚的数据集，例如 100–200 个样本起步，再按缺口扩展。不要把 1000 张当自动产生质量保证的目标。
- 区分图片 OCR、字段提取、分录建议和助手任务四层，避免将 OCR 字符错误算成模型推理错误。
- 覆盖反光/模糊/旋转、多页、一图多票、含混摘要、历史版本、企业混淆、来源矛盾和未知结果。真实材料必须获授权并脱敏；合成数据与真实数据分开统计。
- 划分开发集和独立验收集；同原件的裁剪、换名、转码等变体按来源组划分，不能通过换 ID 泄漏。
- 金额、税额、日期、票号前导零、企业归属等关键字段用严格匹配；固定分母，missing/unknown 单列，关键退步不能被平均分抵消。
- 同时观察可回答任务成功率、适当弃答、人工修改量、耗时和成本。只有确实存在可解释概率置信度时才测 ECE，不把模型自报“很有信心”当概率。

验收：样本、金标、划分与候选绑定；坏候选能被拒绝；未接真实模型时仅宣布离线工程通过。固定集观察到零错误，不等于未来所有输入零错误。

**08．三个可解释的只读分析场景**

建议先选：本月为何不能交付；本月与上月某费用差额来自哪些记录；某张票据与凭证金额为何不一致。

- 复用现有调查和 ContextPack，只增加明确的参数化领域读取，不开放任意 SQL、网络或 shell。
- 对比要核对企业、账套、期间、币种、科目口径与事实版本；结果返回覆盖范围、未检查部分、分页和来源。
- 服务端确定金额、差额、排序与归属；模型可选择解释结构或提出待查方向，不能自己补数字或确定因果。
- 不能认为有 `[fact:id]` 就已验证一句话。事实“差旅费增加”不能证明“浪费”或“某人导致”；引用存在不代表支持断言。先使用可验证的结构化陈述与受控渲染，再研究更自由叙述。
- 用户答案组织为：当前结论、关键依据、未检查范围、谁来处理、能打开的现有入口；不可支持的问题给明确边界和人工路径。
- 每步仍查权限、范围、版本和租约，沿用费用预算和 attempt 链；已发送的未知结果不得自动重发或切供应商。

验收：独立任务集验证断言与来源的支持关系，不只检查数字存在；撤权或过期证据不发布；不自动复核、记账、导出、通知或签收；完整性与错误率一起看，不能全弃答换“零错误”。

**10．逐域整理数据库与 Python 职责**

- 先列每个约束防什么、哪些角色能绕过服务直接写、并发时依赖什么，再决定移动位置。

验收：原生 SQL 绕过、跨企业引用、撤权、复核与锁期竞争继续拒绝；PG16/17 无跳过动态回归和恢复验证通过；不存在以“薄数据库”为由转成仅靠应用自觉的控制。
