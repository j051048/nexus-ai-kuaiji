## 2. 缺口（按代账业务顺序）

1. 没有"本期销项/进项从哪来"的可追溯清单（凭证？发票导入？两者差异？）；
2. 没有"账上 2221 与底稿税额差多少"的核对（这是代账会计每个月手工做的第一件事）；
3. 没有版本化的底稿（谁在什么时候按什么口径算的、谁复核的）；
4. 没有导出物（客户要一份能看的税负说明，税务师要一份明细）。

## 3. 三档范围

### A. 只做底稿与核对（建议先做）
- 按期间生成**增值税底稿**：销项（来源：已审核凭证中 6001/2221 相关 + 发票导入 output 行）、进项（发票导入 input 行 + 凭证 2221 借方）、应纳税额、附加税（城建/教育/地方教育，税率可配置）。
- **差异核对**：底稿应纳税额 vs 账上 `2221` 净变动，超阈值即标红，必须人工写说明。
- 状态机：`draft → reviewed → delivered`（复用现有 `expected_version` + 独立复核：制单人 ≠ 复核人）。
- 导出：CSV（UTF-8 BOM，复用 `presentation.py` 的序列化与来源指纹）。
- 不做：申报表套打、不写凭证、不猜测留抵。

### B. A + 申报表草稿（PDF/Excel 套打）
需要维护各地申报表版式，版本化成本高，且没有真实申报口径来源，容易做成"看起来像申报表"的假东西。**不建议现在做。**

### C. B + 申报/缴款对接
涉及外部系统与法律责任，工作令已明确不做（不接真实外发）。**排除。**

## 4. 建议的最小切片（M1，约 3 个提交粒度）

1. **数据模型**：`tax_profiles`（企业 × 生效期间的纳税人类型/税率/附加税率/是否季报）+ `tax_workpapers`（book_id, period, version, status, inputs_json, totals_json, variance_json, created_by, reviewed_by, reason）+ `tax_workpaper_lines`（逐行来源：source_kind=invoice|voucher、source_id、方向、金额分、税额分）。
2. **计算服务**：`app/tax/workpaper.py`，纯确定性；金额一律整数分（复用 `invariants.money_to_cents`）；税率来自 `tax_profiles` 而非硬编码；缺 profile 时**拒绝生成**并说明缺什么，不猜。
3. **复核与导出门**：沿用 `review`（独立复核）+ `expected_version` 乐观锁 + `audit_events`；导出复用 `presentation.py` 的三阶段（快照→渲染→提交前重验）。

## 5. 风控红线（写进测试）

- 底稿**不写任何凭证**、不改 `2221`、不影响报表；
- 缺 `tax_profile`、缺期间、期间已锁、权限不足时一律拒绝，且错误可解释；
- 制单人不得复核自己的底稿（复用既有独立复核门）；
- 差异未写说明不得置为 `reviewed`；
- 导出必须带来源指纹与生成人，不导出"未复核"底稿给客户视图。

## 6. 验收标准（先红后绿）

- 单测：小规模 3% / 1% 征收率、一般纳税人销项-进项、附加税、四舍五入（分）、跨月不串期、缺 profile 报错；
- 差异核对：账上 2221 与底稿差 1 分也算差；
- 权限：非本书复核人不可复核；制单人复核被拒；
- 导出：来源变化后导出失败并提示重新生成（复用 Q05 的指纹机制）；
- PG16/17 上跑一遍真实 RLS（沿用 `tmp_test/p02_pg_*.py` 的建库方式）。
