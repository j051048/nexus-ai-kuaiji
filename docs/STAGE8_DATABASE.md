## 批量复核

`review_previews` 保存本人选择的账套集合、逐项版本、完整预览及有效期；`review_confirmations` 为预览保留唯一确认命令和个人幂等键；`review_book_receipts` 按确认命令与账套唯一保存结果。

三表启用 FORCE RLS，历史和回执不可更新或删除。预览、确认及回执的 SQL 能力重新检查当前事务所、本人身份及预览中全部账套复核权限；知道 ID 或保留旧令牌不能继续读取失权账套。成功回执要求包含该账套预览的完整集合，且所有凭证确实由当前复核人完成规定版本的审核；失败回执不能声称已审核项。

确认命令先独立持久化，随后每个账套使用一个写事务：重算预览上下文 → 校验全部选中项 → 调用单张审核内核 → 同事务捕获样例 → 保存账套回执。事务失败则该账套没有半批审核成功；其他账套可以分别完成。断电后重试根据已有账套回执恢复，不重新审核已成功的凭证。失败回执保留，重新处理须建立新预览。

审核内核继续检查期间开放、当前账套复核授权、草稿版本、有效科目及辅助项、精确借贷与来源金额、当前票据与流水异常、未关闭处理任务。申请人不能审核本人业务事项凭证。导出保留独立的当前完整校验。

## 异常与补件表

| 表 | 内容 |
| --- | --- |
| `case_tasks` | 当前企业来源、任务类型、优先级、期限、状态、版本与证据修订号 |
| `case_responses` | 响应草稿、提交、接受/退回与独立核验人 |
| `case_attachments` | 私有存储键、SHA-256、类型、体积和上传来源 |
| `case_history` | 带 `internal/requester` 受众的不可覆写历史 |
| `case_commands` | 个人幂等键、请求指纹及结果版本 |
| `case_supersessions` | 同事项旧原件的明确替代及接受来源 |

任务与事件、账套、来源、凭证的外键限制归属。业务 payload 和原始提交/审批快照保留在既有业务域。补件不写回旧快照；接受时在同一事务中更新响应、附件归属、替代历史及业务事实版本。银行补件使用不可覆写的 `source_evidence` 增量证据与草稿版本，不改原始银行来源。

员工补件接收人只访问公开请求和本人响应；内部调查与内部说明保留会计范围。银行资料收集人必须是本企业财务、有目标账套编辑权、并明确被指派。数据库通过受限收集投影和更新能力处理公开资料，不扩大内部 `case_tasks` 原始 SELECT 许可。收集人不能核验自己提交的响应，也不能通过指派取得额外账套或企业权限。

核验、指派、关闭与上传再次检查当前归属、角色、来源未审核及期间开放。业务补件提交人已失去企业成员权限时接受步骤拒绝。文件下载重新授权，并由私有附件存储校验内容哈希；数据库不保留公开下载地址。

`case_source_blocked(book, source)` 只返回授权来源是否存在未关闭任务；不会为了会计金额检查开放员工补件原件或内部任务备注。`event_superseded_attachments(event)` 仅返回当前可见事项的替代标识。票据核对、队列阻断与建议上下文使用当前有效附件，历史原件和替代关系仍完整保存。

补件状态变化和证据修订参与审核及建议上下文。接受更新 `fact_version` 后旧租约/候选失效；关闭任务只解除待办阻断，其他财务校验仍独立执行。

## 审核样例与规则

`learning_samples` 以凭证唯一保存真实审核来源：账套/企业/期间、审核与批准版本、业务/来源事实、原/最终分录、修正记录、证据指纹。捕获发生在批准状态更新之后的同一事务；事务失败不会留下孤立样例。样例不可修改或删除，来源的当前账套权限继续控制读取。

`learning_rules` 保存当前版本、状态版本及 `draft/published/retired` 状态；`learning_rule_versions` 保存不可覆写的定义、正例、理由与创建人；`learning_rule_evaluations` 保存反例、评估报告和不可覆写回执。四表 FORCE RLS，worker 不获得原始学习表直接读写授权。规则定义和消费限定同企业、同账套、同期间和指定 source kind。

发布前的 PostgreSQL 防线在数据库内执行：

1. 校验样例来自当前真实冻结凭证，核对来源事实与最终分录；业务样例还绑定原事件 payload、模板、事实版本、部门及申请人。银行样例绑定固定银行来源。所有样例先验证真实性，再判断是否匹配，不能以伪造“不匹配反例”绕过。
2. 重新计算当前有效 OCR 的已知净额/税额，排除已替代原件。规则金额只允许 `gross/net/tax`，两侧均须等于一份含税总额；科目须有效，辅助项按当前客户要求及归属验证。
3. 正反例互斥、不可重复且须有当前真实审核来源；扫描该账套已有审核样例，匹配结果必须与最终已审分录一致。评估报告的 `passed` 与计数必须等于数据库确定性结果。
4. `db_input_fingerprint` 由数据库触发器写入，包含真实规则定义、正例、客户科目版本/状态/辅助要求及该账套审核样例上下文。它与服务的请求指纹分别保存，不信任调用方声明的数据库哈希。
5. 发布重新检查数据库上下文并重新执行确定性评估。失效科目、新样例、冲突处理或伪评估不能通过原生 SQL 直接发布。修订生成下一不可覆写版本并回到待发布；停用立即改变后台策略指纹。

这些校验是发布边界，不构成会计准确率或税务规则覆盖保证。人工修正不会自动污染企业规则，更不会成为跨企业全局训练数据。

## 企业规则 worker 回执

`proposal_jobs` 新增 `result_rule_id/result_rule_version`，外键引用该账套的不可覆写企业规则版本，与既有 `result_template_id/result_template_version` 分开。API 创建及人工重试不能制造企业规则执行回执；后台成功通过独立 worker 能力写入。

`worker_finish_proposal_company_rule` 将租约、原请求人当前授权、事件事实版本、草稿版本、期间、人工干预标记、规则当前已发布版本、条件、实际公式与辅助核算、未关闭异常同时验证，再结束尝试并写入草稿版本回执。规则分录采用与回执在同一写事务内完成，失败整体回滚；它不修改批准状态。

常规 worker 先消费本企业已发布规则，其次使用客户固定模板，无匹配时才进入模型建议。人工改稿、规则发布/修订/停用、事实变更和权限撤销均可使旧任务失效。记录的规则版本提供生成依据，不能作为人工复核或外部过账回执。

## 部署与验证范围

数据库迁移成功不等于真实企业验收完成。正式试点须使用独立数据库、私有附件目录和受限 API/worker 账号，验证跨企业隔离、原生 SQL 权限、批量账套原子回滚、幂等恢复、补件独立核验、有效原件替代、规则显式评估发布与人工复核后导出。测试计数与执行环境记录在最终验证文档，本说明不提前宣称验证结果或承载企业数量。
