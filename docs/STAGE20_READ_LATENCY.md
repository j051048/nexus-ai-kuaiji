# 第二十阶段：首页、助手与事务往返优化

日期：2026-10-15。目标是在现有 Zeabur 首尔 / Supabase 加拿大部署中减少数据库往返与写锁占用，保持企业权限隔离、异常人工处理和会计复核后导出。没有数据库迁移，也没有改变部署地域或提高连接池上限。

## 改动

- PostgreSQL 事务初始化使用 psycopg `ClientCursor` 的 simple query protocol，一次发送 `BEGIN`、固定角色、事务局部 search_path 和参数绑定的身份。继续禁用 pipeline / prepared statements；只允许既有三种受限角色，身份不拼接为 SQL，初始化全部成功后才交给领域代码。只读事务仍为 `REPEATABLE READ READ ONLY`，结束和失败时仍清理身份、回滚并归还连接。API、后台任务、心跳、供应商并发槽及统计写入使用同一初始化方法。
- `firm_role`、企业、账套授权各用一条查询读取当前账号状态、资源及授权，保留原来的权限函数和 403/404 行为。没有跨请求权限缓存；PostgreSQL FORCE RLS 继续生效。
- 已验证登录身份的姓名、邮箱没有变化时，`register_identity` 只读返回，不再争用全局会计写锁。首次开通或资料变化仍在写锁内重新检查停用状态；后续 `/me` 和业务授权独立核验当前账号及权限。
- 首页角色资料不再加载完整业务目录、账套健康及凭证统计，改为一个只读事务、三条领域 SQL。新增 `can_operations` 只用于导航显示，实际入口仍由后台重新授权。
- 首页不再提前请求 `/workbench → /books → /drafts`，费用监控企业列表仅进入该页面时读取。离开会计页取消旧读取，重新进入重新核权；从首页跳转账套只发起一次工作区加载。
- 助手历史读取使用完整实时会话范围谓词，当前事实快照另行核验并复用同一事务刚读取的引用。账套统计、计划回执及数据库时钟批量读取，不再逐条往返。已保存回答、证据引用、资料变化提示和任务执行确认均保留。
- OCR 核对复用本次读取的原件、最新识别与账套上下文；批量获取异常和最新人工复核。重复发票先读取本企业最新成功结果，只对实际匹配事项做可见性和补件替代校验；最新失败不会回退到旧成功结果。持久化核对总是重新收集证据。
- 业务移交的来源、草稿、任务、版本及审计仍原子提交。完整详情移到提交后的新只读事务，并重新验证事项权限与目标账套编辑权限。提交后撤权会拒绝响应；已提交收据保留，恢复权限后的同键重试不重复创建。

## 同场景测量

| 测量 | 修改前 | 修改后 | 范围 |
| --- | ---: | ---: | --- |
| 线上事务初始化 | 761.58 ms | 190.73 ms | 同一受限连接各三次，验证当前角色、只读隔离和回滚清理；不是完整 HTTP 耗时 |
| 助手完整详情 | 195 条 SQL | 86 条 SQL | 单账套、已识别且移交的事项及草稿；完整输出与原实现比较一致 |
| 20 条未执行助手计划 | 35 条 SQL | 5 条 SQL | 批量回执与统一数据库时间，不包含已执行计划的进度展开 |
| OCR 核对，额外 12 个无关事项 | 91 条 SQL | 29 条 SQL | 针对核对实现的对照，使用同一授权实现；findings 和 fingerprint 一致 |
| 移交写锁内读取 | 29 条 SELECT | 17 条 SELECT | 针对移交实现的对照，使用同一授权实现；详情提交后读取，额外执行当前授权检查 |
| 首页角色资料 | 三段完整服务调用 | 一个事务 / 3 条领域 SQL | 100 家企业仍保持固定查询次数；返回的企业和账套数量仍影响传输体积 |

数据库往返实测仍约 191 ms。领域 SQL 数量不包含 RLS 函数内部查询，也不等同于模型生成时间或端到端延迟。

本轮发布前后从同一正式域名、同一客户端及既有虚构资料执行相同浏览器脚本。首页同时登录员工、会计两个账号，计时从点击登录到角色资料、待办和后台摘要全部返回；助手记录读取已有会话详情接口的耗时，不是模型生成耗时。

| 线上浏览器场景 | 修改前 | 修改后 | 耗时下降 |
| --- | ---: | ---: | ---: |
| 员工首页就绪 | 26.224 s | 15.614 s | 40.5% |
| 会计首页就绪 | 28.923 s | 14.142 s | 51.1% |
| 已有助手会话详情 | 44.045 s | 19.414 s | 55.9% |

这是每种场景各一次的功能验收样本，包含登录、网络、并发竞争等影响，不是 p95 或容量基准。助手保留四条来源引用、历史依据变化提示及会计复核提示，390 px 手机布局无横向溢出；两组浏览器均无 JavaScript / HTTP 错误。首页不再发送无关 `/workbench`、`/operations/companies`、账套和凭证预加载。

## 验证与边界

新增回归覆盖授权组合、停用与撤权、跨企业不可见、身份参数转义、初始化失败后连接清理、只读一致快照、全局写锁被占时读取不变身份、最新失败 OCR、补件替代、人工复核依据、移交提交后撤权和幂等恢复。既有会计复核、冻结、导出、并发和队列恢复回归一并执行。

- 独立本机 PostgreSQL 18、迁移 001–082、受限 app/worker 登录：全部 `*postgres.py` 专项 **533 项通过**；另单独执行既有 `test_postgres_integration.py` 的权限、并发、复核/导出、关期与回滚测试通过。
- 后端全量首次运行 **1754 通过、596 跳过、1 失败**，该次未注入 PostgreSQL 测试连接；PostgreSQL 专项另行执行，结果如上，不把跳过项计为通过。唯一失败为原有网关深层登录配置测试，隔离运行同样复现：Python 3.12 的 JSON 实现会接受 1500 层输入，不能依靠 `RecursionError` 作为固定深度限制。本轮补显式 64 层限制，完整网关专项 **96 项通过**，覆盖高递归上限、编码与边界；修后没有重复运行 20 分钟全套。另新增登录快速路径后撤权测试，访问控制专项 **13 项通过**。
- 前端 **291 项单测、15 项浏览器回归通过**；构建（含类型检查）、ESLint、修改文件的 Ruff/格式及 diff 检查通过，保留原有主包体积提示。
- 浏览器首次整合运行 14 过、1 项旧的四身份流程超时，失败快照停在身份连接等待。只将该用例总等待设为 90 秒、切换身份后的标题等待设为 15 秒，保留全部 API、权限、角色和手机断言；随后完整 15 项通过。该用例约 40.4 秒，包含本地夹具创建和冷开发服务，不用作线上性能指标。
- 独立审阅发现并修复“移交提交后仍能读事项、但已失去账套权限时旧收据可能返回”的边界，新增专项测试。另一轮 PostgreSQL 新测试失败是共享测试 helper 缺少 actor，补为受限会计身份后通过，没有放宽数据库要求。

前端依据 Vercel React Best Practices 检查请求瀑布、effect 生命周期和取消逻辑；既有生产部署沿用 Vercel Git 集成，发布前核对目标项目和提交。数据库协议依据 [psycopg ClientCursor 文档](https://www.psycopg.org/psycopg3/docs/advanced/cursors.html#client-side-binding-cursors)，并在实际 Supabase pooler 上做了只读兼容性验证。

性能验证使用明确标记的既有虚构企业，不提交真实财务软件，也不生成新的模型费用。

## 部署地域仍是后续瓶颈

本轮减少往返，不能消除跨洲 RTT。正式扩大试点前应将 API、三个 worker、PostgreSQL 和原件存储放在同地域或低时延网络。优先按实际客户的数据驻留要求确定地域，再选择迁移后端或新建同地域数据库项目。

地域调整需要独立实施：清点 Auth 用户/MFA、数据库角色/RLS/迁移、原件与摘要、队列和未知结果；准备备份及恢复验证；在写入窗口停收并处理在途任务；复制校验后切换连接及原件地址；重新验证隔离、登录、识别、复核和导出。保留旧环境与明确回退步骤，不能直接替换数据库地址后让两边同时接受写入。

本次仍保留现有全局写锁及已审查的企业范围锁规则。后续应继续缩短其他长事务，并将大规模重复发票比对改为经过迁移和权限回归验证的索引投影；当前优化仍会读取本企业最新识别结果。合成样本的响应改善不代表 200–500 家企业吞吐量验收。
