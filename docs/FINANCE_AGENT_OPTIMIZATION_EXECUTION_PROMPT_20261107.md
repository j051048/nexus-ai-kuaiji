# 财务智能体能力补强执行提示词（P0–P2）

> 用途：把本文件整体交给另一个执行型 AI。  
> 它不是审计报告，而是可执行的工程任务书。执行者必须先核对仓库现状，再按 P0 → P1 → P2 连续推进。  
> 本文件中的路径、能力判断和候选数字均为编写时快照；执行时必须重新核对，不得把快照当成当前事实。

---

## 0. 角色与总目标

你是一名资深财务软件工程师、产品架构师和测试负责人，负责在一个已有的多客户会计工作台项目上完成增量补强。

项目当前定位：

- 面向中国大陆、人民币、事务所多客户账套的辅助记账与复核平台；
- 已有员工业务事项、附件、OCR/规则建议、会计制单、独立复核、正式记账、月结、报表、月度包、客户签收；
- 已有应收应付辅助核销、固定资产折旧后端接口、批量作业、人工接手、只读分析助手；
- 产品原则是“AI 只写草稿，会计复核后导出/记账”，不是无人审核的自动记账系统。

本轮目标不是把产品改成用友 BIP，而是补齐四个方向的实际业务内核：

1. **P0 费控与票据可信**：发票验真适配、费用标准、提交前风险拦截、效果度量；
2. **P1 会计与共享作业深度**：AP/AR 子账、固定资产全生命周期、多账套月结编排、可行动助手、共享作业总结；
3. **P2 商旅报账与试点验证**：差旅申请、行程结束后的报销草稿、语音/自然语言入口、真实试点度量。

最终要能回答：

- 哪些能力已经真实可用；
- 哪些只是接口或演示；
- 哪些必须等真实供应商、真实用户或生产授权；
- 每个结论对应哪条测试、哪个候选、哪份证据。

## 1. 开始前必须做的事

### 1.1 读仓库规则与现状

按顺序读取：

1. 仓库根目录及子目录的 `AGENTS.md`；
2. `README.md`；
3. `docs/UX12_CAPABILITIES_AND_PILOT.md`；
4. `docs/IMP_REPAIR_ACCEPTANCE_20261106.md`；
5. `docs/IMP_EXECUTION_STATUS.md`、`docs/IMP_EXECUTION_CHECKPOINT.md`（若存在）；
6. 与本包相关的源码、迁移、测试、前端组件。

不要只读本提示词就开工。

### 1.2 记录基线

在任何修改前记录：

- `git rev-parse HEAD`
- `git status --porcelain`
- 已有未提交修改及归属
- `candidate_fingerprint()` 的 source 文件数/摘要、migration 文件数/摘要
- 当前迁移最大版本（SQLite/PostgreSQL 分开）
- 当前测试命令、环境、数据库版本、浏览器版本

把基线写入独立运行目录，例如：

```text
tmp_test/finance-agent/<run-id>/baseline.json
tmp_test/finance-agent/<run-id>/CHECKPOINT.md
```

### 1.3 先判断“已有能力”还是“缺失能力”

如果代码已经存在：

- 先验证接线、权限、契约、错误路径；
- 不重复造模块；
- 不为了产生 diff 而改正确代码。

如果报告说“缺失”但代码已存在：

- 以代码和运行结果为准；
- 更新文档，不重建。

### 1.4 不要相信旧文档里的候选和数字

旧验收文档可能停留在旧 HEAD、旧候选、旧 HTTP 数据。  
执行时必须重新计算候选、重跑相关测试，不能把旧证据拼到新候选上。

## 2. 不可破坏的边界

以下规则优先级高于“尽快完成”。

### 2.1 授权边界

本轮只允许：

- 修改本任务相关的代码、测试、文档、CI 定义；
- 使用本地隔离 PostgreSQL 16/17、SQLite、虚构企业、测试身份、私有测试对象存储；
- 使用 FakeProvider、本地模拟 OCR/通知/发票查验/语音服务；
- 创建任务专用临时目录和可识别归属的本地资源。

禁止：

- 未授权提交、推送、部署、修改线上配置、执行线上 SQL、重启线上服务；
- 调用真实模型、真实税局查验、真实通知渠道、真实客户数据；
- 创建收费云资源；
- 打印、提交或写入公开报告的密码、令牌、DSN、私钥、真实财务原文；
- `git reset --hard`、`git clean`、整批覆盖文件、删除未知归属目录；
- 改写已应用历史 SQL、迁移 checksum、数据库迁移登记；
- 通过扩大数据库权限、关闭 RLS、关闭复核、删除负向测试、跳过测试来获得通过。

### 2.2 业务不变量

必须保持：

- 企业、事务所、账套、期间隔离；
- 权限由服务端当前有效授权决定，前端显示不构成授权；
- 制单责任绑定待审版本；
- 独立复核政策不降低；
- AI 建议只能写草稿，不能自行决定正式账务；
- 会计复核后才能导出/正式记账；
- 包草稿、发布、通道接受、送达、查看、客户签收分别记录；
- 费用未知不改为零；
- 已发送但结果未知的 attempt 不自动重发；
- 不覆盖人工修改；
- 不补造历史审核、申报、送达、签收记录；
- 不自动申报、不自动缴款、不自动过账到外部 ERP。

### 2.3 工程边界

- 新迁移必须同时覆盖 SQLite 和 PostgreSQL（如涉及）；
- 迁移只前进，不改历史 checksum；
- 所有金额用整数分，禁止浮点；
- 所有时间带时区；
- 所有外部调用有超时、幂等、unknown 状态、失败分类；
- 所有新增权限检查必须在服务端；
- 所有新增写操作必须有审计；
- 不新增“管理员可直接改已记账凭证”的捷径；
- 不新增“无审计解锁”。

## 3. 执行循环

每个工作包都按同一循环：

1. 读当前实现和已有测试；
2. 写一个能复现缺口的失败测试；
3. 实际运行，保存失败证据；
4. 做最小修复；
5. 跑定向回归；
6. 涉及数据库的，跑 SQLite + PG16 + PG17；
7. 涉及 UI 的，跑真实浏览器（桌面 + 手机）；
8. 核对候选指纹；
9. 更新状态台账和验收文档；
10. 继续下一包，不逐包停下询问。

失败必须分类：

- 产品缺陷：写红测、修复、复跑；
- 测试/夹具缺陷：先证明夹具违反现行契约，再修夹具；
- 环境缺失：复用现有脚本建立隔离环境，不整片跳过；
- 外部授权缺失：保留限制，继续独立本地任务；
- 并发修改：保存现场，不覆盖，先做不冲突任务。

禁止：

- 同一个失败命令反复重试而不分析；
- 用 `xfail`、`skip`、零用例、提高阈值、删除断言掩盖失败；
- 把“测试通过”写成“生产可用”；
- 把“已配置”写成“已验证”。

## 4. P0：费控与票据可信

P0 的目标是让“报销审核”从人工翻查，变成“确定性规则 + 可追溯外部查验 + 人工只看风险点”。

---

### P0-1 发票验真适配器

#### 现状判断

当前系统有：

- OCR/XML 解析；
- 发票号码、税号、金额、日期、重复票等确定性检查；
- 明确文案“识别不代表票据已验真”。

当前没有：

- 税局/供应商发票查验接口；
- 验真结果模型；
- 验真失败/不可用/不一致的持久化证据。

#### 必须实现

1. 新增验真领域模型，至少包含：
   - `verification_id`
   - `firm_id/company_id/book_id`
   - `attachment_id`
   - `invoice_key`（销方税号 + 发票号码，或平台定义）
   - `status`：`verified` / `invalid` / `mismatch` / `unavailable` / `unknown`
   - `provider`、`provider_version`
   - `request_fingerprint`、`response_fingerprint`
   - `checked_at`、`reason_code`、`reason_text`
   - `raw_response_sha256`（不存敏感原文）
2. 新增 `InvoiceVerificationProvider` 接口：
   - `verify(invoice_fields, original_bytes?) -> VerificationResult`
   - 显式超时、重试上限、熔断；
   - 不允许把异常吞成 `verified`。
3. 实现 `FakeInvoiceVerificationProvider`：
   - 固定夹具覆盖：一致、票号不存在、金额不一致、销方不一致、超时、返回 unknown；
   - 测试可注入延迟和失败；
   - 不读取金标来“伪造通过”。
4. 持久化：
   - 验真记录 append-only；
   - 与附件、发票字段、事项版本绑定；
   - 同一请求幂等，不同内容同键冲突；
   - 企业隔离；跨企业查询 404。
5. 业务接入：
   - 员工提交/会计复核时显示验真状态；
   - `invalid`/`mismatch` 必须阻断提交或进入强制人工说明；
   - `unavailable`/`unknown` 不得显示“已验真”，不得自动放行；
   - 人工覆盖必须填原因、留审计，不能改写原始验真结果。
6. 配置：
   - 默认关闭真实 provider；
   - 缺少配置时明确“未配置”，不是“验证通过”；
   - 日志不得打印发票原文、税号、密钥。

#### 必须新增的测试

- 验真一致 → `verified`；
- 票号不存在 → `invalid`，提交被阻断；
- 金额/销方不一致 → `mismatch`，进入人工；
- provider 超时 → `unknown`，不自动重试成通过；
- 同键不同内容 → 409；
- 跨企业读取 → 404；
- 未配置 provider → 明确不可用；
- 日志/响应不含密钥和财务原文；
- 重复提交不重复产生验真记录。

#### 完成门槛

- SQLite + PG16 + PG17 通过；
- 前端可见验真状态；
- 负向路径有浏览器证据；
- 明确写出“真实税局接口未验证”，只完成 adapter + fake；
- 不把 fake 结果写成真实查验。

---

### P0-2 费用标准与政策引擎

#### 现状判断

当前没有按城市、职级、差旅类型、住宿/交通限额的费用标准引擎。  
现有“费用限额”是 AI 调用预算，不是报销标准。

#### 必须实现

1. 政策模型：
   - `policy_set`：事务所/企业级，生效期间、版本、状态；
   - `policy_rule`：费用类别、职级、城市档位、差旅类型、期间口径、限额、币种、超限处理（block/warn/require_reason）、所需附件。
2. 版本与生效：
   - 政策版本绑定提交时的版本；
   - 历史事项不因新政策改写；
   - 政策变更有审计、生效时间、停用时间。
3. 评估器：
   - 输入：事项金额、类别、日期、城市、员工职级、住宿夜数、交通类型、附件；
   - 输出：`pass`/`warn`/`block`、规则 ID、政策版本、计算口径、剩余额度；
   - 纯确定性，不用模型；
   - 缺职级/城市/标准时明确 `incomplete`，不能默认通过。
4. 管理界面：
   - 管理员可创建/复制/停用政策；
   - 预览某笔事项会命中哪些规则；
   - 不提供“一键关闭全部校验”的入口。
5. 提交接入：
   - 员工提交前显示命中规则；
   - `block` 服务端拒绝；
   - `warn` 需填写说明；
   - 会计复核看到政策版本和规则。
6. 种子数据：
   - 只放虚构示例；
   - 明确“示例标准，需企业确认”，不得冒充法定标准。

#### 必须新增的测试

- 城市档位/职级/类别边界；
- 超限 block；
- 临界值；
- 缺职级/城市 → incomplete；
- 历史政策版本不被新政策覆盖；
- 跨企业政策不可见；
- 客户端伪造政策版本被服务端拒绝；
- 政策停用后新提交不能用旧版本。

#### 完成门槛

- 政策 CRUD + 评估 + 提交拦截；
- SQLite/PG16/PG17；
- 浏览器：管理员建政策、员工被阻断、会计看到规则；
- 真实企业标准未确认，文档明确待业务确认。

### P0-3 提交前风险分级与自动拦截

#### 现状判断

已有附件完整性、重复票、税号、金额、日期等检查，但：

- 不是所有风险都在提交前强制阻断；
- 没有统一风险分级；
- 没有“员工先改，再提交”的闭环；
- 期间/账套准备检查与费用校验未统一。

#### 必须实现

1. 统一风险结果：
   - `risk_id`、`severity`（block/warn/info）、`category`、`message`、`field`、`source`、`rule_version`；
   - 风险结果绑定事项版本。
2. 服务端提交前聚合：
   - 票据完整性；
   - 发票验真；
   - 费用标准；
   - 重复票；
   - 金额/日期/税号；
   - 期间/账套开放；
   - 附件缺失/损坏；
   - 收款方/交易对方异常。
3. 行为：
   - `block` 服务端拒绝，返回可定位字段；
   - `warn` 允许提交但必须说明，会计看到；
   - `info` 仅提示；
   - 前端不能绕过，直接 API 也必须拒绝。
4. 员工修正闭环：
   - 显示“哪一项、为什么、怎么改”；
   - 修改后重新评估；
   - 不要求员工理解会计科目。
5. 会计侧：
   - 风险清单可筛选；
   - 只看风险点，不重复看全部字段；
   - 可退回补件，保留版本。
6. 期间预检：
   - 提交前检查企业/期间是否有开放账套；
   - 无开放账套时明确“等待会计开账”，不要等到财务交接才阻断。

#### 必须新增的测试

- block 风险服务端拒绝；
- warn 需说明；
- 修改字段后风险消失；
- 直接 API 绕过前端仍被拒绝；
- 无开放账套阻止提交；
- 撤权/过期版本不缓存旧结果；
- 风险结果绑定事项版本。

#### 完成门槛

- 员工桌面/手机真实浏览器；
- 会计风险清单；
- SQLite/PG16/PG17；
- 不能把“前端提示”当服务端拦截。

### P0-4 费控效果度量

#### 必须实现

1. 事件：
   - 提交、首次通过、退回、补件、重提、审核开始/结束、超时；
   - 固定 `submission_id` 和 `policy_version`；
   - 不采集无关用户行为。
2. 指标：
   - 首次通过率；
   - 打回率；
   - 平均补件次数；
   - 提交到审核完成时长；
   - 风险命中率；
   - 人工修改率。
3. 口径：
   - 分母固定；
   - 缺失/unknown 单列；
   - 不用 0 代替未知；
   - 不把重复提交稀释分母。
4. 展示：
   - 事务所/企业/期间；
   - 不排名个人；
   - 可导出 CSV。
5. 样本不足：
   - 显示“样本不足”，不生成漂亮但无意义的百分比。

#### 完成门槛

- 指标 SQL/服务/页面；
- 固定分母测试；
- 空样本不补零；
- 真实效果标注 pending。

## 5. P1：会计与共享作业深度

---

### P1-1 应收/应付子账

#### 现状判断

已有：

- 应收/应付科目；
- 银行流水辅助核销；
- 历史迁移的未结往来分配；
- 部分发票计提。

没有：

- 完整客户/供应商往来主数据；
- 账龄；
- 付款计划；
- 对账单；
- 催收；
- 坏账/核销；
- 预收/预付。

#### 必须实现

1. 往来对象：
   - 复用现有企业/交易对方数据，不重复建一套；
   - 客户/供应商标识、税号、联系人可选；
   - 企业隔离。

   - 来源凭证、金额、已核销、未结、到期日、账龄桶；

   - 支持预收/预付；
   - 不允许超额核销；

3. 账龄：
   - 0–30/31–60/61–90/90+ 可配置；

4. 付款计划：
   - 到期提醒；
   - 不自动付款；
   - 逾期只读提示。
5. 对账单：
   - 生成客户/供应商对账单；
   - 版本化、可下载；
   - 不自动发送。
6. 核销：
   - 银行流水、收款/付款凭证、未结项三方绑定；
   - 金额守恒；
   - 跨企业拒绝；
   - 已关闭期间拒绝；
   - 重复核销拒绝。

#### 必须测试

- 部分核销、超额、重复；
- 账龄边界；
- 总账与子账勾稽；
- 跨企业；
- 关闭期间；
- 反核销审计；
- 并发核销；
- 迁移旧数据不丢。

#### 完成门槛

- SQLite/PG16/PG17；
- 浏览器：创建未结项、部分核销、账龄、对账单；
- 不自动付款、不自动催收。

### P1-2 固定资产全生命周期

#### 现状判断

### P1-4 会计助手：从解释到可行动

- 不自动写。

#### 必须实现

1. 输出必须包含：

   - 固定开发集/验收集；
   - 验收集不参与选优；
   - 固定分母；
   - 关键退步否决；
   - 记录人工修改率、调用次数、耗时、费用 unknown。
5. UI：
   - 打开证据、原记录、办理入口；
   - 不写业务。

#### 完成门槛

- 离线确定性回放；
- 真实业务查询契约；
- 不宣称真实模型准确率。

## 10. 停止条件

遇到以下情况，记录并继续其他独立包，不要停住全部工作：

- 真实税局/发票供应商未授权；
- 真实模型/通知未授权；
- 真机/微信/iOS 不可用；
- 远端 CI 不可用；
- 生产部署未授权；
- 并发任务占用共享文件。

只有以下情况才暂停并说明：

- 数据库迁移会破坏历史数据；
- 权限/复核/隔离无法在不降低门槛的情况下实现；
- 同一阻塞连续 3 轮无进展；
- 需要用户做产品/合规决策（例如是否允许单人复核、是否接受外部税局接口成本）。

## 11. 最终判定口径

不要把以下内容写成“完成”：

- 只有接口，没有 UI；
- 只有 UI，没有服务端拦截；
- 只有 SQLite，没有 PG；
- 只有 mock，没有真实链路；
- 只有 fake provider，没有真实供应商；
- 只有本地容量，没有生产容量；
- 只有配置，没有送达/查验结果；
- 只有平均分，没有关键退步否决；
- 只有“已实现”，没有负向测试。

可以写成“完成”的：

- 本地实现 + 定向测试 + PG16/17 + 浏览器 + 负向路径 + 证据路径 + 候选指纹；
- 外部依赖明确标注 pending；
- 失败路径明确、可恢复、不自动重发；
- 权限/复核/隔离未被降低。
