# 衡账：综合审计后的改良执行计划

日期：2026-10-18。用途：交给其他 AI／工程团队逐批执行。本文是规划，不表示代码已完成或生产已验收。

## 0. 执行基线与目标

- 审计基线：本机 HEAD `f7bd7b12`；PostgreSQL 迁移已到 `101`。执行者必须重新核对当时主干、未提交改动和迁移状态，不能沿用旧报告中的版本假设。
- 结合材料：本轮 Gemini 报告、当前代码、此前代码审计，以及工作区已有总账规划。已有规划文件保留；本文明确纠正的技术方案不要再照旧稿执行。
- 首批仍为 **2–3 家真实企业、人民币、会计复核后导出**；不把其他草案里的“6 家、26 周”当作已经确认的范围或工期。
- 当前产品具有受控的采集、识别、草稿、审核、交付和事务所运营基础，尚不能把参考余额、月度简报或人工回执称为完整正式总账。
- 产品主线：**可靠的会计作业平台 → 可验证的正式账本 → 高效的人机协作 → 逐级扩大客户量**。
- P0 分两类：现有生产流程的正确性／恢复风险必须先处理；正式总账相关 P0 是替代现有财务软件前的必备条件，不表示旧辅助工作流必须立即停用。
- 本轮仅生成计划。代码开发、生产迁移、重启、数据外发和正式账本切换不是同一项授权；按用户当时授权及 AGENTS.md 执行。

## 1. 对 Gemini 建议的取舍

| 建议 | 结论与执行口径 |
|---|---|
| 总账、账簿、报表成为主线 | 采纳。新增确定性账务内核，复用现有证据、授权、队列和复核流程。 |
| 完善真实科目、辅助核算和结转 | 采纳，但按准则和生效期间版本化。已有 Catalog 配置能力，不能再造平行配置系统。 |
| 云端／本地 AI 统一接入 | 采纳。现有 provider 已支持 `json_schema` 和 `json_object`，真正补端点授权、能力描述及兼容性验证。 |
| 月结引导、同屏复核、角色导航 | 采纳。沿用现有工作流组件，不把“必须六步／必须十二页”作为验收标准。 |
| 自动沉淀企业规则 | 采纳为候选规则发现、评测、批准和版本化发布；多次相同修正不直接激活规则。 |
| 给 drafts 增加 posted 就形成总账 | 不采纳。草稿审批、正式记账、外部交付是三条独立状态轴。 |
| 关账前重排凭证断号 | 不采纳对已记账编号的重排。采用事务内发号和唯一约束，保证同类正式凭证连续编号。 |
| 统一硬编码 4103／6001／6602 等科目 | 不采纳。小企业与企业准则不能混用；纳税人身份也不等于会计准则选择。 |
| 简单对方科目／摘要推断现金流，或用间接法简报替代正式现金流量表 | 不采纳。需现金范围、内部划转排除、混合分录分配、未分类处理及正式映射。 |
| 本地模型可放开所有内网地址，失败后自动转云端 | 不采纳。端点明确批准；每次发送执行企业数据政策，禁止仅本地策略自动出域。 |
| 多个 JSON 取最后一个合法对象、修复字段后继续入账 | 不采纳。只接受唯一、完整、无歧义结果；有限外围包裹兼容不能修改语义。 |
| 强 RLS 等于物理隔离，哈希等于不可篡改 | 不采纳。RLS 是逻辑行级防线；需受限身份、状态约束、审计权限及独立恢复验证。 |
| 四周全部完成、98%解析率、70–80%规则覆盖、每户五分钟 | 不作为承诺。先建立样本、业务口径、实际人工时间和性能基线，再确定阶段指标。 |

会计依据：不同准则科目不能混用，例如小企业准则附录的本年利润、主营业务收入、管理费用为 3103、5001、5602。[财政部科目及报表附录](https://kjs.mof.gov.cn/zhengcefabu/201111/P020111118325852734144.pdf)

正式记账的不可逆性、编号、审签、账簿和结账应按适用规范设计。自动审核可以在明确授权、可追溯规则下另行规划，但本项目本阶段保留用户要求的会计复核。[会计软件基本功能和服务规范](https://www.mof.gov.cn/jrttts/202408/P020240809318551591785.pdf)

## 3. B01：先修已确认的正确性与恢复风险

### B01.1 简报金额与来源口径

证据：`nexus_backend/app/monthly/briefing.py:105` 计算有符号净流量，却在第 120 行使用仅允许非负值的金额格式化函数；银行来源汇总未排除已隔离重复副本，费用排名使用绝对值。

执行：

- 区分非负交易金额、有符号余额和净变动；不要把原本只允许正数的交易校验一律放宽。
- 简报和关期共享“有效来源”的明确查询口径；正常余额方向、费用冲回和辅助维度汇总一致。
- 保留“参考数据”的产品标识，不能因修复简报就改称正式财务报表。

验收：净流出月份、缴税、退款、费用冲回、正常贷方应付余额、父级与辅助明细同时存在、重复来源隔离后，金额正确且接口不报 500。

### B01.2 完整原件备份与恢复

证据：`scripts/backup_accounting.py:71`、`:186`、`:361` 的枚举漏了 `material_attachments`、`invoice_import_batches` 对应原件。

执行：

- 明确数据库、原件、身份系统、角色映射、配置和密钥恢复的责任及依赖；不能把仅 accounting schema 的备份称为整个系统备份。
- 区分灾难恢复包与企业资料导出包；共享用户、事务所权限等使单企业恢复需要专门设计。

验收：全部附件类型恢复到隔离环境并逐项下载、验哈希、验权限；故意遗漏或改动一件原件必须阻断完整性验收。恢复后的 worker 默认禁止自动外发，先处理在途任务及结果未知状态。

### B01.3 审核边界与数据库防绕过

执行：

- 先编写 PostgreSQL 受限身份的负向测试，覆盖关键状态直接写入、越企业写入、不平衡审核、关闭期间、过期事实及审核后修改。

## 4. B02：核算契约、长期账套和正式期初

主要复用：`nexus_backend/app/ledgers/`、`nexus_backend/app/accounting/catalog.py` 及配套模型／路由、`nexus_backend/app/legacy_migration/`、`nexus_backend/app/monthly/`、现有主数据和账套权限。新模块命名先检索，避免与现有 ledger 映射职责混淆。

### 必须先确定的设计

1. **首批准则与行业范围**：根据试点实际选择一个先验收，建议优先低复杂度服务企业；不能仅根据“小规模纳税人”自动选择小企业准则。两套准则的模型可兼容，未经验证的模板不开放使用。
2. **账本归属**：每个长期账套及切换期间明确外部正式账本、内部影子核对或内部正式账本；一个期间不能同时有两个互不勾稽的权威账本。
3. **长期配置**：科目稳定 ID、父子层级、末级记账限制、正常方向、辅助要求、历史版本和生效期。科目编码只是标识之一；更名、停用不改历史凭证含义。
4. **金额契约**：人民币金额整数分；数量、单价、税率使用明确精度十进制；红字、方向、零金额、余额符号和舍入尾差均有样本，不随意引入 float。
5. **正式期初**：年初、启用期期初、本年累计、辅助余额及未结事项有一致校验；试算平衡只是必要条件，还需总分及辅助勾稽。
6. **历史迁移边界**：历史资料归档与正式期初启用分开。保留旧 book／draft／source ID 和权限关系；不能按企业直接合并旧账套，不能把 exported 自动回填为 posted。
7. **政策版本**：准则、报表、税务和结转政策都有适用期间。新准则发布不等于立即对全部历史账期替换模板。

会计金标准样本至少覆盖：期初／年中启用、销售与采购、报销、进销项税、退款、跨期收付、手续费、预收预付、折旧或摊销、红字与更正、期末结转、跨年。每例由会计负责人给出期望分录、余额和报表影响；开发 AI 不能自己生成答案后只验证自己。

验收：期初与科目／辅助逐分一致；历史不重复计入；跨月仍使用稳定配置；旧期间查询和现有导出不变；修改当前模板不会改写已冻结历史。期初启用前保留可修订草稿，启用后使用有审计的更正机制。

## 5. B03：正式凭证、原子记账及账簿

建议新增独立账务内核，数据职责包含正式凭证及分录、记账命令／回执、编号范围、证据关联和冲销调整关系。具体表名由设计评审确定，不机械照搬草稿表。

### B03.1 状态与原子命令

- 草稿审核、正式记账、外部交付分别建模。现有 approved／exported 和回执保持兼容。
- 记账事务同时检查企业／账套／期间、科目及辅助、事实／审核版本、借贷平衡、当前权限、审核政策、幂等键与凭证编号。
- 连续编号按明确账套、期间和凭证类别范围在事务内分配；不能用可能跳号的普通 sequence 后再批量改号。失败回滚、并发和重试验证同一作用域的编号与结果。
- 已记账凭证只允许关联冲销／调整，保留原分录、编号、证据与操作者。关期后更正走受控期间策略，不覆盖旧快照。
- 记账、业务回执及待发送事件在同一事务保存；通知失败不回滚或重复记账。

### B03.2 不依赖银行流水的会计处理

- 保留现有来源校验；新增手工转账、计提、折旧、摊销等凭证入口，不伪造银行流水凑来源。
- 凭证与原始证据支持受约束的多对多关联；借贷平衡与来源金额勾稽是不同规则。
- 适配合并／拆分、部分支付、手续费、扣缴等实际场景；不得以“自动补一行差额”掩盖错误。
- AI 与人工草稿都通过同一审核及记账命令；AI 不直接操作正式分录表。

### B03.3 统一账簿和余额读模型

- 有效期初＋正式分录生成现金／银行日记账、科目明细、辅助明细、总账与科目余额表。
- 余额缓存／期间汇总可随时重建，不能成为唯一财务事实；汇总查询避免父级与明细重复计数。
- 查询在数据库执行授权过滤和分页；科目／辅助下钻至正式凭证，再到原件。
- 审计为受限追加记录，覆盖命令、事实版本及结果；哈希校验、数据库权限与独立备份共同支撑可验证性，不能宣称仅哈希即可防数据库管理员改动。

验收：重复请求一次记账；并发记账无重复号且符合连续编号政策；写入与锁期／撤权竞争结果一致；崩溃恢复不重复；不平衡、无效科目、错误辅助、过期审核均拒绝；冲销与调整可追溯；缓存删除重算仍逐分一致；跨企业 ID 猜测、列表及附件访问失败。

## 6. B04：必要子账、月结和正式报表

### B04.1 先覆盖试点真实业务

- 复用 `app/settlements/` 的确定性分摊，扩展长期账套的跨期未结事项、预收预付、部分／合并收付、手续费和账龄；子账与总账勾稽。
- 完成 `app/revisions/` 的调整建议到新凭证、审核、记账和报表追踪闭环。
- 固定资产、工资、存货不一开始全部做成 ERP。试点有相关业务时，必须具备可审核的台账／导入和凭证生成方案；不能把定时凭证模板称为完整资产或存货系统。
- 税务先做基础台账、差异清单和人工确认的申报准备；自动申报、自动缴款另行评审。应交税费净变动不等于应纳税额。

### B04.2 结转与月结任务

- 使用统一期间任务：资料与异常检查 → 业务凭证完成 → 必要计提／结转 → 试算及子账核对 → 报表复核 → 锁期归档。
- 结转按准则、损益分类、政策与有效期配置，不硬编码 4103 或科目数字前缀；月度结转和年度结转分别处理。
- 自动生成的结转草稿仍须会计复核。生成基于确定快照并幂等；新增业务或修订使旧预检／结转依据过期，要求明确重新处理。
- 利润表按业务发生额计算，正确处理结转抵销，不能月结后收入费用全部变零。
- 锁期保留来源、未决项、余额、报表及政策版本快照。重开须有权限和理由，保留旧快照；不能借重开修改已记账凭证。
- 外部正式账本模式保留交付／回执核验，内部正式模式走内部账本闭环；影子模式仍须与外部权威账本核对。

### B04.3 报表引擎及发布

- 按准则及适用期间提供报表模板、映射和比较列；资产负债表不统一写成“月初／期末”。
- 利润表、资产负债表、现金流量表及适用的权益变动表、附注分步验收；“三表页面存在”不能代表所有准则的完整报告包。
- 现金流明确现金及等价物范围，排除内部划转，分离非现金交易，处理多借多贷和分类未决项。分类建议可来自 AI，正式归类与金额由受控规则／人工和确定性程序完成。
- 直接法现金流主表与适用的补充调节分别实现，不能拿管理简报替代正式表。[现金流量表准则](https://cwfwpt.ggj.gov.cn/zcfg/qykjzd/202306/P020230620618855468299.pdf)
- 每个报表数字可下钻；保存输入快照、映射版本、计算版本、复核与发布时间。客户领导只看已发布版本，修改后形成新版本。
- PDF／表格导出保留单位、期间、金额单位、版本及状态；印章图片不宣称为合法电子签名。电子归档保留原件、元数据和真实性状态。

验收：连续两个月及跨年样本；损益结转前后经营发生额口径正确；资产负债平衡、利润及权益衔接、现金净变动与现金余额变动相符；总账／明细／辅助／子账逐分勾稽；未分类现金流及未完成关键任务阻止正式发布／结账；发布版本可追溯、可重算。

## 7. B05：让 AI 更有用且边界明确

复用 `app/intelligence/provider.py`、`app/intelligence/cache.py`、`app/assistant/`、`app/jobs/` 和跨进程限流。企业 AI 默认开启、管理员暂停／恢复和限额的现有产品语义保持；新增数据政策不能偷偷改变为全企业默认关闭。

### B05.1 数据提取及企业规则

- 原生结构化电子凭证优先解析，图片再 OCR；提取、真实性查验与会计判断分开显示。XML 可解析不等于发票已验真。
- 规则／历史审核样例优先，模型处理未覆盖项；缓存保持企业、原件、模型、提示词、解析器和事实版本范围。
- 多次修正形成候选规则，显示命中、反例、误命中和影响范围；经批准发布企业版本，支持停用回退，不自动传播到其他企业或改历史。
- 会计解释绑定证据；老板解读只使用有权访问的已发布报表快照，缺失信息明确显示。

### B05.2 模型能力和地址

- 复用场景配置，增加可信端点目录及能力配置：结构化输出、视觉、模型版本、上下文、超时、并发及费用。
- 运维批准精确协议／主机／端口；本地 HTTP 是明确例外，不开放整个 RFC1918。校验覆盖实际连接地址、IPv6、DNS 变化、重定向和元数据地址。
- 企业管理者只能选择已批准端点；供应商密钥和调用地址不能通过员工附件或聊天内容改变。
- 兼容性探测使用合成数据；已支持 json_object 的场景不重复建设。

### B05.3 解析、重试与外发政策

- 每个模型选择明确输出模式；只允许完整单一代码围栏或明确完整思考前缀等无歧义外包裹处理，不从多段内容挑 JSON，不静默修复金额／科目／语法。
- 保留拒绝、截断、工具调用、重复键、超长响应及 schema 校验；失败不得形成可审核的有效建议。
- 区分未发送、明确拒绝、发送后未知。未知结果不盲目重试或换供应商；业务幂等不代表推理调用或计费幂等。
- 每次新发送／降级／备用模型都记录尝试、费用和政策版本，并重新验证企业权限、暂停、预算、事实版本与取消状态。
- 建立最小字段上下文、企业外发政策、必要的代号映射；覆盖图片、OCR 文本和日志。本地模型也不能读取越权事实。
- 仅本地政策不得云回退；公开 HTTPS 地址或正则脱敏都不能单独证明商业资料安全。

验收：恶意票据指令、相互冲突的两个 JSON、重复金额键、截断输出、非法科目、暂停后排队任务、仅本地策略、发送后断网、费用未知、跨企业缓存命中全部有测试。分别统计结构解析、字段正确、分录被接受及异常漏检，不能只报一个模型准确率。

| 部门审批人 | 待审批、范围内事项及缺件原因 | 其他部门和全所企业 |

2. 科目＋金额＋原件＋依据同屏；企业、账套、期间、状态始终可见。助手作为上下文侧栏和动作预览，不代替记账表格。

5. 月度批量任务轮询能取消／卸载，组织列表真正分页；交接计划与确认绑定版本摘要，不能确认后重新计算出另一批任务而无提示。
6. 手机优先优化员工上传、补件及审批；桌面优化密集复核和账簿。键盘操作、焦点、字号、对比度及非颜色状态提示统一。
7. 统一空／加载／错误／过期状态。不要用无限 spinner 隐藏权限拒绝或未知结果；会话续期与安全退出单独设计，不直接长存敏感 token 解决重登。
8. 收敛页面职责后再拆大组件，优先路由壳、查询、领域表单和证据面板；不是按固定行数机械切文件。

## 9. B07：部署、恢复和性能

### B07.1 先观测，再消除等待

- 分开量测页面可操作时间、认证、数据库连接／锁等待、SQL、对象存储、任务排队、模型首个有效响应和完整结果时间；记录同数据同并发的 p50／p95。
- `app/uploads.py` 的远程读对象、哈希和解析移出数据库写事务；提交时重新校验授权、版本、期间及对象，不能简单换小锁后保留长网络等待。
- 首页投影先限定授权范围、查询条件和分页，再检查脏数据；维护增量刷新，防旧脏企业长期饥饿。不得通过长期缓存撤销前的权限提速。
- `app/unified_worker.py:62` 的同步顺序执行会被慢任务阻塞；保留独立助手容量或有界执行池，维护任务也有容量。跨进程供应商总限额、企业公平、租约和 fencing 不变。
- `src/api.ts` 增加有界等待及取消；读操作重试与写操作结果未知分开处理；页面先显示已到达的必要数据。
- `services/api_gateway/main.py` 有 4 MiB 响应限制；附件不仅要能上传，还要能授权预览／下载。选择受控流式下载或短时签名链接，并明确签名链接有效期内的撤权窗口；要求立即撤权的内容走在线授权代理。
- 锁的拆分必须基于等待数据和固定取锁顺序；现有全局预算、跨企业事务、审计与系统任务分别分析，不能全局替换 transaction 参数。

性能验收包含批量 OCR 同时运行、冷启动、权限撤销和大附件。目标基于基线确定；不拿 SQLite 合成查询或单次本机响应证明 500 家企业容量。

### B07.2 云部署与私有部署分别交付

云版本保留 Vercel＋持久 API／worker＋PostgreSQL／私有原件的现有路径。私有版本提供反向代理、API、必要 worker、维护进程、数据库、私有存储、OCR、可选模型及**生产身份服务**。

- 短期优先评估与现有认证兼容的自托管身份；若改 OIDC，作为独立适配任务。不能把演示 local 身份解除限制当作私有生产认证。
- 对完全离线和“业务数据不发模型云”分别描述。镜像、依赖、模型权重、字体、遥测、认证和更新全部列入外部依赖清单。
- 小型与标准运行配置使用实际受支持的启动角色，包含维护进程；依赖／镜像固定可追溯版本。硬件按模型和负载实测，不统一承诺某 GPU 可支持任意人数。
- 健康检查区分进程存活和依赖就绪，不用付费模型调用探活；记录积压、最老任务、租约、错误率、备份失败和费用异常，明确负责人。
- 将 B01 的恢复修复固化为定期演练流程；数据库与原件恢复点、身份恢复和在途任务处理一起验收，RPO／RTO 由实际演练与业务需求确定。
- 升级采用扩展、迁移、收缩；新旧应用／模式及混合 worker 状态验证。不以 incremental 标记宣称无停机和随时回滚。

验收：空环境按文档安装；完整登录、上传、识别、复核、记账／导出和恢复通过；离线产品须在阻断公网情况下实测。滚动重启、崩溃、旧版本回退与未知任务不得造成重复账务或未经批准的数据外发。

## 10. B08：试点验收与切换条件

1. 用 2–3 家企业实际适用的准则和业务类型建立脱敏／授权样本；至少两个完整连续账期双轨核对，另补年中启用和跨年回归。不能用合成测试冒充真实账期验证。
2. 新旧系统按科目、辅助、期间、未结事项和报表逐项核对；应一致的金额逐分一致，差异不能靠四舍五入容差或临时配平掩盖。
3. 证明企业／部门／本人权限、撤权、管理员操作、企业暂停、跨企业批量任务和恢复后权限均正确。
4. 验证会计复核后导出仍可用，内部正式记账也经过同一复核边界。人工上传回执与厂商真实记账回执区分，未知结果保留待处理。
5. 抽取正常、异常、补件、冲销和关期样本，从原件到凭证到报表再到归档全程可追溯。
6. 完成数据库＋原件＋身份恢复，并实测批量任务下首页／助手性能。未达到本地部署要求的版本明确标为仅支持云部署，不宣称离线可用。
7. 会计负责人确认核算范围及未覆盖事项。正式切换另行提出具体企业、期间、备份、停止旧账操作的边界与恢复方案，请用户确认后执行。

切换前外部财务软件仍是既定正式账本，内部为影子核对。切换后保留旧证据及回执；不得因“旧库只是模拟数据”而推定后续真实账套也可删除。

## 11. 暂缓、降级和可删除项

### P2：有证据后再投入

- 自动税务申报／缴款、资金支付、任意工具型 Agent；先保留人工确认和确定性执行。
- 同时适配全部金蝶／用友产品。T+ 先确定实际版本、授权和测试账套，再完成一次真实提交、查询、差异及未知结果闭环。
- 制造成本、复杂存货、合并报表、多币种和集团管理；试点不涉及则不为“完整”一次铺开，涉及则纳入该客户上线门槛。
- 自训专用模型、向量图专用存储、微服务拆分；先度量规则命中、真实错误和模块瓶颈。
- 自动审核／自动记账扩大授权范围：先建立规则版本、误放评测、撤回／暂停及可追溯机制，另行批准；当前阶段不取消会计复核。

### 降级显示而非立即删除

- prompt 版本、哈希、队列租约、schema 等工程字段移到诊断抽屉，审计证据继续保留。
- 在内部正式账本验收且相关企业已切换后，参考余额导入才可从主入口降级；外部账本模式仍需保留。
- 重复运营入口、旧平台未启用模块先做调用／路由／数据依赖清单，再删除确认无用的代码。不可只因代码多、文件大而删权限、审计或历史迁移。

## 12. 成功指标：证明一人多企业，而非只证明模型能回答

| 维度 | 记录方式和门槛 |
|---|---|
| 核算正确 | 金标准、账簿与报表勾稽全部通过；试点无未解释余额差异 |
| 权限与重复入账 | 负向／并发测试中的越权成功和重复记账为零；这是测试门槛，不是零风险承诺 |
| AI 质量 | 分开记录提取正确、建议接受、重大修正、异常漏检及人工撤销；按企业／业务类型分层 |
| 人工效率 | 每企业每月总人工分钟，拆分催资料、整理、复核、异常、申报、沟通与返工；浏览器活跃时间不等于总工时 |
| 客户体验 | 首次提交成功、退回原因可理解、补件周期、报表按时交付；观察小白实际操作 |
| 运行性能 | 页面可操作、助手排队／响应、任务积压的 p50／p95，附地区、数据量、并发和模型 |
| 成本与恢复 | 每户总成本含模型、OCR、基础设施和人工；备份完整性、实测恢复时间与数据损失窗口 |

容量计算：可承接企业数 ≈ 月度有效人工分钟 ÷ 单户全流程人工分钟，并预留峰值和异常余量。例如按每月 120 小时有效作业时间估算，200 户平均每户 36 分钟，500 户只有 14.4 分钟；这只是容量算术，不是本产品当前效率。缩短聊天响应不能单独兑现该目标。

先验证 2–3 户，再逐级扩大并观察月末峰值、企业分布和异常负荷。扩大前需明确一人无法同时担任独立复核角色时的事务所复核资源安排。

## 13. 给执行 AI 的工作协议

1. 读取 AGENTS.md、当前代码、最新 Git 状态与本计划；保留用户及其他 AI 的未提交工作。只执行指定批次，未经委派不扩展范围。
2. 开始前说明复现证据、复用模块、契约变化和小提交顺序。核算政策不能自行猜测；用样本和待确认项显式呈现。
3. 迁移编号在执行时分配；不修改已应用迁移，不预占固定 102–106，也不批量设置兼容标记绕过启动检查。
4. 优先模块化单体；公共规则集中但保留必要的数据库防绕过。不要同时重写鉴权、队列、UI 和账务内核。
5. 任何批次都保持企业隔离、撤权及时生效、证据历史和会计复核后导出。不能用放宽权限、自动配平、取消未知状态换取通过率。
6. 使用适当的单元、HTTP、真实受限 PostgreSQL 及关键 UI 测试；核算改动必须覆盖失败、并发、重试、锁期与旧数据。未执行的测试明确标为未验证。
7. 测试账号／资料明确标为虚构；默认本机或隔离环境，不发送邮件，不使用真实客户数据调用供应商。秘密不写入源码、计划、日志或聊天。
8. 每批提交交付说明：改动文件、数据库影响、实际测试命令及结果、兼容／回退边界、未解决问题和下一批依赖。代码完成不自动代表上线验收完成。
