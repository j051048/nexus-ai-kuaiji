# 企业业务录入与会计处理规划

目标是让企业员工按模板提交日常事项，由主管确认业务、企业财务核对资料，会计集中复核异常与凭证。企业业务事实、内部审批、会计处理各有独立记录，逐步减少重复填表和跨部门补资料。

## 当前能力与建设边界

第二阶段已建立真实身份及事务所、客户企业、部门、企业成员、账套授权的数据库与 API 骨架；`firms → firm_clients → companies` 表达服务关系，`departments / company_memberships` 表达企业组织，`books / book_access` 表达账套范围。现有导入、建议、人工审核、导出流程继续使用独立账套权限。

2026-10-11 第三阶段已实现三个员工表单模板、私有附件、明确部门审批授权、企业财务核验及移交会计草稿，详见 [试点操作](STAGE3_PILOT.md)。企业角色为 `owner/admin/finance/employee`，部门归属不自动授予审批，审批职责来自 `department_approvers`。结构化 OCR、真实模型建议、支付回执同步、撤回/作废与更多行业模块仍待后续建设。

## 统一事项与可扩展模板

所有事项共用稳定 envelope，行业字段放在版本化模板 payload 中。

| 内容 | 关键字段与约束 |
| --- | --- |
| 身份与范围 | `event_id/company_id/department_id/applicant_id`；服务端从身份确定申请人，部门必须属于该企业 |
| 模板与版本 | `template_id/template_version/payload_version`；提交时冻结模板、字段与审批配置快照 |
| 业务事实 | 发生日期、事项类型、说明、交易对方、项目 / 合同标识；日期与会计期间分别保存 |
| 金额 | 币种、含税 / 未税 / 税额原始字段、明细与合计；人民币 MVP 使用十进制字符串与整数分校验 |
| 证据 | 附件 ID / SHA-256、原件位置、字段证据坐标或文本区间、人工修正记录；不能只保存模型摘要 |
| 收付款 | 待收 / 待付 / 部分完成 / 完成状态、流水关联与提供方回执；内部审批通过不代表已付款 |
| 追踪 | 来源渠道、外部 ID、幂等键、提交版本、操作人、时间、关联账套；不允许客户端自由指定权限范围 |

模板包含字段 schema、界面布局、必填证据、校验、审批路由与会计映射候选。通用模板可由企业扩展，但发布须审核、版本化，已提交事项继续引用原版本。行业会计制度、科目与确认时点由会计专家配置；新企业不能直接沿用演示科目或另一个客户的处理规则。

首批最多三个模板：**员工报销、采购 / 费用支出、日常收支事项**。销售订单、工资、库存、固定资产、工程项目以后逐模块接入。制造成本、库存计价和项目成本分摊需要独立业务模型、余额与核算流程，增加几项表单字段不能代替这些模块。多币种也需汇率来源与折算规则，MVP 先限定人民币。

## 目标权限矩阵

以下为业务录入阶段的目标权限；本人、部门、企业及已移交账套范围已实现，模板发布治理、付款回执及后台模型仍属于后续能力。

| 身份 | 事项可见范围 | 可执行操作 | 账务边界 |
| --- | --- | --- | --- |
| 企业员工 | 本人事项及必要回执 | 草拟、提交、补证；退回后修订 | 不读取账本，不审批本人申请 |
| 部门审批人 | 被明确授权部门 | 确认业务必要性、退回补充 | 跨部门不可见，不代替会计复核 |
| 企业财务 | 被授权企业内跨部门 | 核票、匹配收付款、移交会计 | 凭证操作仍需具体账套角色 |
| 企业管理人 | 企业组织与授权范围 | 管理成员、模板与审批配置 | 管理身份不自动成为审批节点 |
| 事务所会计 | 服务关系有效且获授权的账套 | 生成建议、修改或复核、导出 | 按账套角色；仅接收移交所需事项证据 |
| AI / 后台任务 | 当前任务获准的企业与账套 | 提取字段、提示异常、生成建议 | 无自动付款、税务申报或自行复核权限 |

每次列表、搜索、附件下载、异步任务和导出都重新校验范围。员工“本人可见”、主管“部门可见”和财务“企业可见”分别实现，不能因为同属一家企业就共享全部原件。工资、个人银行信息等进一步按字段和用途限制。事务所服务关系与企业组织关系独立；负责人管理本事务所账套的既有能力，不自动开放客户所有员工事项。

## 数据与状态分离

新增 `business_events` 保存事项主信息，`business_event_versions` 保存不可覆盖的 payload / 模板快照，`attachments` 保存私有原件与哈希，`approval_steps` 保存审批节点与决定，`provider_receipts` 保存外部原始回执，`journal_mappings` 关联事项版本、来源流水与凭证建议。原始 `sources` 继续保留；一个事项可有多张票据、多笔流水和多条分录，避免将三者压成一行。

业务状态采用“草稿 → 已提交 → 业务批准 / 退回 / 撤回”；会计状态独立采用“待资料 → 待建议 → 待复核 → 已审核 → 已导出”。主管批准证明业务成立，不能直接把事项标成会计已审核。收付款状态保持独立，未付款是否需要确认账务由已审核的模板规则决定。

提交、审批、移交、导出均使用版本检查和数据库事务；修改已提交事实须新建版本并撤销受影响的旧审批有效性。重试使用企业、来源和外部 ID 范围的幂等键；相同键不同内容报冲突。附件哈希、票号和相似金额只产生重复候选，由规则与复核确定处理，不把相同金额直接删单。已审核记录沿用冻结与更正机制。

AI 输出保存模型、规则版本、字段证据与解释，仅提出分类和匹配建议。状态转换、金额合计、权限、借贷校验由确定性程序完成。异步任务通过事务内任务记录 / outbox 分发，回执验签、去重后再更新收付款事实；通知失败不能重复生成凭证。原件访问使用短时授权链接，检索与缓存同样按企业和账套隔离。

## 试点顺序与验收

1. 先选资料可获得、制度明确的 **2–3 家真实企业**，由会计确认三类以内模板、审批人、科目及导出目标，记录现行处理时间。
2. 实现员工提交、私有附件、版本和幂等；覆盖员工本人、主管部门、财务企业的隔离测试，再接业务审批与会计移交。
3. 接结构化 OCR 与受限模型建议，把缺资料、重复候选和低确定性处理集中到异常工作台；保留人工完成整条流程的入口。
4. 用完整月份核对原件、流水、审核凭证、导出回执与客户财务系统结果，再评估扩大模板及企业数量。

试点逐项记录：每事项 / 企业每月人工分钟、员工补资料次数、首次资料完整率、复核修改率、重复提交处理结果、导出核验差异、跨范围访问拒绝、失败重试与恢复结果。指标按事项类型和异常原因拆分，与试点前基线比较；先收集真实数据，再设改善目标。账务差异须逐项解释并处理，不能用平均准确率掩盖未解决事项。服务企业数量来自实测处理量、复杂度和月结质量，不在代码中固定容量承诺。
