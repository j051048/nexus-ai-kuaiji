# 第三阶段业务事项数据库

业务原件与账务来源分开保存。员工的事项完成部门审批、企业财务审批后，才在一个事务中生成 `sources.source_kind='business'` 的来源和待会计复核的凭证草稿。`handed_off` 表示已交会计处理，不表示正式过账或已经支付。

## 迁移与部署

- SQLite 的 `003_business.sql` 新增业务表，`004_business_create_idempotency.sql` 增加创建重试去重，均由现有数据库启动迁移器应用，用于本地演示和自动化验证。
- PostgreSQL 的 `005_business.sql` 新增业务表、私有函数、强制 RLS，以及来源种类；`006` 增加申请人专用的审批配置检查；`007` 明确普通员工部门限制和企业管理、财务身份选部门的权限；`008` 增加创建重试去重；`009` 仅向可见事项的用户提供该事项申请人姓名。
- 已应用迁移保留原文与校验和，后续变更新增迁移。运行服务不会执行 PostgreSQL 管理员迁移。
- 按 [POSTGRES_SETUP.md](POSTGRES_SETUP.md) 使用管理员连接运行 `python scripts/migrate_accounting.py migrate`，再使用独立受限运行账号启动后端。Supabase 仍使用同一流程，`accounting` 是后端私有 schema，不把它加入浏览器 PostgREST 的公开 schema。

`accounting_app` 保持 `NOLOGIN / NOSUPERUSER / NOBYPASSRLS`，运行登录账号通过现有事务适配器切换该角色，并在事务内设置已经验证的用户和事务所身份。`accounting_system` 仅用于账号身份同步，不能读取任何业务事项表。新的安全函数固定 `search_path`，撤销 `PUBLIC` 执行权，由具备 `BYPASSRLS` 的迁移所有者维护，避免策略递归和隐藏记录导致的错误授权。

## 数据契约

| 表 | 用途与关键约束 |
| --- | --- |
| `business_events` | 当前事项；固定申请人、企业、事务所、部门、模板身份，保存当前状态及乐观锁版本 |
| `business_versions` | 提交时的 payload、模板和附件列表快照；主键为事项与提交版本 |
| `business_attachments` | 私有附件元数据与 SHA-256；文件路径仅在授权下载服务内部使用 |
| `business_actions` | 部门、财务、退回、移交记录；关联实际提交版本，不随后续修改改变 |
| `business_mappings` | 事项到来源与草稿的单次移交回执；事务所内幂等键唯一 |
| `department_approvers` | 明确授予的部门审批范围；撤销公司成员时自动删除其审批授权 |

创建表单可以提供幂等键；事务所与申请人范围内，同一个键只对应一条事项。响应丢失后的同内容重试返回现有事项，修改金额等内容后沿用旧键会返回冲突，不会再生成一笔报销。事件内的创建键与原始请求指纹不可更改，接口不会暴露内部指纹。未指定幂等键的内部调用保持兼容。

子表都通过 `(event_id, firm_id, company_id)` 外键绑定事项。移交表还把账套与企业、来源与账套、草稿与来源同时绑定，禁止同事务所内的跨企业错账以及同账套内的来源错配。每个事项最多有一个移交回执，同一来源与草稿不能再映射另一个事项。既有账套在迁移时补齐 `2241 其他应付款`，新账套沿用当前科目模板。

原件、快照、审批和回执表只授予运行角色 `SELECT / INSERT`，没有 `UPDATE / DELETE`。SQLite 对这四类表设置不可修改触发器，但 SQLite 不具备 PostgreSQL RLS；其读写范围依靠同一业务服务校验，仅作为本地验证部署。审批状态和版本的完整流程由固定业务服务控制，数据库再约束身份、外键与角色范围。

## 数据可见范围

申请人可读取自己的事项；部门审批人可读取明确授权部门的事项；公司 `finance` 可读取该企业全部事项。企业 `owner/admin` 与事务所管理员的管理权限不会自动开放员工事项、附件或业务审批权，需要额外明确的审批身份。

已有账套读取权限的会计及查看人员，只有在事项已经移交且映射到其授权账套后，才可读取相关业务证据。没有账套授权的事务所成员无法读取；普通员工不会因为录入权限得到整个企业账本。移交回执中的账套、来源和草稿 ID 仅开放给企业财务或实际授权的账套人员，申请人仍可查看事项的移交状态。

所有范围都要求当前事务所匹配、用户有效、客户服务关系有效；权限检查实时读取数据库。撤销公司成员、部门审批权、账套授权，或暂停客户服务关系，会在下一次事务请求生效。提交准备检查只向申请人返回“是否存在有效且非本人的部门、财务审批人”布尔值，不开放其他员工名单。

部门和财务审批人可显示其可见事项的申请人姓名。姓名查询函数仍使用完整事件范围判断，隐藏事项返回空值，不开放申请人的邮箱或用户表其他资料。

## 独立验证

`nexus_backend/tests/test_business_postgres.py` 使用明确指定的管理员及运行测试 DSN，随机创建隔离测试 ID，不截断已有表。此次在本机专用 PostgreSQL 数据库上通过 37 项测试：

- 绕过 API 的 SQL 仍受到本人、部门、企业、事务所与账套 RLS 限制；管理员不会自动看到未移交员工资料。
- 跨事务所、停用账号、暂停客户、撤销成员和审批授权后，各层原件及审批记录不可见。
- 禁止本人审批、伪造申请人、普通员工跨部门建单，以及修改既有原件、提交快照、审批记录和移交回执。
- 三个模板的五种常用收支情况完成业务服务录入、附件、提交、双审、移交、会计复核和 CSV 导出。
- 四个并发移交请求只产生一个来源、一份草稿和一个回执；退回重提保留原提交金额与审批版本。
- 四个并发建单请求只产生一个事项，内容改变后复用创建键被拒绝；不同申请人的创建键互不影响。
- 申请人姓名函数遵循既有事项可见范围，管理员、其他员工和未收到移交的会计不能查询该事项申请人姓名。

测试环境是独立本机 PostgreSQL，不代表已经接入真实企业、Supabase 云端或完成真实月份关账。2–3 家企业试点应使用各自独立企业和账套授权，按实际成员配置部门审批人及财务，并继续保留会计审核后导出的工作方式。
