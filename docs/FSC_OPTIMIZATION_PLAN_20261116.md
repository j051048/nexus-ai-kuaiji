## 1. 背景变化带来的优先级重排

审计时按"代账中心、上千客户"的假设评估。真实场景是同一国企集团下五家独立核算单位、由约 5 名核心财务集中办理。这改变了问题的轻重：

| 审计发现 | 原定级 | 重排后 | 理由 |
|---|---|---|---|
| 审计日志无防改删触发器、无哈希链 | 中 | **最高** | 巡视、国资监管、外部审计要求留痕可自证 |
| 读取与下载不留审计 | 中 | **高** | 涉密单位（内部医院）必查"谁看过什么" |
| 单人模式可关闭制单复核分离 | 中 | **高** | 国企不相容职务分离是硬要求，应可按集团策略禁用 |
| 事务所 owner/admin 全权限 | 中 | **高** | 系统管理与账务复核须分离 |
| 只有小企业报表模板，`standard_kind` 未生效 | 中 | **最高** | 国企通常执行企业会计准则，医院可能适用其他制度 |
| 税种仅增值税加附加，取整三套规则 | 中 | **高** | 广告、食材、贸易各有专门税费口径 |
| Postgres 金额列 32 位（上限约 2147 万元） | 高 | **最高** | 贸易公司单笔极可能超限 |
| 备份未加密、敏感字段无脱敏 | 中 | **高** | 医院准入前置条件 |
| 主干 CI 持续红灯 | 最高 | **最高** | 不变 |
| 批量 worker 无部署角色 | 最高 | **高** | 不变，五家批量开账和月结都依赖它 |
| 无定时调度 | 高 | **高** | 5 人办 15 人的活，不能靠人记得去点 |
| 全局写锁、并发上限 8、队列无租户公平 | 高 | **中低** | 五家单位、个位数并发用户下不构成瓶颈；仅需保证新代码不加重 |
| 前端密度低、录入慢、金额浮点 | 中 | **高** | 人效目标直接取决于单笔办理时间 |

## 2. 对 Gemini 规划的取舍

### 2.1 采纳

1. **砍掉内部交易镜像与合并抵消。** 五家基本无内部交易，集团层只做管理汇总。须在界面和报告中写明"管理汇总不等于合并财务报表"。
2. **一套通用批次内核加行业配置包。** 与 FSC04 一致。
3. **证据门禁："审批快照、合同、验收或出入库单、发票"四件套。** 缺件转补件请求，不带病入账。与 FSC05 一致。
4. **集团监管看板：五家横向指标加"两金"（应收账款、存货）与账龄预警。** 归入 FSC11。
5. **月结就绪度视图：每家卡在哪一步、缺哪份材料。** 归入 FSC06、FSC11。
6. **助手只筹备动作，人点击确认。** 现有 `assistant/actions.py` 的指纹化计划机制可直接扩展。
7. **医院导入时剥离个人敏感字段，只保留科室、批次、金额。** 作为必要条件采纳，但不充分，见 2.3。

### 2.2 修正后采纳

| Gemini 原提法 | 问题 | 修正 |
|---|---|---|
| "不新增冗余数据表，直接扩展" | 会把领域实体塞进 JSON 或出租车专用表 | 按总工作令第 3.8 条：需要领域实体时合理新增表 |
| 用 `transport_aliases` 做贸易客商别名库 | 出租车专用表承载通用概念 | 抽出通用别名表，出租车迁移过去 |
| 用 `lease_contracts` 做物业预收分摊 | 仅改界面术语不够 | 可复用分期引擎，但收入确认方法须来自企业批准的政策 |
| "出租车已就绪 90%" | FSC02 状态为"进行中，未整体通过"；五家档案 12 栏全部为空、状态未确认 | 以 `FSC_EXECUTION_STATUS.md` 为准，不引用该百分比 |
| 第 1 个月上线出租车加贸易 | 贸易依赖金额列扩容和存货权威系统核定 | 贸易排在金额列修复之后，顺序按 FSC07–10 且可按资料成熟度调整 |
| "2 天内完成五家月结" | 是目标不是承诺 | 作为 FSC12 的测量项，按总工作令第 7 节口径计量 |
| 复核抽屉右侧显示四件套检查 | 方向对，但规则不能写死 | 证据政策按动作、金额、业态配置，带版本和生效期 |

### 2.3 Gemini 规划遗漏、必须补上的

1. **核算制度。** 系统只有 `small_enterprise_basic` 一个报表模板（`app/reports/service.py:21`），科目代码写死在约 18 个文件里。国企子公司大概率执行企业会计准则；内部医院适用何种制度须逐家确认，不能从行业名推定。
2. **税费模型。** 现在每账套一个增值税率加附加。广告的文化事业建设费、食材的农产品进项抵扣、企业所得税预缴、印花税都没有模型。Gemini 提到了前两者，但没指出底层缺口。
3. **部署形态与数据出境。** 现架构是 Supabase 认证加外部大模型接口。脱敏只解决字段问题，不解决"数据是否允许离开单位网络"。医院默认不得上云、不得调用外部模型，直到准入通过。
4. **审计留痕的技术可信度。** Gemini 把"巡视审计留痕"列为第一优先级，却默认底座已"防篡改"。实际上凭证有硬触发器，审计日志没有。
5. **工程门禁失效。** 主干 CI 红灯、提交直接进主干。任何行业包建立在不受保护的主干上都不可靠。
6. **版本引用不准。** 文中 "v001–v243" 等编号与仓库迁移编号（Postgres 至 252、SQLite 至 166）对不上，不作为依据。
