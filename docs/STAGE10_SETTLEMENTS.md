# 同期应收应付辅助核销

本轮只支持同一企业、同一开放期间物理账套、人民币的辅助未结事项。长期账套身份不会自动授予其它月份权限。跨期支付、以前已审核业务的首次登记、复杂多科目原业务和已导出调整，暂不在本轮范围。

## 会计闭环

1. 当前移交的业务事实为 `payment_status=unpaid`；未审核业务草稿以一个支持的应付/应收科目记录全部金额。登记未结事项时绑定事实版本、来源指纹、稳定交易对方 ID 和原始名称。
2. 一笔银行流水可以分配多个未结事项，一项业务可以接受多次银行支付。每次分配金额分别不能超过银行未分配余额、业务未结余额，且同企业、同期间、同方向和同稳定交易对方。所有计算使用整数分。
3. 原业务凭证仍按未付款/未收款审核，例如 `借：费用，贷：应付账款`。登记后原业务可以先审核，之后继续分配支付，不修改原未付款事实或已审核分录。
4. 银行流水全部分配，且被关联业务原凭证均已审核/导出后，生成银行清偿草稿，例如 `借：应付账款，贷：银行存款`。会计核对、补齐辅助项并审核后正常导出。银行草稿不能再重复计入费用或收入。

支持的原业务清偿科目为 `2202/2241`（应付）、`1122/1221`（应收），银行清偿目前使用 `1002`；多级子科目、多个原应付科目及更多银行账户科目需要以后配置扩展，不能猜测科目替代。业务金额不能因分配而改变。

当前员工模板中日常收支固定为已收/已付，采购/报销支持未付款，因此真实页面首先验证应付清偿。底层保留应收清偿校验，但未来增加经过审核的未收款业务模板前，不宣称员工页面已经覆盖应收款登记。

## 凭证与变更保护

所有登记、预览、确认、分配和撤销为追加记录。确认重验预览里的来源、事实、草稿版本、主数据映射和双方剩余余额；重试同幂等键返回原回执，不重复占用余额。

撤销需要另一名仍有当前账套复核权限的人员、当前分配指纹和理由，追加 `settlement_reversals` 记录。已审核或已导出的银行凭证不能撤销分配，需要另行调整流程。已审核原业务本身不会禁止后来收付分配。待审批事实修订阻止新分配；旧业务存在有效分配时不能替代事实，应先独立撤销未审银行分配。原件、原事实和分配历史一直保留。

旧 `ai_bank_links` 完整流水匹配与新核销分配互斥。已分配银行不能当作重复来源隔离。部分分配银行不允许审核、导出或通过月结；正常未付款业务的未结余额本身不会被解释成月结失败。银行全额分配后仍需逐科目验证清偿分录，不能只根据金额平衡放行。

## API

以下接口均位于 `/api/books/{book_id}/settlements`，需要当前账套 review 权限，写入另检查当前开放期间。

- `GET ?limit=20&offset=0`：未结余额分页、可登记当前业务、待分配银行和分配/撤销历史。原始名称与稳定主数据 ID 并列，身份不明确时不自动分配。
- `POST /items`：`source_id/counterparty_id/expected_draft_version/idempotency_key/reason`。
- `POST /previews`：`bank_source_id/parts[{item_id,amount}]/reason`；金额为精确到分的字符串。
- `POST /previews/{id}/confirm`：`idempotency_key`，私有预览 10 分钟有效。
- `GET /banks/{source_id}/clearance`：确定性清偿草稿及阻断项，最终写草稿使用既有 DraftUpdate API，审核/导出继续走原流程。
- `POST /allocations/{id}/reverse`：`expected_fingerprint/idempotency_key/reason`。
- `POST /split`：`total/parts[{key,weight}]`，整数最大余数法，余数并列按稳定 key 排序；总和精确等于原金额，少于一分的分配可能为零，确认不接受零金额事项。

## 数据库与集成

PG045 / SQLite031：`settlement_items/previews/commands/allocations/reversals`。PostgreSQL FORCE RLS 在读取之前检查当前账套复核范围；API/worker 不能直接插入、修改或删除核销事实，原生能力重新计算余额和预览。worker 没有这些私有表的读取权限。

`SettlementService.blocking_issues_in_transaction(conn,actor,source,lines)` 对有关银行检查全部分配、业务原凭证已审核和精确清偿科目；`source_allocated[_in_transaction]` 用于旧匹配、事实修订和来源隔离互斥，`policy_fingerprint_in_transaction` 将分配/撤销证据纳入旧审核预览失效判断。月结将登记/分配/撤销追加记录纳入私有事实指纹。

这是辅助核销记录和凭证交付闭环，不是自建正式总账或完整应收应付模块。真实试点需在客户财务软件核验业务应付/应收凭证与银行清偿凭证均入账、余额一致、无重复费用/收入。

## 清偿样例的学习范围

PG054 / SQLite039 将已审核银行清偿样例保留用于追溯，但不允许用作普通银行分类规则的正例、显式反例或发布依据。审核本身仍成功，自动提议普通规则会跳过这种样例；界面说明范围并禁用建立普通规则/选为反例。API 和原生版本、评估收据、发布触发器分别重新检查，旧规则也不能凭过往评估收据推广。

清偿依赖实际核销余额、原应收应付凭证和付款对应关系，仅按交易对方/方向的普通分类条件不能表达这些前提。因此已有历史错误发布规则若引用这种样例，后续草稿生成会忽略它；不会修改或删除原样例、规则版本及审核证据。以后支持核销条件的独立规则语言和评估前，不把应付清偿自动推广到其它普通银行付款。
