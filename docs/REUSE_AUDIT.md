### BaseTool 移植时必须处理的边界

1. `base_tool.py:131` 从旧 `reviewed_policies` 读取工具策略。会计工具应使用自己的显式白名单，未登记的工具必须拒绝执行，不能让模型自行决定动作级别。
2. `base_tool.py:289` 为确认流程导入整个 Agent checkpointer。会计审核应由业务数据的状态、版本、审核人及证据摘要持久化；不要仅因为内存确认成功就允许过账。
3. `base_tool.py:260` 的金额门槛只识别 `int | float`。会计 API 使用精确金额字符串或分整数后，不能沿用该分支作为资金或过账控制。
4. `base_tool.py:320` 捕获错误的 JSON Schema 后仅记录日志。会计分支应在参数 schema 错误时拒绝执行，避免错误定义被当成校验通过。
5. `base_tool.py:393` 返回结构化 `ToolResult`，可与 `result_contract.py` 一起保留。结果必须区分建议成功、被阻止、失败、结果未知；这些状态不等同于凭证已过账。
6. 过账、关账、冲销的权限、平衡、版本与幂等校验必须落在领域服务和数据库事务中。`BaseTool` 只是外围工具协议，不承担账务正确性。

### 为什么不复用旧 Finance 作为账本

本次读源码仍能确认 Opus 提到的具体边界：

- `nexus_backend/app/routers/finance.py:15` 的 `BudgetCreate` 要求 `category/amount/period`，`src/pages/FinanceCenter.tsx` 的预算提交使用 `name/total_amount/period`。
- `finance.py:17` 与 `:23` 的预算/发票金额为 `float`。
- `nexus_backend/app/tools/finance_tools.py:477` 的 `InvoiceOCRTool` 最后在 `:563` 将识别文本置于 summary，`data={}`，无法作为结构化会计证据。

因此，旧预算、报销、发票展示属于企业运营功能。会计科目、期间、原始来源、凭证分录、审核与过账需要独立实现。原始流水应保留，可重复运行分类流程；草稿不能覆盖原始证据。

## 分期实施与验收

### 第一阶段：本地可验证的会计核心

范围：Python FastAPI + SQLite 本地开发模式、React 例外工作台、账套与期间、来源流水导入与去重、可解释分类建议、凭证草稿/编辑/审核、确定性校验与通用凭证 CSV 导出。金额使用精确表示，UI 不参与账务计算。本轮不是正式总账：导出冻结不等同于财务软件已接收或正式过账，不提供总账余额、报税或财务报表。

SQLite 只用于低成本验证领域规则和 UI 流程；开发身份不是客户身份系统，也不是正式多用户部署方案。没有正式认证/授权时，生产运行必须拒绝启动或拒绝受保护操作，不能以可伪造的 user/book 请求头提供生产授权。

第一阶段最低验收：

- 重复导入不产生第二份来源，同一幂等请求重复导出返回同一收据；接入正式账本后再验证重复过账不产生第二张凭证。
- 一次失败的整批导入、审核或导出不会留下部分业务变更。
- 借贷不平、禁用科目、跨账套关联、期间关闭、草稿已被修改时拒绝审核或新建导出。
- 审核绑定草稿版本；已审核记录冻结，后续如提供撤回编辑必须使旧审核失效。
- 原始来源可追踪，金额可复算，已导出记录不提供普通删除/覆盖接口。
- UI 只展示真实返回的统计，演示数据明确标识；规则建议不冒充已接通的大模型。

### 第二阶段：面向真实试点的认证、数据库和证据

迁移 PostgreSQL（可托管于独立 Supabase 项目），建立事务所成员、客户账套授权、RLS、复核职责分离、审计事件、事务性 outbox 与后台任务。把 JWT 验签适配到新的身份表，补充发行方和受众校验，权限撤销及时生效。

接入结构化 CSV/Excel/银行流水、票据文件存储与 OCR 字段来源。逐字段校验金额/税额/日期/主体，识别错误进入例外队列。接入受约束的模型适配器并保存模型/提示/规则版本；模型只提建议，不能绕过凭证校验和人工审核。

验收使用跨事务所/跨账套权限测试、并发过账与重试、数据库迁移、备份恢复、客户原始单据追踪、导出回执及差异校验。不能用单机 SQLite 通过测试代替这些证明。

### 第三阶段：批量生产力与真实月结

先在单一客户群验证基础对账、补资料清单、规则复用、批量审核、冲销调整、期初余额与月结检查，再增加客户现有财务系统的正式适配。Firm 层仅共享授权的规则和模板，不默认共享客户原始票据或训练样例。

“1 人管理 200–500 家企业”是要通过真实业务验证的产品目标，不是第一版的性能承诺。至少持续记录：每账套单据量、自动建议覆盖率、人工修改率、待补资料占比、每百笔审核耗时、每户月结耗时、过账错误与追溯恢复时间。吞吐量、审核质量和会计月结耗时都达标后才扩大账套数量。

## 本轮独立复核记录

本轮实际的 `nexus_backend/app/tools/accounting_tools.py` 是参考上游 BaseTool 的策略分离思想编写的最小适配器，并未继承或完整复制旧 BaseTool、result_contract、LangGraph 或模型网关。其权限检查仍委托会计领域服务执行；规则建议明确标识为确定性规则，尚未连接大模型。

独立审查发现并交由后端作者修复的具体问题：来源导入 SQL 的占位符数量与列数不一致，会使首次导入失败；数据库初始化连接使用 SQLite 上下文管理器后未显式关闭，在 Windows 临时数据库清理时暴露文件锁。复核使用单独临时数据库，不接触项目演示库或外部服务。

占位符修复后的独立服务探针通过：

- 金额 `0.01`、`0.29` 和上限 `999999999999.99` 精确往返；拒绝浮点、指数、非有限数、负数、超两位小数、超限金额和无效日期。
- 批量导入遇到已有 ID 的不同内容时回滚此前新增行；相同规范化内容重复导入不增加来源。
- 复合外键拒绝跨事务所账套授权和跨账套来源/凭证/分录关联；服务拒绝跨事务所访问与缺少复核角色的审核。
- 补证追加记录保留原来源 hash，使已有草稿版本失效；已审核后拒绝补证。
- 导出保存原始精确金额并转义 CSV 公式文本；相同幂等键返回同一收据，其他幂等键不能重复导出已冻结凭证。
- 注入审计写入失败时，导出收据和凭证冻结状态一起回滚；4 个线程并发重试同一导出请求最终仅有 1 份导出、1 条导出审计。初始化连接改用显式关闭后，Windows 临时库正常清理。
- 关闭期间拒绝新的写入，但允许重放已有导出收据。
- HTTP 层拒绝未登录访问（包括 API 文档）、非回环客户端、不可信 Host/Origin、过期令牌和浮点 JSON；生产模式拒绝启动。

这些检查证明本轮本地实现的若干关键边界，不能代替正式 PostgreSQL/RLS、多用户身份、恢复演练、真实客户月结及 200–500 家企业负载验证。后端作者维护的自动化测试和前端端到端检查是后续回归入口。
