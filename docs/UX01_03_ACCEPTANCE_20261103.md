## 02：消息权限与错误处理

先写失败测试，复现 3 个缺陷：同企业其他员工的定向消息可被标记已读；广播的一个读者影响其他人的已读状态；撤权后仍能读取历史定向消息。

修复后：

1. 列表与标已读共用当前事务内的可见范围：当前事务所、有效企业关联、成员/授权关系、收件人，明确括号避免广播条件跨越事务所边界。
2. 广播按读者保存回执，重复标记幂等；服务器生成读时间。历史定向消息兼容已有 read_at，历史广播共享 read_at 不充当个人已读证据。
3. PG 原生 SQL 也受 RLS 保护；个人回执仅 SELECT/INSERT，不扩大员工账套权限。
4. 页面读写错误受控展示；撤权清掉旧消息和计数；不把读取失败显示成“没有消息”；发送中的按钮防连点。
5. 写入结果未知时不自动重复 POST，要求用户刷新读取实际状态。成功后也重新读取权威结果，不乐观伪造已读。
6. 未读数明确为“当前页”，未知时不伪装为零。

新增 PG `215_client_message_receipts.sql`、SQLite `132_client_message_receipts.sql`。只在本地隔离库应用，未修改历史 SQL/checksum。

## 03：期间与交接准备前置

先写 8 项失败测试，再实现 `GET /api/business/preparation`，复用现有权限和实际交接检查。

- 输入绑定当前企业与真实发生日期，严格校验日期。返回仅有准备状态、责任岗位与下一步，不向员工暴露账套 ID、余额或额外账簿权限。
- 区分可继续、未开账、账期关闭、缺交接权限。财务/会计的编辑授权必须实时成立。
- 员工选择企业/日期时即可看到提示；财务在核验、交接前即可看到缺口，不再到最后一步才知道。
- 缺账期允许先保存原件及业务资料，明确等待会计准备；不把业务发生日期自动挪到其他月份，不自动开账、不自动授予权限。
- 实际交接仍在事务内重新检查权限、期间和版本，前置提示不是交接凭证。
- 换企业、换日期、撤权后旧结果不再显示；响应中的企业、月份、状态等必须通过运行时校验。重新检查同时刷新可交接账套。

新增 PG `216_business_preparation_projection.sql`：受控函数只输出准备状态，员工仍不能直接查询账簿。未改审批、独立复核、正式记账或导出政策。
