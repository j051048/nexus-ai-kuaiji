完整后端测试先通过 187 项；随后增加已确认邮箱的校验及 6 个认证边界用例，对认证子集复验 107 项通过。因此本轮总计 193 项分别完成验证，没有将真实 Supabase 在线验收计入这些结果。

PostgreSQL 已实际执行 001–004 显式迁移。运行连接没有 SUPERUSER/BYPASSRLS，所有业务表强制 RLS。验证了直接绕过服务查询时的跨事务所/未授权账套/普通员工拒绝、viewer 写入拒绝、客户暂停及用户停用、公司部门归属、一致快照、并发去重/审核/导出与期间关闭、审计失败整体回滚。系统身份角色只能访问用户资料，不能读取账务。

HTTP 接口联调使用真实 PostgreSQL，跑通登录身份同步、新事务所开户、客户企业及账套创建、按邮箱授权、录入与复核分离、导出与重新下载、账套撤权、员工登录无账本，以及同一身份切换两个独立事务所。

## 审查中修复的权限边界

- 企业管理员不能更改自身职责为 owner/finance，不能赋予 owner；相关升级用例被拒绝。
- 企业管理员不能通过企业身份管理改变事务所人员的职责或账套分工。
- 历史 CSV 下载仍要求复核/导出权限，不能只凭读取权限下载。
- PostgreSQL RLS 不再隐藏管理校验所需的混合身份关系，避免把事务所人员误判成纯企业成员。
- 暂停客户的账套旧授权在撤销事务所成员时同步清理，重新加入不会自动恢复。
- 原始来源、追加证据、导出回执及审计对运行角色保持不可覆盖。
- 未确认的邮箱不能成为按邮箱授权的身份；认证服务故障和数据库故障不会降级放行。

## 合成工作台基准

第二阶段更新基准数据结构后执行 `python scripts/benchmark_workbench.py`：500 个客户账套、50,000 条来源、100,000 行分录。

- SQLite 总览 8 条 SQL（6 个 SELECT 与 BEGIN/COMMIT），本次约 505.08 ms。
- 账套、待审和异常数量断言通过。

这只是本机合成数据的一次汇总查询，不代表真实代账产能，也不是 PostgreSQL 多用户性能测试。MVP PostgreSQL 写操作采用全域事务锁；后续按账套细分并加入连接池、分页和任务调度。

## 试点前仍需完成的现场验证

在独立 Supabase 项目上执行迁移、建立受限运行账号、填写新环境配置、手动创建并确认少数用户，然后验证实际邮箱密码登录、密钥轮换、连接模式与撤权。Supabase shared pooler 的项目专属连接地址须从 Connect 面板取得，本机测试没有覆盖远程 Supavisor。

Supabase access token 签出后可能保持有效至过期；前端退出会立即清理资料，业务授权撤销每次数据库检查生效。即时会话吊销需后续核验 `auth.sessions`，当前不作此承诺。

真实业务还需确认客户适用科目、私有原件存储、备份恢复、外部财务系统回执与完整月份核对。员工业务表单、部门审批、OCR 与模型建议按 [后续规划](BUSINESS_ENTRY_ARCHITECTURE.md) 推进。
