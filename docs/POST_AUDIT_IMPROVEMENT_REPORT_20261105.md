## 0. 结论摘要

两份审计报告的价值不在评分，而在于它们从不同角度指向了同一组问题：

> **衡账的“控制链”已经明显强于普通 AI 记账 Demo，但“使用链”仍然偏重、偏长、偏工程化；要成为一人服务多家企业的生产系统，必须同时做减法和增智。**

两份报告与本次复核共同支持、建议进入后续路线的改良点有 8 项：

1. **前端壳层与列表减负**：压缩四层抬头，去掉列表里重复的说明长句，把双大卡改成紧凑切换器。
2. **界面语言通俗化**：隐藏 UUID/哈希等机器码，把“事实版本”等内部术语换成会计和员工能懂的话。
3. **移动端首屏直达**：金额、事由、票据置顶，审批按钮吸底，说明折叠。
4. **AI 从模板播报升级为“受控叙述 + 只读聚合分析”**：保留确定性校验，但允许带引用的解释和跨期对比。
5. **建立真实脏数据评测集**：用脱敏疑难票据和真实分录评估 OCR/LLM，而不是只做契约回放。
6. **数据库减负**：冻结复杂 PL/pgSQL 业务逻辑，明确 SQLite 只做测试/离线，不让双轨制继续膨胀。
7. **用真实容量与真实用户证明“200–500 家”**：当前只有 2–3 家试点定位和局部容量数据，不能把目标当结果。
8. **Design System 与前端工程治理**：收敛字号、色值、断点和巨型文件，继续压缩员工首屏包体。

建议按“**先减负、再增智、后治理**”推进，而不是先做大规模架构重写。

## 1. 共识边界：这些控制不能为了“好用”而削弱

以下边界来自现有产品契约，任何改良都不得绕过：

- 权限由服务端当前有效授权决定，前端显示不构成授权。
- 企业、事务所、账套、期间必须隔离；跨企业对象不可探测。
- 制单责任绑定待审版本；独立复核政策不得降级为默认自审。
- AI 只能写草稿，不能自行决定正式账务、复核、发布、通知或签收。
- 会计复核后才能导出；导出、包草稿、发布、通道接受、送达、查看、签收分别记录。
- 费用未知不得改为零；已发送但结果未知的 attempt 不得自动重发。
- 不覆盖人工修改，不补造历史审核、申报、送达或签收记录。
- RLS、账本不可变、append-only、审计日志等数据库防线不得为了“薄触发器”而删除。

**本报告中的“减负”只减界面噪声和重复工程，不减控制。**

## 3. 工作包

### WP1／P0：信息架构与首屏减负

**现状证据**

- 1440×1000 下，全局顶栏、身份通栏、轻壳导航、工作台大标题四层合计约 290px，再叠加动作说明卡，第一条业务数据被推到首屏下半部。
- 会计待办列表每行重复同一句 44 字“下一步”说明；7 条记录就需要滚动较长时间。
- “需要我处理 / 我的办理进度”被做成两张高约 100px 的统计卡，列表头又重复一次数字。
- 页面底部纵向堆叠多个折叠手风琴与 AI 免责说明。

**改法**

1. 顶部保留一条全局栏 + 一条**紧凑上下文条**，上下文中必须始终可见：
   - 当前身份
   - 当前企业
   - 当前账套
   - 当前期间
   - 权限范围入口
2. 删除装饰性英文眉题和重复的“当前工作台 / 我的工作台”状态条。
3. 双大卡改为 36–40px 的 segmented tabs；统计数字只出现一次。
4. 列表行改为“状态 + 摘要 + 客户/申请人 + 金额 + 主动作”的紧凑结构。
5. “下一步”按状态分层：
   - 常规行：不显示；
   - 退回、阻断、unknown、跨企业、权限不足：显示一行原因和下一步；
   - 一般规则：收进行展开或 `?`。
6. 底部手风琴按用途迁移：
   - 岗位说明 → 顶栏帮助浮层；
   - 签收资料包 → 待办列表的一个 Tab；
   - 其他授权工作 → 左侧导航或顶栏菜单；
   - AI 免责 → 草稿旁一行徽章 + tooltip。

**验收**

- 1440×900 首屏至少完整展示 6 条待办，理想 8–10 条。
- 单条常规待办行高不超过 64px。
- 页面总高度相比基线下降 ≥35%。
- 当前企业/账套/期间始终可见，不能为了高度把安全上下文藏进头像菜单。
- 保留 blocked/退回/unknown 的原因和下一步。

### WP2／P0：语言通俗化与机器码治理

**现状证据**

- `src/WorkspaceHome.tsx:599`：`数量暂未汇总，以当前清单为准`，与列表 0 项不一致。
- `src/task-presentation.ts:199`：`确认当前事实版本后按页面授权审核`。
- `src/FirmCockpit.tsx:205`：`可能跨月，不是个人指派量`。
- `src/ReviewWorkbench.tsx:462`：`基础检查分组用于定位待办，正式审核会重新核验全部事实`。
- 审计截图中出现过 UUID 后缀和 SHA-256 进入标题/文件名的情况；前端没有统一的人类可读标题兜底。

**改法**

1. 建立 `src/presentation-copy.ts` 或等价模块，集中管理：
   - 状态名
   - 下一步文案
   - 退回原因
   - 金额/日期/票据类型
   - 机器码展示规则
2. UUID/哈希展示规则：
   - 默认不显示；
   - 详情页以“票据原件 #1 · 查看存证指纹”折叠；
   - 复制按钮保留，但不占标题黄金位置；
   - 没有业务摘要时，用“类型 + 日期 + 金额”生成标题，禁止直接回退到 UUID。
3. 统一术语：
   - 会计事实 → 票据/业务记录/凭证依据
   - 事实版本 → 资料版本/审核版本
   - 基础检查分组 → 检查项分类
   - 当前客户全部会计事实与待办 → 当前客户的票据、凭证与待办
4. 免责声明保留，但压缩：
   - “AI 生成草稿 · 待人工复核”徽章；
   - 详细说明放 tooltip；
   - 不删除合规提示。
5. 计数未知时不要显示 `—` 和“数量暂未汇总”；返回真实计数，或显示“查看清单”，不得让用户以为系统没算完。

**验收**

- 关键页面不出现裸 UUID、裸 SHA-256。
- 员工端与财务端核心流程不出现“事实版本”“会计事实”等内部术语。
- `数量暂未汇总` 不再作为常驻占位。
- 免责声明仍可在 1 次点击内看到。

### WP3／P0：移动端首屏直达

**现状证据**

- 390×844 下，员工端首屏被全局栏、身份栏、四个 tab、标题、步骤卡和三张模板卡占满。
- 客户企业、部门、附件、日期、金额都在折叠线以下。
- 企业财务核验页同样被状态说明框和“本步核对要点”占据，票据与审批按钮落到第二屏。

**改法**

1. 手机端顶部只保留一条 48px 导航栏：
   - 左：返回/标题；
   - 右：身份/企业胶囊。
2. 主导航改为底部固定 Tab；先做 A/B，不直接全量替换。
3. 核验详情页第一屏顺序：
   - 金额大字
   - 报销人/事由
   - 票据缩略图
   - 关键差异/阻断原因
4. `退回修改` / `核验通过` 固定在底部，但必须避开系统键盘和 safe-area。
5. “当前状态 / 下一步 / 本步要点”折叠为一行可展开提示。
6. 员工录入表单单列化；附件和金额优先，分类/用途/项目放“更多信息”。

**验收**

- 390×844 首屏可见金额、事由、票据缩略图、主动作。
- 单手可完成“查看—通过/退回”。
- 键盘弹出、横屏、长企业名、底部 safe-area 不遮挡按钮。
- 真机覆盖 iOS Safari、Android Chrome、微信内置浏览器；模拟视口不能代替。

### WP4／P1：AI 受控叙述与只读聚合分析

**现状证据**

- `nexus_backend/app/assistant/fact_validation.py:3` 明确模型 prose 不可信。
- 最终回答由 `_descriptor` 和固定模板拼接，主要支持金额、日期、计数叶子。
- 对“本月差旅费为什么上涨”“哪几个部门集中报销”这类问题，容易落到 `unsupported_case`。

**改法**

1. **保留**现有金额、日期、版本、证据引用的确定性校验。
2. 允许模型生成**带句级引用的叙述**：
   - 每个关键断言附 `[fact:id]`；
   - 前端渲染为可点击的引用胶囊；
   - 未绑定的断言直接拒绝，不回退成自由文本。
3. 增加只读的**参数化聚合查询工具**：
   - 按期间、科目、部门、往来单位、费用类型聚合；
   - 只允许 SELECT/聚合，不允许写；
   - 限制时间范围、返回行数、扫描量；
   - 明确返回“覆盖范围”和“未检查部分”。
4. 弃权仍然保留，但只在：
   - 证据不足；
   - 证据冲突；
   - 超出支持范围；
   - 需要会计判断。
5. 回答结构统一：
   - 结论
   - 关键数字 + 引用
   - 范围/口径
   - 下一步/负责人
   - 未知或未检查部分

**验收**

- 固定评测集上事实错误率为 0；所有金额/日期可回链。
- 聚合查询有行数/时间上限，超限明确弃权。
- 回答不能出现未引用数字。
- 不允许 AI 生成正式分录、复核结论或签收。

### WP5／P1：真实脏数据 OCR/LLM 评测集

**现状证据**

- 现有 NEXT10 是固定确定性回放，`real_model_evaluated=false`。
- 现有测试强在超时、格式、权限、回滚，不强在真实票据准确率。

**改法**

1. 建 500–1000 张脱敏/合成疑难票据集：
   - 褶皱、反光、模糊、旋转；
   - 手写定额发票；
   - 一图多票、粘贴单；
   - 跨多月分摊合同；
   - 含混银行摘要；
   - 中英文混排、大小写/全半角。
2. 固定 dev / held-out 划分；held-out 不参与提示词和规则调优。
3. 指标：
   - 字段级 precision/recall/F1；
   - 金额、日期、税额的 exact match；
   - ECE 校准度；
   - 弃权率；
   - 人工修改率；
   - 单票耗时/成本。
4. 失败样本按“票据类型 × 字段 × 原因”归档，不只报总分。
5. 真实模型未接入时，明确写“离线工程通过”，不得宣称真实准确率。

**验收**

- 评测脚本可复跑，数据版本和 manifest hash 固定。
- 固定分母，missing/unknown 不从分母删除。
- 关键字段退步一票否决，不能被平均分抵消。
- 报告同时给出样本量、置信区间和失败样本。

### WP6／P1–P2：数据库减负与 SQLite 边界

**现状证据**

- 当前有 **205 个 PostgreSQL 迁移文件**、**133 个 SQLite 迁移文件**；schema 版本为 217（不是 217 个迁移文件）。
- 迁移文本中有 774 处函数/触发器定义/重定义。
- 清单校验、通知文案、复杂角色条件确实有进入 PL/pgSQL 的情况。
- 同一业务约束在 Python、PG、SQLite 三处维护。

**改法**

1. 建立“薄触发器”红线：
   - 数据库保留：RLS、唯一性、外键、账本不可变、append-only、已结账期间禁写、职责分离的最终防线。
   - 移出数据库：JSON manifest 排序/哈希、通知文案拼装、复杂工作流编排、跨表业务决策。
2. 新迁移必须说明：
   - 为什么必须在数据库层；
   - 是否可用 Python 事务 + 约束替代；
   - 对 SQLite 的等价策略；
   - 回退/恢复影响。
3. SQLite 定位收敛：
   - 本地演示、单元测试、离线轻量预览；
   - 不再强求复刻所有 PG 安全约束；
   - 维护“SQLite/PG 行为差异清单”，测试按能力跳过并注明。
4. 迁移债务账本：
   - 记录历史复杂触发器；
   - 新功能不得增加同类债务；
   - 逐步把可移出的逻辑迁回 Python，不做一次性大爆炸重写。

**验收**

- 新迁移中没有新增复杂业务 PL/pgSQL（有评审豁免清单）。
- RLS、不可变、复核、append-only 负向测试仍通过。
- SQLite/PG 差异有文档、有测试标记，不静默跳过。
- 迁移数量不再作为质量指标；以约束覆盖和恢复证据衡量。

### WP7／P0（外部门槛）：真实容量与真实用户

**现状证据**

- `README.md:1` 明确 200–500 家是目标，不是已完成验收。
- `docs/ACCOUNTING_ROADMAP.md` 当前面向 2–3 家试点。
- `docs/B08_MASTER_ACCEPTANCE_20261018.md:120` 真实企业试点“未开始”。
- 本地 100 clients 诊断出现 132 次 `queue_full`（单机、pool=4 的诊断，不计验收）。
- `docs/WORKBENCH_USABILITY_TRIAL.md:3` 仍是“待实测”。

**改法**

1. 容量：
   - 固定机器、PG 版本、API/worker 数量、连接池预算；
   - 按 50/100/200 阶梯，记录成功 p50/p95/p99、拒绝、超时、DB CPU、连接、锁等待、队列、恢复时间；
   - 多企业热点与单账套热点分开；
   - 同机多进程不能宣称多节点。
2. 真实用户：
   - 3–5 名非技术员工 + 一线会计；
   - 跑 6 项核心任务；
   - 记录完成率、耗时、错路、求助、重复提交、跨企业；
   - 手机覆盖 iOS Safari、Android、微信内置浏览器。
3. 真实试点：
   - 2–3 家真实企业、连续两个完整月；
   - 统计每企业每月人工分钟、每百笔修改数、缺资料等待、返工率；
   - 没有这些数据，不对外承诺 200–500 家。

**验收**

- 容量报告能解释瓶颈，不以无限队列/自动重试/放宽权限改善数字。
- 真机报告有设备、网络、参与者、任务、失败步骤。
- 真实试点报告有企业授权、脱敏证据和会计签字。
- 外部门槛未完成时，状态写“未验证”，不写“已配置”。

### WP8／P2：Design System 与前端工程治理

**现状证据**

- 124 个 `.tsx`、67 个 `.css`、25,444 行 CSS。
- 2,062 处硬编码 hex、1,560 种写法。
- 457 处 `<12px` 字号；其中 11px 181、10px 158、9px 67、8px 28。
- 36 种 border-radius；31 种 `max-width` 断点；35 种 font-size。
- 10 个 `.tsx` 超过 1,000 行；`LegacyMigrationWorkspace.tsx` 3,141 行、`App.tsx` 1,972 行、`styles.css` 5,095 行。
- 主 chunk 565,606 字节；已有路由级 `React.lazy`，不是“完全没拆”。

**改法**

1. 字号阶梯：
   - 正文/表单 ≥14px；
   - 辅助信息 ≥12px；
   - 8–11px 仅限非关键装饰，逐项豁免；
   - 金额列 `font-variant-numeric: tabular-nums`。
2. Token 收敛：
   - 语义色 `--canvas/--surface/--ink/--brand/--ok/--warn/--danger`；
   - 先替换高频 hex，再处理透明色/图表色；
   - 不追求一次性 100% 清零。
3. 断点收敛：
   - 先定 3–4 个主断点；
   - 旧断点按页面迁移，不做全局正则替换。
4. 文件拆分：
   - `styles.css` 按 shell/data-table/cards/forms 拆；
   - 巨型组件优先拆“视图子块”，不先动业务状态；
   - 每次拆分配截图对比和关键流程回归。
5. 包体：
   - 已有 lazy 的路由继续保留；
   - 员工首屏只加载报销/审批所需模块；
   - 用 gzip/brotli 后体积和 4G LCP 验收，明确口径。

**验收**

- `<12px` 字号有豁免清单，关键页面为 0。
- 新增颜色必须走 token；硬编码 hex 不再增长。
- 主 chunk 相比基线下降 ≥30%，员工首屏达到约定预算。
- 拆分不改变关键流程、权限和恢复行为。

**退出条件**：新迁移不再增加复杂触发器债务；关键页面字号/token 达标；包体和长任务有持续监控。

## 6. 治理要求

1. **同候选**：所有改前/改后数据必须绑定同一候选指纹；候选变化后旧证据失效。
2. **固定分母**：missing/unknown 不从评测分母删除；skip/xfail 不算通过。
3. **不删负向测试**：权限、复核、租户、费用、attempt 的负向用例不得为了“体验顺滑”而删除。
4. **外部门槛分开写**：远端 CI、真机、真实通知、真实模型、真实试点分别记录，不能用“已配置”代替“已验证”。
5. **文档留痕**：每个工作包记录问题、失败证据、修改、通过证据、剩余风险。
6. **不做大爆炸重写**：先压缩交互和文案，再增智，最后做 DB/Design System 收敛。

## 7. 明确不纳入共识的建议

以下建议看似合理，但不应照做：

- **把身份通栏完全藏进头像菜单**：会丢失当前企业/账套/期间/角色上下文，增加错账风险。
- **删除所有免责声明和“下一步”说明**：合规提示仍需要，只是要压缩和分层；blocked/退回/unknown 必须保留原因。
- **放开 AI 自由生成财务叙述**：只能在引用和确定性校验下增加叙述，不能放开金额/结论。
- **按“217 个迁移文件”制定改造**：实际是 205 个 PG 迁移文件、217 是 schema 版本；用错误数字会误判工作量。
- **认为前端“完全没有代码分割”**：已有路由级 lazy；问题是主 chunk 仍 565KB，需要继续拆。
- **用 200–500 家目标宣称已支持该规模**：真实试点未开始，100 clients 已出现队列拒绝；必须先证明。

**报告结论**

衡账不需要先重写，而是需要一次**有纪律的减法**：

> 把用户不需要的工程噪声从界面上拿掉，把 AI 从模板播报升级为可引用的分析，把数据库从“业务逻辑仓库”收回到“一致性防线”，再用真实用户和真实容量证明它。

这四件事按顺序做完，产品的“好用”才配得上现有“可控”的工程底子。
