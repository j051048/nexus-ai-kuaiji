# PLT04：出租车一条有差异的业务走到底

先读 `PLT00_MASTER.md`。前置：PLT02（出表模式）、PLT03（待办直达）。

现有验收都是金额正好对上的路径。本批专门处理**没有正好对上**的业务，沿"运营结算单 → 回款流水 → 差异处理 → 凭证 → 复核 → 月结 → 报表 → 下钻回原始行"查每一次交接。

线索：`nexus_backend/app/tax/`（`fees.py`、`fee_guard.py`、`sources.py`、`pilot.py`）、`fee_receivable_*` 相关表、`nexus_backend/app/settlements/`、`reconciliation/`、`subledger/`、`src/TaxFeeBatchPanel.tsx`、`src/TaxSourcePanel.tsx`、`src/ReconciliationWorkbench.tsx`、`src/SettlementWorkbench.tsx`、`docs/FSC02_*`。

## PLT04-A  链路盘点与断点清单 【可独立完成】

**做法。** 只读。用现有合成数据，从一条规费结算行出发，逐步追到报表数字，写入 `docs/pilot/TAXI_CHAIN.md`：

- 每一步：所在页面与接口、涉及的表、对象之间靠什么字段关联、由谁操作。
- 每一步的**反向**能否走通：从报表数字回到科目、凭证、分录、应收项、结算行、来源文件的行。
- 断点：需要开发人员查库才能关联的地方、需要人记住编号手工查找的地方、状态只在一侧更新的地方。

本模块不改代码。

## PLT04-B  差异类型与处理 【可独立完成】

**设计约束。**

1. 支持的到账差异情形（均用合成数据）：
   - 跨日或跨期到账。
   - 部分到账。
   - 到账金额少于应收（可能是扣费，也可能是别的原因）。
   - 到账金额多于应收。
   - 一笔到账对应多笔应收；多笔到账对应一笔应收。
   - 有流水但找不到对应应收。
2. **系统不判断差额的原因。** 差额只被计算和展示；原因由有权限的人选择并附依据。"金额恰好等于某费率"不构成依据。
3. 差异处理是一个有状态的对象：待处理、处理中、已处理、已撤销。记录处理人、原因类型、依据（引用原件或记录）、处理时间。写审计。
4. 原因类型来自企业政策配置的清单（如手续费、代扣、尾差、待查）。没有配置时只能选"待查"。每种原因对应的会计处理（进哪个科目）也来自政策，不写死。
5. "待查"状态的差异：
   - 不生成正式凭证。
   - 在月结权威预检中作为阻断或提示，取决于政策；没有政策时作为阻断。
6. 差异处理生成的凭证草稿仍走正常的制单与独立复核，处理人不能自己复核。
7. 撤销已处理的差异：已生成凭证的走冲销，不删除。
8. 复用现有分配、撤销、退款机制（`fee_receivable_allocations` 等），不另造并行的核销表。

**先失败测试。**

- 上述每种情形各一条合成用例，走到"差异已处理、凭证已复核"。
- 未配置原因类型时只能选"待查"，且月结预检被阻断。
- 差额等于某费率金额时，系统不自动标为手续费。
- 处理人复核自己生成的凭证被拒。
- 双会话同时处理同一差异，只成功一个（PG）。
- 跨期到账在期间已锁时的行为符合现有锁期规则。

**验收。** 新增用例 SQLite 与 PG16、PG17 通过；FSC02 现有规费用例无新增失败。

## PLT04-C  未匹配流水的责任与待办 【可独立完成】

**做法。**

1. 每笔未匹配或有差异的流水有明确的处理人或处理岗位；没有指派时归入"未分配"，并出现在主管视图。
2. 它们作为待办出现，遵守 PLT03-B 的契约：动作名"核对到账差额"，直达该笔流水的处理界面。
3. 处理界面同屏显示：流水事实、候选应收项、差额、已有依据、可选原因。
4. 处理人可转交；转交不授予额外权限。

**先失败测试。** 新产生的未匹配流水出现在对应处理人的待办；点击直达该笔；处理后待办消失；无权限的人看不到。

**验收。** 后端用例与 Playwright 用例（桌面、手机）通过。

## PLT04-D  报表下钻到原始行 【可独立完成】

**做法。**

1. 下钻路径：报表行 → 构成该行的科目及金额 → 科目明细账 → 凭证 → 分录 → 业务来源（应收项、差异处理记录）→ 结算行 → 来源文件及行号 → 原件。
2. 每一层的合计等于上一层的数字，在界面上显示"本层合计"与"上层金额"，不一致时明确提示而不是静默。
3. 每一层按当前用户权限过滤；无权看原件的人能看到"有原件，无权限查看"，看不到内容。
4. 下钻读取在同一报表版本的快照上进行；报表生成后数据有变化时提示"报表生成后有变动"。
5. 反向入口：在结算行、流水、凭证页面提供"影响了哪些报表行"。
6. 报表行到科目的关系取自 OPT07-B 的模板数据，不另写映射。
7. 用 SQL 聚合完成，不把全部分录读进内存。

**先失败测试。**

- 合成账套中，从利润表某收入行逐层下钻到具体结算行，每层合计相等。
- 人为制造一处不一致（测试内），界面与接口都报出。
- 无原件权限的用户下钻到最后一层被拦在原件之前。
- 反向：从一条结算行找到它影响的报表行。

**验收。** 后端用例 SQLite 与 PG 通过；Playwright 用例：会计从利润表数字点到原始结算行，全程不需要输入任何编号。

## PLT04-E  真实月份走查工具包 【需客户输入】

**你要做的。**

1. 写 `docs/pilot/TAXI_WALKTHROUGH.md`：驻场走查用的清单。包含需要客户提供的授权样本（一个月的结算单、对应银行流水、至少一笔对不上的业务）、脱敏要求、每一步由谁操作、每一步要记录什么（耗时、是否求助、是否离开系统去查 Excel）。
2. 写一个导入前校验脚本：检查样本文件的表头、行数、金额格式、日期范围是否符合现有导入契约，输出不符合项。只读，不入库。
3. 走查记录模板：每一次交接一行，含"是否需要开发人员解释""是否需要改库"两列。

**不得做。** 不用合成数据填写走查记录；不宣称链路已在真实数据上走通。

**验收。** 清单、校验脚本、模板存在；校验脚本在合成样本上运行正常。状态最高为"工具就绪待客户输入"。

**通过标准（由人判定）。** 正常款与至少一种客户确认存在的差异情形各走通；会计能从利润表数字找到原始结算行，能从未匹配流水找到处理人；全程不改库、不靠开发人员解释。
