# PLT05：外部财务软件的文件往返核对

先读 `PLT00_MASTER.md`。前置：PLT02。

本批只做**授权文件交换**：导出文件、人工导入对方系统、把对方的结果文件带回来核对。不做在线接口，不连接任何真实 T+。

线索：`nexus_backend/app/integrations/tplus54.py`、`integrations/service.py`、`integrations/fde.py`、`delivery/external_evidence.py`、`docs/FDE_ADAPTER_CERTIFICATION_20261116.md`。

## PLT05-A  系统分工与三态模型 【可独立完成】

**做法。**

1. 每个账套有一项配置"正式账所在系统"：本系统，或外部系统（写明名称）。来自企业批准的政策，未配置时为"未核定"。
2. 导出批次的对外状态拆成三个独立事实，各有时间、依据、登记人：
   - **已导出**：本系统生成了文件。
   - **对方已接收**：对方系统接受了导入（依据是回执文件或登记的证据）。
   - **对方已正式过账**：对方系统中已成为正式账。
   
   三者不互相推定。任何界面、接口、统计中不得把前一个当后一个显示。
3. 另有两个状态：**部分失败**（逐笔结果不同）、**结果未知**（导出后没有任何回音）。结果未知不自动重导。
4. 正式账在外部系统的账套：本系统的报表标题区注明"正式账以某系统为准"，PLT02-B 的"正式"模式是否可用由政策决定，未核定时只能试算。
5. 检查现有导出状态字段（如 `exported`）的所有使用点，确保没有地方把它展示成"已入账"。

**先失败测试。** 仅导出的批次，在列表、详情、月结预检、助手回答、集团汇总中都不显示为已接收或已过账。登记接收后才显示已接收；仍不显示已过账。

**验收。** 新增用例 SQLite 与 PG 通过；`integrations`、`delivery` 现有测试无新增失败。

## PLT05-B  返回结果的导入与逐笔核对 【可独立完成】

**做法。**

1. 定义"返回结果文件"的契约（CSV，字段：批次标识、凭证标识或行号、对方凭证号、结果、失败原因、对方过账日期），写入 `docs/pilot/ROUNDTRIP_CONTRACT.md`。真实 T+ 能否产出这样的文件尚未确认，在文档中写明这是待确认的假设。
2. 导入返回文件：按原件服务存档并记摘要；逐笔与导出批次匹配。
3. 逐笔核对结果：一致、对方缺失、对方多出、金额或科目不一致、重复。差异进入一个可处理的清单，每条有处理人，作为待办（遵守 PLT03-B）。
4. 无返回文件时，允许有权限的人手工登记"对方已接收"或"已过账"，必须附证据原件，且标记为"人工登记，未经文件核对"。
5. 全部一致才把批次标为对方已接收；是否标已过账取决于返回文件是否带过账信息。

**先失败测试。**

- 全部成功、部分失败、对方缺一笔、对方多一笔、金额不符，各一条合成用例。
- 同一返回文件重复导入：幂等，不重复改变状态。
- 返回文件的批次标识不属于当前单位：拒绝。
- 手工登记无证据：拒绝。

**验收。** 新增用例 SQLite 与 PG 通过。

## PLT05-C  重复导出、映射变更、补导 【可独立完成】

**做法。**

1. 同一凭证集合重复导出：沿用现有幂等键规则；界面明确提示"这批已导出过，对方状态为某某"，不静默生成第二份。
2. 部分失败后的补导：只包含失败的那些，新批次引用原批次；成功的不重复导出。
3. 导出后科目映射发生变更：
   - 已导出未接收的批次标为"映射已变更，需确认"，不能直接登记接收。
   - 已接收的批次不受影响，变更记录可查。
4. 导出后原凭证被冲销：批次中该笔标注，核对时提示。

**先失败测试。** 上述每条各一个用例；补导批次中不含已成功的凭证；映射变更后直接登记接收被拒。

**验收。** 新增用例通过；`e2e/` 中导出相关用例本机能跑则跑。

## PLT05-D  前端呈现 【可独立完成】

**做法。** 导出与交付相关页面：

1. 三个状态用三个独立的标记显示，各带时间和依据入口。
2. 结果未知时显示"尚无对方结果"及下一步（导入返回文件或登记证据），不显示为成功。
3. 逐笔核对差异清单可筛选、可直达对应凭证。
4. 用现有公共组件与变量。

**验收。** `npm run typecheck`、`npm test`、`npm run lint`、`npm run format:check` 通过；新增 Playwright 用例：仅导出的批次页面上不出现"已入账""已过账"字样。
