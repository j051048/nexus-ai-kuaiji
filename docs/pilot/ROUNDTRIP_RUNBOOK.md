# 现场往返联调工具包（ROUNDTRIP RUNBOOK）

- **状态**：工具就绪待客户输入
- **边界**：本手册描述的是**授权文件交换**（导出 → 客户在对方系统导入 → 取回结果 → 逐笔核对）。**没有**在线接口，**未**与任何真实 T+ 环境联调，也不宣称已完成真实联调。
- **适用对象**：衡账实施顾问、客户财务负责人、客户 T+（或其它外部正式账系统）管理员。
- **配套契约**：`docs/pilot/ROUNDTRIP_CONTRACT.md`（返回结果文件字段契约）、`docs/pilot/PLT05_EXTERNAL_ROUNDTRIP.md`（PLT05-A~E 要求）。

## 一、需要客户确认的事项（未确认前不得开始联调）

| 编号 | 待确认事项 | 为什么必须先确认 | 由谁确认 | 记录位置 |
| :--: | :--- | :--- | :--- | :--- |
| C1 | 哪套系统是**正式账**（本系统 / 外部系统名称） | 决定报表标题区标注与「正式」模式是否可用；未核定时只允许试算 | 客户财务负责人 | 账套政策 + 台账 `formal_book` |
| C2 | 谁负责在对方系统**导入**导出文件 | 导入人≠复核人是内控要求，且需留痕 | 客户财务负责人 | 本手册「参与人清单」 |
| C3 | 谁负责在对方系统**过账** | 过账是外部事实，必须由对方人员声明 | 客户财务负责人 | 同上 |
| C4 | 哪份结果是**最终依据**（对方回执文件 / 对方导出报表 / 人工登记证据） | 决定「对方已接收」「对方已过账」的证据来源 | 客户财务负责人 | 同上 |
| C5 | 对方系统**能导出什么格式**的结果（列名、编码、是否含过账日期与金额） | 决定返回文件能否按契约解析；不能解析时只登记证据，不猜 | 客户 T+ 管理员 | 「格式差异记录」 |
| C6 | 联调使用**测试账套**（不得在生产账套试） | 避免污染正式账与月结 | 双方 | 测试账套名 + 期间 |
| C7 | 期初科目映射表（本地科目 → 对方科目）与辅助核算映射 | 缺一个映射，导出即 409；补导也依赖它 | 客户会计 + 顾问 | 映射配置版本号 |

> 以上全部确认后，把「参与人清单」「测试账套与期间」「映射配置版本」三行填进本手册末尾的记录表，再进入第二节。

## 二、联调步骤（每步都要记人、时间、文件摘要）

> 统一要求：每一步完成后立即在文末记录表登记 **操作人 / 时间（含时区）/ 文件名 / SHA-256**。文件摘要由系统在导出与上传时自动给出，人工登记时抄录即可。

1. **准备（一次性）**
   1. 确认测试账套处于打开期间，且已冻结交付清单（交付工作台「核验并冻结」）。
   2. 录入 C7 的科目/辅助项映射并生效，记下**映射版本号**。
   3. 选 2~3 张已审核凭证作为联调样本（建议一张正常、一张金额较大用于观察尾差）。
2. **导出**
   1. 「集成 / T+ 交付」→ 冻结交付意图 →「生成 54 列」→ 下载 CSV。
   2. 记录：`artifact_id`、`content_sha256`、行数、凭证数、当时的映射版本。
   3. **此时页面只能显示「已导出」**；不得显示为已接收或已过账。
3. **客户导入（测试账套）**
   1. 客户用自己的账号导入 CSV；导入人不得是本系统操作人（C2）。
   2. 客户回报：导入成功/失败笔数、失败凭证编码与原因。**口头回报不算证据**，必须进入第 4 步。
4. **取回结果**
   1. 优先：客户导出符合 `ROUNDTRIP_CONTRACT.md` 的结果文件 → 在「回传结果文件」中导入。
   2. 次选：客户提供回执原件（PDF/截图）+ 人工登记「对方已接收」或「已过账」，**必须附证据原件**，系统会标记为「人工登记，未经文件核对」。
   3. 记录：返回文件 `content_sha256`、导入时间、批次标识。
5. **逐笔核对**
   1. 在逐笔差异清单里逐条处置（一致 / 对方缺失 / 对方多出 / 金额或科目不一致 / 重复）。
   2. 每条处置必须写原因码与依据；`other` 必须写清 ≥10 字。
   3. 「导出后已冲销」的行会显式标注，须按冲销后的凭证重新核对。
6. **收口**
   1. 全部一致 → 批次显示「对方已接收」；**只有返回文件带逐笔过账信息**才显示「对方已过账」。
   2. 未取得对方结果 → 保持「尚无对方结果」，**不自动重发**，按第三节情形 4 处置。

## 三、四类必演练情形（每次联调都要走一遍）

| 情形 | 怎么造 | 期望系统行为 | 记录 |
| :--- | :--- | :--- | :--- |
| **1. 重复导入** | 把同一份返回文件再导入一次 | 幂等：不改变状态、不新增第二次回执；同一批次标识+同一摘要直接返回原记录 | 记录两次导入的时间与摘要是否一致 |
| **2. 部分失败** | 返回文件里把其中一笔标为 `rejected`（并写原因） | 批次为「部分失败」；失败笔进入差异清单；**补导**只生成失败那几笔，且不含已成功凭证 | 记录补导批次 id、补导文件凭证数、是否含成功凭证（必须为否） |
| **3. 映射变更** | 导出后重新核定一版科目映射（版本 +1） | 已导出未接收：显示「映射已变更（导出用 vN，当前 vM）」，**直接登记接收被拒**；补导会按新映射自动重映并记录 `source_configuration_version / configuration_version`；已接收批次不受影响 | 记录两个版本号与补导是否 `remapped=true` |
| **4. 无结果** | 只导出，不导入任何回执/返回文件 | 显示「尚无对方结果，不自动重发」；补导被 409 拒绝；月结/交付页不得把它当成已入账 | 记录导出时间与超过约定时限后仍未回音的处理人 |

> 补导三条硬边界（现场不要试图绕过）：①父批次 `result_unknown` 时一律 409；②必须有**逐笔返回文件**才能确定失败项，只有回执计数不行；③已处置为 `resolved` 的失败项不再补导。

## 四、返回文件格式差异的记录规范

原则：**现场不改代码、不改契约、不改对方系统**。发现差异按下面格式登记，由开发后续适配。

```
差异编号：RT-DIFF-<序号>
发现时间：YYYY-MM-DD HH:MM (+08:00)
发现人：
对方系统与版本：
对方导出路径：
样例文件：<文件名> / sha256=<64 位>
契约要求的列名：批次标识,凭证标识,对方凭证号,结果,失败原因,对方过账日期,金额,科目
对方实际列名：
差异类型：缺列 / 多列 / 列名不同 / 编码不同（GBK 等）/ 金额格式（千分位、负数、含币种）/ 日期格式 / 结果值不在枚举内 / 一行多凭证
影响：可解析 / 需人工登记
临时处置：<例如：客户另导一份 UTF-8 CSV；或走人工登记+原件>
后续动作：<开发适配任务编号>
```

常见差异与临时处置建议：
- **GBK 编码**：请客户另存为 UTF-8(bom)；不要现场转码后当作原件存档（摘要会变）。
- **金额带千分位/币种**：请客户改为纯数字两位小数；否则该行只能人工登记。
- **结果值不在枚举内**（如「成功」「失败」中文）：映射为 `accepted/rejected` 前必须先登记差异，**不得在文件里手改**（手改即伪造原件）。
- **一行多凭证**：请客户按凭证拆行；拆不了则整批拒绝并登记。
