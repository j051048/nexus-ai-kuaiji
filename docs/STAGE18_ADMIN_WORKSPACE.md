# 第十八阶段：组织管理后台

版本 `0.18.0`，面向 2–3 家企业试点。新增 `/admin` 管理企业与人员，继续使用 Supabase 身份、应用数据库授权及现有人工会计复核流程。本文描述仓库实现与发布步骤，不表示线上已经完成升级或账号初始化。

## 入口与管理范围

正式前端入口为 `https://kuaiji.flydao.top/admin`。未登录时显示管理登录页；登录后仍须通过真实角色授权与 MFA。普通用户进入该地址不会获得管理权限。

| 入口 | 用途 |
| --- | --- |
| `/admin` | 当前事务所的企业列表，按名称、税号与状态筛选并分页 |
| `/admin/organizations/:id` | 企业资料、人员、部门审批配置、账套授权及该企业操作记录 |
| `/admin/members` | 事务所人员与职责，仅事务所负责人／管理员可用 |
| `/admin/audit` | 当前管理范围内的组织、人员、授权与开户审计 |
| `/account-activation` | 接收人确认加入企业或事务所；未接受前不授予业务权限 |
| `/account-recovery` | 本人主动申请密码重置邮件，回跳后设置本人密码 |

同一个人使用一个 Supabase 账号。切换企业不会冒用员工身份；操作记录保留实际执行者。拥有多个事务所授权时，必须先选择当前事务所，各所数据独立过滤。

组织结构为“事务所 → 客户企业 → 部门与账套 → 会计期间”。本阶段一条企业记录只属于一个事务所；相同企业历史上如已存在多个事务所服务关系，升级会停止，需明确处理原共享关系，不自动合并或转移资料。

## 角色与权限

| 角色 | 范围与能力 |
| --- | --- |
| 事务所负责人 `owner`、管理员 `admin` | 管理本事务所全部企业，包括新建企业；具备所属账套的编辑、复核、导出及授权能力 |
| 经办会计 `operator` | 需要明确账套授权；可编辑获授权草稿，不因账套授予 `reviewer` 而获得最终复核权限 |
| 复核会计 `reviewer` | 需要账套 `reviewer` 授权才可复核与导出；只授账套 `viewer` 或 `editor` 时遵守该范围 |
| 事务所只读成员 `viewer` | 仅查看明确分配的账套，无修改、复核及导出权限 |
| 企业 `owner/admin` | 管理本企业有效状态下的资料、成员与部门；不能管理事务所人员或改变企业生命周期，账务访问还须具体账套授权 |
| 企业财务 `finance` | 处理本企业获授权业务，访问账务和移交事项还须相应账套权限 |
| 企业员工 `employee` | 录入并处理本人事项；部门审批另授指定部门权限，不自动获得账本访问权 |

企业管理者不能修改自己的企业职责或账套授权，不能授予企业所有者身份，不能调整事务所人员的企业或账套授权。普通管理入口不能移除或降级事务所负责人，也不能把普通事务所成员升级为 `owner`。

“全部企业”仅指当前事务所，不是所有事务所。部署维护所用的数据库管理员与应用内事务所负责人分开；前端不存在按邮箱识别的永久特权。

## 企业生命周期

| 状态 | 业务行为 | 可进行的管理 |
| --- | --- | --- |
| 正常 `active` | 按当前成员、部门和账套授权开展业务 | 授权管理者可维护资料；仅事务所管理者能变更状态 |
| 停用 `suspended` | 企业业务读取、写入及新的后台任务领取停止 | 事务所管理者可查看基本管理资料、修改资料、归档或恢复 |
| 归档 `archived` | 与停用相同，不删除原件、账务、授权和审计历史 | 事务所管理者可查看基本管理资料，并说明原因后恢复 |

资料更新及状态变更要求填写原因，并提交 `expected_version`。他人已修改时返回冲突，刷新后重新核对。恢复企业保留历史记录及仍然存在的授权；恢复前应检查当前人员和待办。

数据库把企业停用／归档同步为暂停服务关系，禁止绕过企业状态单独重新激活服务关系。企业及服务历史不能直接删除。事务所管理者在停用后可读的管理摘要仅包含人员、部门、账套基本字段，不开放流水、票据原件或凭证明细。

待办统计仍按当前登录者的业务权限计算，员工私人草稿、退回后本人编辑的事项及对应 OCR 不进入管理员汇总。停用后业务统计可能为零，不能据此认定该企业没有尚未完成的历史任务。

OCR／分录领取在数据库调度层排除停用企业，不占用其他企业的任务名额；恢复后仍由现有调度器领取符合条件的任务。已经发送给供应商的请求不能撤回；发布结果时再次检查当前权限和事项状态，未知结果继续按原有人工确认流程处理。

## 人员开通与撤权

管理员在企业人员页选择姓名、邮箱、企业角色和部门；事务所人员页选择事务所角色。开户请求持久保存，接口重试使用相同幂等键不会重复授权。

1. 后端使用独立的 Supabase Auth Admin 配置查询或创建身份，网络请求在数据库事务外执行。
2. 成功后返回一次性激活链接，由管理员私下交付给对应人员。此流程使用生成链接接口，不发送邀请邮件；接口及数据库不接收或保存员工明文密码。
3. 新用户在激活页设置自己的密码，页面要求至少 12 位，同时遵守 Supabase 项目的密码策略。已有账号使用原邮箱和密码登录后确认加入，不覆盖密码，也不替换其他企业授权。
4. 接受时重新核对邮箱、身份 ID、邀请摘要、有效期、发起人权限、企业状态和目标角色。只有全部通过，才在事务中创建成员关系并记录接受人。
5. 请求失败可重试；重试生成新链接并使旧应用授权令牌失效。应用邀请有效期为一小时，供应商激活令牌还有独立有效期。发起人失权或企业停用后不能继续完成旧邀请，应由有权限的管理者核对后处理。

激活链接只在生成时返回，数据库仅保存应用令牌摘要。链接遗失可重新生成，页面刷新不恢复已清除的链接秘密。复制的完整链接应直接交给接收人，不放入群公告、工单日志或仓库。

首次激活若中断在邮箱确认之后、设置密码之前，接收人可主动进入密码恢复页发送重置邮件。此时需要 Supabase SMTP 可用，Auth Redirect URLs 包含完整的 `https://kuaiji.flydao.top/account-recovery`（其他部署使用自己的前端域名）。请求只由本人点击触发，开户重试不会自动发送邮件，管理员也不能获取已有账号的重置登录链接。恢复密码后，重新打开仍有效的应用邀请，使用本人账号完成加入；已过期则由有权限的管理员重新生成邀请。

成员变更按当前数据库授权在后续 API 请求中生效，不依赖用户再次登录。从甲企业移除非事务所员工，或将其企业财务职责降为普通员工时，数据库同时清除该企业的账套访问、长期账套管理及历史迁移项目授权；移除成员还撤销其部门审批资格。再次加入企业或恢复财务职责也不会自动恢复这些授权，需要逐项重新授予。不会删除 Supabase 身份或影响乙企业。

一个人另有独立的事务所身份时，移除其企业成员关系保留事务所明确授予的业务权限，由事务所管理员处理。撤销事务所成员会清除其在该事务所的账套、长期账套管理及历史迁移项目授权，即使仍有企业成员身份也不会保留这些旧授权；其他事务所不受影响。此清理在数据库触发器内完成，直接 SQL 撤权和应用 API 保持一致。授权中的企业财务仍可凭有效的来源账套权限和明确的长期账套管理职责创建新期间；新期间只继承已选择且当前有效的账套成员。

本阶段不提供企业管理员全局封禁 Supabase 账号、替他人修改密码或冒用登录的入口。已有下载文件无法通过撤权收回；新的读取、下载和后台发布会重新验证权限。

## 复核与审计

管理员身份不改变账务约束：已审核与已导出凭证不可直接改写，关闭期间不可写，事实修订和独立审批继续生效。自动识别、生成草稿和组织管理都不能代替会计复核，也不能把导出文件当作外部软件已入账回执。

管理审计与相应变更在同一事务提交，保存操作人、事务所、企业／账套范围、动作、对象和时间。企业资料、状态、成员与账套授权调整记录前后值及原因；开户记录请求、链接生成或失败、撤销及接受身份。管理后台不把其他企业财务日志混入当前企业列表。

## 登录与环境配置

真实 Supabase 模式下，整个 `/api/admin/*` 管理入口，以及原有创建企业、事务所和人员／部门授权写接口，要求验证后的 `aal2` 会话。唯一面向接收人的邀请接受接口使用接收人真实登录与一次性邀请验证，不要求接收人事先拥有管理员身份。

首次进入 `/admin`，管理员用手机验证器绑定 TOTP，并输入六位动态验证码；已有验证器直接挑战验证。后端校验签名与身份服务返回的用户，不信任前端开关或可编辑的用户元数据。用户更换验证器的人工恢复不属于本阶段自动开户流程，应由受控运维核验身份后处理。

API 服务增加或确认以下配置，范本见 [API 环境文件](../deploy/.env.api.example)：

| 环境变量 | 配置要求 |
| --- | --- |
| `ACCOUNTING_AUTH_MODE` | 真实试点为 `supabase` |
| `ACCOUNTING_SUPABASE_URL` | 当前身份项目的固定 HTTPS 根地址 |
| `ACCOUNTING_SUPABASE_PUBLISHABLE_KEY` | 当前项目的公开登录 key，不代替管理密钥 |
| `ACCOUNTING_SUPABASE_ADMIN_KEY` | 服务端 `sb_secret_…` 或 legacy `service_role` 密钥，仅 API 开户功能及受控初始化使用 |
| `ACCOUNTING_PUBLIC_APP_URL` | 前端固定 HTTPS 根地址，例如 `https://kuaiji.flydao.top`，不带路径、查询串或末尾页面名 |
| `ACCOUNTING_ALLOW_FIRM_SIGNUP` | 试点保持 `0`；真实模式默认 `0`，禁止普通登录用户自行创建事务所 |
| `ACCOUNTING_DATABASE_URL` | API 专用受限 PostgreSQL 账号，远端启用 TLS；不能使用迁移管理员连接 |

未配置 Auth Admin 密钥时，既有登录与授权保留，新增账号激活功能显示未配置，不降级为无验证开户。不要将 Auth Admin 密钥放入 `VITE_*`、Vercel 网关或 worker。原件 Storage 服务密钥和 Auth Admin 密钥在配置与用途上分开。

`ACCOUNTING_ALLOW_FIRM_SIGNUP=0` 只控制本应用的事务所创建接口；Supabase 自身的公开注册策略仍需在身份项目中单独配置。能注册或登录身份不代表已获得事务所、企业或账套权限。

Vercel 已为 `/admin`、`/admin/*`、`/account-activation` 与 `/account-recovery` 配置 SPA 路由回退；`/api` 继续通过已有网关转发到 Zeabur。其他前端宿主也应提供这些路径的 `index.html` 回退。

## 初始负责人初始化

这是独立维护命令，不是应用公开 API。先完成数据库迁移，然后在可信维护终端设置下列环境变量：

- `ACCOUNTING_ADMIN_DATABASE_URL`：具有迁移维护权限的数据库连接，仅供本次 CLI 使用。
- `ACCOUNTING_SUPABASE_URL`、`ACCOUNTING_SUPABASE_ADMIN_KEY`、`ACCOUNTING_PUBLIC_APP_URL`：与部署目标一致。

不要把管理员数据库连接注入 API 或 worker。以下命令中的邮箱、名称和事务所 ID 都是占位示例：

```powershell
# 新数据库，尚无事务所时
python scripts/bootstrap_admin.py --email owner@example.com --name "事务所负责人" --firm-name "试点会计事务所"

# 已有数据时，明确指定需要初始化的事务所，避免选错工作空间
python scripts/bootstrap_admin.py --email owner@example.com --name "事务所负责人" --firm-id "已核实的事务所ID"
```

按实际情况只执行其中一条。新 Supabase 身份的初始密码通过终端隐藏提示输入，不放在命令参数、脚本或文档里。已有且已确认的身份沿用原密码；已有未验证邮箱须先处理原身份验证，命令不会直接覆盖。被应用停用的账号也不会被初始化命令重新启用。

初始化写入一次性回执及 `admin.bootstrap.owner` 审计，不在代码中硬编码邮箱。相同事务所和相同身份重复执行不会重复授权；已为另一个身份完成初始化则拒绝替换。完成后移除维护终端的管理员凭据，使用该账号登录 `/admin` 并绑定 MFA。账号是否已在真实 Supabase 建立，须以实际执行结果为准。

## PostgreSQL 升级与发布

本版本完整 PostgreSQL 迁移终点为 **082**，新增 **080 组织管理、081 身份开通、082 停用企业调度过滤**；SQLite 新增 **064–065**。运行进程只校验迁移，不代替部署管理员迁移生产库。

当前线上数据库基线记录为 **072**，因此这次发布不能只执行 080–082；应先只读核对实际版本，再完整应用缺少的 **073–082**。若现场版本已变化，以迁移状态及校验结果为准，不重复手写 SQL 或修改已应用文件。

1. 备份数据库及同一批私有原件，确认可恢复；暂停用户写入，停止 API 和 OCR／分录、助手、旧账 worker。
2. 在独立维护环境使用新版本代码检查迁移状态，再运行完整迁移：

   ```powershell
   python scripts/migrate_accounting.py status
   python scripts/migrate_accounting.py migrate
   python scripts/migrate_accounting.py status
   ```

3. 核对迁移终点 082、文件校验、受限 API／worker 数据库角色及私有 Storage 配置。出现历史多事务所企业关联时停止升级，处理映射后重新迁移，不自动删关联。
4. 完成初始负责人初始化及 API 新增 Auth 配置。API、OCR／分录、助手和旧账 worker 同步发布为同一代码版本，前端与 Vercel 网关随后发布；避免旧 worker 继续使用新数据库。
5. 运行只读部署自检，并使用明确标记的虚构企业和账号走通登录、MFA、企业新建、开户接受、授权及撤权、停用／恢复、审计和审核后导出。

这份说明不声称已对线上执行迁移、发布服务或创建负责人账号。真实供应商、真实企业资料、外部财务软件入账仍需各自验收。

## 验证范围

自动化覆盖 SQLite 与受限 PostgreSQL 的管理授权、跨企业隔离、版本冲突、状态回滚、原生 SQL 防绕过、成员降级与撤销、持久开户恢复、MFA、HTTP 契约及浏览器操作。PostgreSQL 测试只能连接独立测试数据库；缺少测试 DSN 时明确跳过，不能视为已验证。

发布前以当前代码的最终完整测试结果为准。本阶段仍以 2–3 家企业验证操作闭环，不代表已证明一位会计管理 200–500 家企业的容量或效率。
