# 第二十二阶段：首页读取与首屏加载优化

日期：2026-10-15。本轮代码已提交推送并完成线上发布、权限验收和浏览器复测。下文区分本机查询指标与线上实际耗时。上一轮首尔迁移记录见 [第二十一阶段](STAGE21_SEOUL_MIGRATION.md)。

## 改动

- 普通首页登录改为 `GET /api/workspace/bootstrap`，一次返回当前身份、角色能力和第一页待办，消除 `/me` 完成后再读取角色与待办的串行等待。管理后台、非首页深链接沿用原入口。
- 在同一个受限 `accounting_app`、`REPEATABLE READ READ ONLY` 事务内读取当前身份与授权。先选定已获授权的事务所，再单独绑定事务所范围，然后读取角色和待办。没有事务所授权时返回空首页数据，不回落到默认企业。
- 只有首次注册或身份姓名/邮箱发生变化时，才退出只读事务执行既有身份同步，并有限重试；同步前后继续检查账号是否停用。
- 角色与企业能力由三个查询合为一个；待办分页、筛选总数和全局分类数量共用一次授权任务集合，保留空页、越界分页和隐藏资料不计入总数的语义。运行概览也去掉重复的身份/角色读取。
- 首次首页数据只供当前登录范围消费一次。刷新、筛选、返回首页及切换身份继续实时核权；退出和授权范围切换会丢弃迟到响应。
- 运行摘要独立加载并可独立重试。真实待办可先使用；未完成区域继续显示加载状态。审核器、会计列表及权限管理等非首页代码按需加载。
- 兼容分批发布：仅在旧 API 不存在 bootstrap 路由、返回 404 时回退既有身份读取；401、403、503 不回退。
- 已选中事务所的首页事务继续归入该事务所的运行度量；度量标记只影响统计，不改变数据库身份和权限，异常退出也会清理。

## 可复现的改进

使用同一份隔离 SQLite 业务资料分别调用改动前后的实现，员工与会计角色的完整 `me/profile/tasks` 返回值相同，均无业务写入：

| 首页核心读取 | 改动前 | 改动后 |
| --- | ---: | ---: |
| 独立 HTTP 请求 | 3 | 1 |
| 读事务 | 6 | 1 |
| 业务查询 | 15 | 5 |

首包 JavaScript 从 615.40 KB 降至 532.67 KB，gzip 从 185.38 KB 降至 161.30 KB（约 13%）；CSS 的 gzip 从 24.17 KB 降至 21.35 KB。

查询数不包含事务初始化与结束语句；真实 PostgreSQL 还需一次绑定已授权事务所的 `set_config`，原生 RLS 验证已覆盖。运行概览仍为独立请求，不包含在这组关键读取指标中。

部署前在现有正式环境用两种虚构角色同时登录，员工首页全部数据就绪为 5.984 秒，会计为 6.192 秒；这是按钮点击后到角色资料、待办和运行摘要返回的单轮样本，供后续同口径对比，不是 p95。
