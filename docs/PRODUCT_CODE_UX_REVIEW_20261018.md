# 衡账（Nexus 会计工作台）产品、代码与体验审核及优化规划

日期：2026-10-18　版本基线：`a8006d5b`（0.19.0）　性质：**只审核、只规划，不改代码**

审核视角：事务所负责人（经营与人员统筹）× 顶级产品经理（角色与旅程）× 代码团队负责人（架构与交付）。
同时代入七类真实角色：所长、项目经理/主办会计、助理会计、客户领导、客户单位技术负责人、运维/实施、客户普通员工。

---

## 0. 一页结论

**这个项目的工程底蕴明显高于它的产品完成度，产品完成度又明显高于它的交付与商业闭环。**

三句话概括：

1. **底层是对的，而且稀缺**：整数分记账、证据链、强制复核、FORCE RLS、交付回执、投影读模型、统一 Worker、批处理父子任务——这些是同行很少做扎实的部分，不能推倒重来。
2. **中层是堆出来的，不是设计出来的**：30 个工作区视图、16 个导航项、228 个 API、25 个“阶段”文档堆叠在一个产品里。功能都能找到，但**角色找不到自己的下一步**。
3. **上层缺三块拼图**：① 没有“核对用报表”，最后一公里仍要回外部财务软件；② 没有“事务所经营账”（收费、毛利、客户健康度）；③ 没有“可交付的运维包”（监控、告警、备份、数据驻留、SSO），客户 IT 无法自助。

**当前最该做的不是再加功能，而是做三件事：收敛信息架构、补齐价值闭环、把交付变成产品。**
建议冻结新功能 6 周，按“能交付 → 能看懂 → 能算清 → 能规模化”四批推进。

## 2. 现状盘点：四类资产、七类债务

### 2.1 真正的资产（必须保住）

1. **记账正确性**：金额整数分、审核时借贷平衡/来源金额/科目/期间/证据引用校验、已审核不可编辑（`docs/ACCOUNTING_ROADMAP.md:19-25`）。
2. **内控与隔离**：每次请求重新校验授权、FORCE RLS、受限运行账号、审计事件；投影只加速、不成为正确性来源（`docs/WORKSPACE_PROJECTIONS.md:25-31`）。
3. **可追溯交付**：导出冻结清单、逐行回执核验、月结快照、锁期（`docs/STAGE9_API.md`、`docs/STAGE10_API.md`）。
4. **规模化底座已就位**：`batch_operations` 父子任务、统一 Worker、投影维护进程、事务所驾驶舱、客户开通（`docs/FIRM_OPERATIONS_AND_BATCH.md:3-34`）。

### 2.2 正在拖后腿的债务

| 债务 | 表现 | 业务后果 |
|---|---|---|
| **信息架构债** | 30 个视图平铺，会计、专家、后台、客户入口混在一起 | 新用户 3 天内学不会；培训成本高；每个客户都要厂商陪跑 |
| **巨型文件债** | 3131 / 1667 / 1573 行；101 处 AbortController 作用域样板 | 改一处要读一天；回归慢；招人难 |
| **交付债** | 60+ 环境变量、单实例、浅健康检查、告警不出站、备份靠手工 | 客户 IT 无法自助；一次故障就回到厂商救火 |
| **价值闭环债** | 不生成正式报表，最终仍导出 CSV 到 T+/金蝶 | 客户觉得“只是录入工具”；续费与溢价缺支点 |
| **客户端壳穿透** | 客户老板点“本月简报”会进入会计工作台内部壳，统计卡、账套列表、五步流水线全部渲染 | 客户看到不该看的内部动作，信任感受损 |
| **客户端术语泄漏** | XML 预填、科目编码、提交版本号、识别面板直接出现在员工/老板界面 | 小白用户看不懂，退回与沟通成本上升 |
| **同一功能多入口** | 复核 4 个入口、异常 3 个入口、交付 3 个入口、账套 5 个入口 | 用户不知道点哪个；权限与未保存拦截口径不一致 |

### 2.3 已经做对、但还没被“产品化”的能力

- 客户门户四页签（`src/ClientPortalShell.tsx:32-37`）方向完全正确，但目前只有“待办/提交/资料/简报”，没有消息与催办。
- 五步流水线（`src/AccountingBookToolbar.tsx:14-20`）方向正确，但同时存在一条三步说明条（`src/BookWorkspaceShell.tsx:254-270`），**同一页面两套流程心智**。
- 驾驶舱有客户×阶段×风险×负载（`src/FirmCockpit.tsx`），但缺“钱”和“人效趋势”。
- 待办只有“需要我处理 / 办理进度”两桶（`src/WorkspaceHome.tsx:450-513`），缺“逾期/阻塞/待复核/待交付”的优先级分层。

### 2.4 在途未提交代码（不要误判为已完成）

审核期间工作区处于**并行开发状态**：`git status` 除已提交基线外，还有 `firm_tasks`、`ingestion`、`observability` 三个后端模块，`100/101` 迁移，以及 `FirmInbox.tsx`、`ClientMessages.tsx`、`FirmObservability.tsx` 三个前端入口未提交。本报告按“阅读时的快照”标注，**不把这些 WIP 视为已完成能力**；正式评审前应先明确哪些提交、哪些回退。

其中 `firm_tasks` 已实现 `firm/inbox` 五个桶、任务指派/领取/催办、客户消息，是正确方向；但存在三个必须在上线前解决的问题：

1. **消息可见性谓词写反**：`service.py:268-282` 用 `AND` 连接“收件人=我”和“企业广播”，导致普通员工看不到企业广播、管理层看不到全所消息；与 RLS 策略（迁移 100 第 51-57 行）不一致。
2. **写事务仍是全局锁**：`assign/claim/remind` 均 `write=True`（`service.py:141,189,212`），规模化后会成为新的串行点。
3. **收件箱先取 500 行再过滤**：`service.py:74-82`，超过 500 条任务后计数与分页会失真。

## 3. 七类角色的真实诉求（以及它们互相冲突的地方）

> 产品不是“满足所有人”，而是**让每类人在自己的首屏看到该看的，其他全部收起来**。

| 角色 | 真实目标（不是功能列表） | 当前体验 | 最大摩擦 | 优先级 |
|---|---|---|---|---|
| **所长** | 今天哪几家会出事？谁闲谁忙？这个月赚不赚钱？ | 驾驶舱能看风险与负载 | 看不到收入/毛利/人效趋势；转派要进客户 | P0 |
| **项目经理/主办会计** | 异常优先、批量处理、少切换、可交代 | 待办 + 批复核 + 五步壳 | 入口太多；异常散在 cases/review/queue/intelligence | P0 |
| **助理会计** | 今天做什么、怎么做、做完谁接 | 有任务列表 | 缺 SOP/模板指引；新手不知道“做到什么程度算完” | P1 |
| **客户领导** | 报表、税、风险、进度、别烦我 | 简报 + 审批 | 没有“一页结论”；没有可下载的报表 | P0 |
| **客户单位技术负责人** | 数据在哪、谁能看、怎么接、出事谁负责 | 有 RLS/审计/导出 | 数据在韩国；无 SSO/SCIM、无开放 API、无驻留承诺 | P0（企业单） |
| **运维/实施** | 一键部署、可观测、可回滚、可自助 | 脚本齐全但全手工 | 60+ 变量、浅健康检查、告警不出站、恢复要厂商 | P0 |
| **客户普通员工** | 拍照、说清楚、知道进度、退回知道补什么 | 四页签 + 移动布局 | 术语仍多；无消息/催办；大文件提示不直观 | P1 |

**三组根本冲突，必须由产品原则裁决：**

1. **“功能全” vs “小白能用”**：功能全的代价是导航爆炸。裁决：**默认极简，专家功能按角色与开关出现**，不是所有人都看得到全部。
2. **“AI 自动化” vs “会计担责”**：裁决：**AI 只做整理、解释、预填、草稿；审核、锁期、导出、报税永远人工**。这条已经写在代码边界里，要写进产品合同与 UI 文案。
3. **“标准化 SaaS” vs “每家客户都不一样”**：裁决：**模板化 + 少量客户级配置**，不为单客户改代码；确实要改的，做成“行业包/服务包”。

### 3.1 客户单位技术负责人会问的 10 个问题（当前答案）

| # | 问题 | 当前答案 | 差距 |
|---|---|---|---|
| 1 | 数据存在哪里？ | 韩国首尔 Supabase（`docs/STAGE21_SEOUL_MIGRATION.md:3`） | 需大陆区域选项或出境合规说明 |
| 2 | 谁能看到我的数据？ | 请求级授权 + FORCE RLS + 审计 | 缺客户侧可读的审计导出 |
| 3 | 支持 SSO/SCIM 吗？ | 不支持（Supabase 邮箱密码 + TOTP） | 企业单硬门槛 |
| 4 | 有开放 API 吗？ | 有内部 API，无对外 scoped token/文档 | 客户 IT 无法集成 |
| 5 | 备份与恢复？ | 有脚本，无计划/保留/PITR；演练是合成数据 | 需 RPO/RTO 与季度演练证据 |
| 6 | 等保/合规？ | 未提及 | 需等保二级材料或明确不承诺 |
| 7 | 数据能带走吗？ | 可导出凭证 CSV，无“全量带走包” | 需一键导出 + 删除承诺 |
| 8 | 可用性 SLA？ | 单实例、无 SLA | 需 99.5% 目标与赔付边界 |
| 9 | 升级/回滚影响？ | 手工、停写、约 10 分钟停机 | 需蓝绿/灰度与回滚演练 |
| 10 | 出问题找谁？ | 厂商，无工单/告警通道 | 需工单、值班、状态页 |

### 3.2 客户领导只会问 5 件事

1. 这个月能不能按时结账、报表什么时候给我？
2. 税有没有风险、有没有少交/多交？
3. 我的人要花多少时间配合？
4. 钱花得值不值（费用 vs 以前）？
5. 数据安不安全、出事谁负责？

**产品含义**：客户领导的首屏不是“待办列表”，而是“本月结论 + 需要我做的事 + 下载”。当前 `MonthlyBriefing` 方向对，但穿透进会计壳、且直接显示科目编码，需要重做。

## 4. 产品战略：先定边界，再谈功能

### 4.1 三条可选路线

| 路线 | 含义 | 优点 | 风险 | 建议 |
|---|---|---|---|---|
| A. 纯作业前端 | 继续只做“录入→复核→导出”，账本留在 T+/金蝶 | 边界清晰、合规风险低 | 价值感弱、可替代、难涨价 | 不作为唯一路线 |
| B. 轻账本 + 核对报表 | 在 A 之上，基于已审凭证生成**参考报表**（科目余额表、试算平衡、资产负债表、利润表） | 闭环、可交付、可溢价；不碰“法定过账” | 报表口径与准则责任 | **推荐主路线** |
| C. 完整财务系统 | 总账、结转、合并、报税、固定资产、存货 | 天花板高 | 战线极长，当前团队扛不住 | 不做，至少 12 个月内不做 |

**建议明确写进产品：B 路线，且报表标注“管理参考，不替代法定申报/客户财务软件”。** 这样既补齐价值，又不承担“正式过账”的责任。

### 4.2 产品北极星

> **一名会计一个月能稳定交付多少家客户，且一次通过率 ≥ 90%。**

配套三个护栏指标：

- 单客户月度人工分钟数（目标下降 30%）
- 交付准时率（按锁期日）
- 客户员工从打开到提交完成的中位时长（目标 < 3 分钟）

### 5.2 要减/冻结的

| 对象 | 处理 | 理由 |
|---|---|---|
| 学习/规则治理/评测的**新增功能** | 冻结 2 个季度，只修 bug | 是差异化，但不是日常价值；当前维护成本高于收益 |
| 旧账迁移的**高级映射** | 冻结；收敛为“上传→映射→验收”三步 | 3131 行是全仓最大单体，低频高复杂 |
| Agent 活动工作台 | 合并进“后台任务”抽屉，不再做一级导航 | 会计不需要“看 Agent 表演”，只需要知道“卡在哪” |

| 重复入口 | 合并：客户月度进度 / 驾驶舱 / 我的待办 三者边界重划 | 同一件事三个入口，用户不知道点哪个 |
| “投资组合/客户人工投入” | 并入驾驶舱的“人效”页签 | 单独一级入口价值不足 |

### 5.3 明确不做的（写进“不做清单”，防止反复讨论）

- 全自动记账、自动审核、自动锁期、自动报税。
- 全税种申报直连电子税务局（至少 12 个月内）。
- 通用流程设计器 / 自定义报表设计器。
- 多币种、多会计准则、合并报表。
- 为单客户改代码；只做配置与模板。
- 在 API 进程里跑常驻后台循环。
- 用模型计算余额、税款、报表合计。

### 5.4 功能准入五问（每个新需求必须回答）

1. 哪个角色、一周用几次？
2. 不做会损失什么（收入/续费/风险）？
3. 节省多少分钟，怎么测量？
4. 失败时如何兜底，谁负责？
5. 能否用配置/模板解决，而不是新代码？

## 7. 前端信息架构与显示层级

### 7.0 先看清“壳”的真实结构

代码里不是五个并列产品，而是 **4 个可导航壳 + 1 个兜底页**：

1. 会计工作区（`src/App.tsx:1077-1277`，含驾驶舱、月度、复核、迁移等全部内部页面）；
2. 客户门户（`src/App.tsx:1033-1075`，四页签）；
3. 管理后台（`src/App.tsx:540-576`）；
4. 登录/激活/找回（`src/App.tsx:501-598`）；
5. 无授权兜底页（`src/App.tsx:588-598`）。

问题在于：**驾驶舱不是独立壳，而是会计壳里的一个页面**；**客户老板的“简报”会穿透进会计壳**。所以“角色分层”目前只在导航层做了，壳层没有真正隔离。

### 7.1 目标架构：三层，而不是三十个入口

```
L0 全局条
   事务所切换 │ 客户/期间上下文 │ ⌘K 搜索 │ 消息 │ 助手 │ 头像
   ─────────────────────────────────────────────────────────
L1 角色工作台（侧栏 4–6 项，按角色计算）
   所长：驾驶舱 / 客户 / 团队 / 经营 / 设置
   会计：我的待办 / 客户账套 / 复核 / 交付 / 助手
   客户：待办 / 提交 / 资料 / 简报 / 消息
   ─────────────────────────────────────────────────────────
L2 账套工作区（进入某个客户后）
   ① 资料与流水 → ② 匹配与核销 → ③ 凭证与复核 → ④ 对账与月结 → ⑤ 交付与导出
   每一步：一个主页面 + 不超过 4 个页签 + 右侧上下文面板
   ─────────────────────────────────────────────────────────
L3 专家模式（默认折叠，按权限出现）
   科目与模板 / 规则与样例 / 集成 / 旧账迁移 / 评测 / 成本
```

**关键动作：把 30 个视图映射到 5 个步骤 + 5 个专家页 + 4 个客户页，其余全部收进“更多”。**

### 7.2 七角色首屏“3 要 3 不要”

| 角色 | 首屏最该看到的 3 样 | 首屏最该隐藏的 3 样 |

| 所长 | 今日风险客户、逾期任务、人员负载/毛利 | 凭证级明细、模型置信度、XML/路径 |
| 主办会计 | 异常优先列表、待复核、待交付 | 学习/规则/评测、模型费用、迁移 |
| 助理会计 | 今天任务、SOP 入口、提交进度 | 全所统计、成本、权限设置 |
| 客户领导 | 本月结论、需决策事项、报表下载 | 科目、分录、异常码、内部状态 |
| 客户 IT | 数据位置、权限与审计、连接与 SLA | 凭证内容、员工个人信息 |
| 客户员工 | 拍照/上传、待补事项、处理进度 | 科目、置信度、规则名、账套 |
| 运维 | 服务健康、队列积压、最近告警 | 业务明细、客户资料 |

### 7.3 账套页的层级修正

现状问题（有代码证据）：
- 同一页面同时有“三步说明条”和“五步流水线”，心智不一致（`BookWorkspaceShell.tsx:254-270` vs `AccountingBookToolbar.tsx:14-20`）。
- “更多账套操作”分组编号是 ①②④⑤，**缺 ③**；③凭证队列与①资料流水都指向 `accounting`，只靠 tab 区分（`AccountingBookToolbar.tsx:37-63`、`bookPipelineStep:23-35`）。
- 工具栏默认可见 14 个控件，展开后 25 个（5 步 + 3 主操作 + 2 折叠菜单 + 3 tab + 生成建议）。
- 账套页单屏三个工作区并列：账套列表（左）、凭证表（中）、复核面板（右 350px）（`BookWorkspaceShell.tsx:271-295,409-525,680-773`、`styles.css:672`）。

建议：
1. **只保留五步流水线**，删掉三步说明条；步骤条固定在顶部，显示“当前步骤 + 该步待办数 + 阻断原因”。

### 7.4 显示层级规范（可直接落地）

- **一屏一个主动作**：主按钮只有一个；次要动作最多两个；其余进“更多”。
- **数字 > 图表 > 表格 > 文本**：首屏先给结论数字，再给明细。
- **状态色只表达状态**：红=阻塞/逾期，橙=待处理，绿=完成，灰=归档；不用品牌绿表达警告。
- **默认收起技术字段**：置信度、规则名、状态码、XML 路径、模型名一律进“为什么/详情”。
- **每张卡片回答三件事**：这是什么、要不要我做、下一步点哪。
- **空态必须给下一步**：不是“暂无数据”，而是“还没有客户，去开通”+ 按钮。
- **错误必须可恢复**：人话 + 重试 + 追踪号；不暴露堆栈。
- **加载用骨架屏**，超过 300ms 才显示；超过 10s 给“仍在处理”与取消。

- **客户分层**：A 类（复杂/高价值）配主办+助理；B 类（标准）批量；C 类（微型）自助+模板。
- **SOP**：每类业务的“收什么、看什么、什么算完、异常找谁”，写进产品而不是只写进培训 PPT。
- **质量抽检**：每月抽 10% 客户复核，指标进驾驶舱；质量分与绩效挂钩。
- **AI 使用规范**：哪些能外发、哪些不能；AI 输出必须人工确认；客户可关闭。
- **交接规范**：人员离职/转岗时，客户、任务、上下文一键交接（已有 `MemberHandoverDialog` 基础）。

### 9.3 发布与反馈节奏

- 双周一个可用版本，周三发布；feature flag 控制；先 10% 客户灰度。
- 每月一次“角色日”：产品/设计/前端各跟半天会计、半天客户员工。
- 每季度一次“恢复演练 + 安全问卷复核”。
- 每个需求上线 30 天后回看：使用率、节省时间、错误率；无数据则下线。

## 10. 需要拍板的 6 个决策

1. **路线 B 是否确认**：做“核对报表”，不做法定总账。
2. **数据驻留**：是否提供大陆区域部署；不提供的客户如何披露。
3. **专家功能**：是否接受“默认隐藏、按权限出现”，而不是所有人都能点。
4. **AI 边界**：是否把“不自动审核/过账/报税”写进合同与 UI。
5. **收费模式**：按客户数、按账套、按坐席，还是按服务包；决定是否现在做计费模块。
6. **团队节奏**：是否接受冻结新功能 6 周，把债还掉再加速。
