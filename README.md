# Nexus AI 会计工作台

面向事务所多客户账套的辅助记账产品。目标是让会计集中处理异常与复核，逐步提高管理企业数量；**200–500 家是产品目标，当前版本没有完成这一规模的业务或负载验证**。

当前 MVP 范围：中国大陆、人民币、员工业务事项与附件、部门审批、企业财务核验、票据识别与交叉核对、结构化记账建议、会计审核后导出。支持 SQLite 本地演示，以及 PostgreSQL + Supabase 邮箱密码登录的试点配置。已加入企业费用与后台监控、客户科目与模板、自动草稿、跨企业批量复核、异常指派补件及版本化企业规则。第九阶段增加流水匹配、稳定银行交易身份和人工导入回执逐行核验。管理员尚未配置供应商时继续使用人工核票和确定性规则。当前提供中性回执文件导入，尚未直连客户财务软件或接入税务申报。预置科目为验证示例，真实企业试点前需由会计核对适用性。

## 运行

第十五阶段加入[全局会计助手](docs/STAGE15_ACCOUNTING_ASSISTANT.md)：本人持续会话、明确企业与账期范围、可配置真实模型对话、当前 OCR 摘要、受控任务预览与确认、共享企业预算及专用后台监控。真实环境另启助手 worker；当前实际模型供应商仍待配置。验证记录见[第十五阶段](docs/VALIDATION_STAGE15_20261013.md)。

第十四阶段将界面收敛为 [会计 Agent 工作空间](docs/STAGE14_AGENT_WORKSPACE.md)：企业与任务快搜、集中分诊与常用视图、真实后台运行轨迹、当前凭证依据助手及手机导航。该阶段的凭证依据助手按已保存证据作确定性解释，原有 OCR / 模型分录管道继续运行，审批与导出保持人工确认。验证结果见 [第十四阶段记录](docs/VALIDATION_STAGE14_20261013.md)。

第十三阶段加入 [旧账迁移向导](docs/STAGE13_USER_FLOW.md)：私有原件、后台解析、科目与辅助映射、逐月余额复算、差异处理、独立验收和接管归档。历史凭证与当前草稿分开保存；明确审核后的历史规则可辅助新流水分类，历史应收应付清偿生成当前草稿后仍须会计复核。当前提供中性 JSON / CSV / Excel 接入，T+、用友和金蝶原生格式需实际版本与样本验证，未启用真实软件连接。部署及有界处理范围见 [第十三阶段接口](docs/STAGE13_API.md)。

需要 Node.js 20.19+ 或 22.12+、Python 3.11+。使用两个终端，在本项目根目录执行：

```powershell
# 终端 1：后端（推荐先创建独立虚拟环境）
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r nexus_backend/requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --app-dir nexus_backend --host 127.0.0.1 --port 8000
```

```powershell
# 终端 2：前端
npm ci
npm run dev
```

打开 http://127.0.0.1:8080。默认通过 `/api` 代理连接本地后端，首次启动创建本地验证身份和虚构账套。本地模式保留第一阶段的完整操作流程。

数据库默认保存在 `nexus_backend/data/accounting.db`，不纳入 Git。关闭服务后备份该文件；可用 `ACCOUNTING_DB_PATH` 指向另一份本地数据库。`ACCOUNTING_SEED=0` 可停用示例账套。

## Vercel 前端与网关

根目录已提供多服务 vercel.json：app 是 Vite 前端，api_gateway 转发 /api 到 ACCOUNTING_BACKEND_ORIGIN 指向的持久会计服务器。数据库、原件和 workers 继续在服务器运行。环境、文件上限和本地联调见 [Vercel 部署说明](docs/VERCEL_DEPLOYMENT.md)，网关环境示例见 [.env.vercel.example](.env.vercel.example)。

## PostgreSQL 与真实登录试点

1. 新建独立 Supabase 项目，配置 Email / Password 用户。使用管理员连接显式执行迁移，并建立受限运行账号，见 [数据库接入](docs/POSTGRES_SETUP.md)。应用拒绝超级用户或 BYPASSRLS 运行连接。
2. 将 [.env.accounting.example](.env.accounting.example) 复制为被 Git 忽略的 `.env.accounting`，填入新项目的受限数据库 DSN、项目 URL 和 publishable key。前端只获取公开 Auth 配置，数据库密码只用于后端。
3. 在应用进程中显式加载新配置，不自动读取旧 `.env`：

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --app-dir nexus_backend --env-file .env.accounting --host 127.0.0.1 --port 8000
```

4. 负责人登录并创建事务所；其他人先登录一次，负责人再在“成员与权限”中分配事务所角色、客户企业身份和具体账套职责。详见 [登录与开户](docs/AUTH_SETUP.md)。真实模式不会创建演示身份或虚构客户。

事务所 owner/admin 管理所属客户账套；普通会计须获具体账套授权。`operator + reviewer账套`仍不能审核，`viewer`不能写入或下载凭证文件。企业普通员工只能读本人事项、不能读账本；部门审批人必须另授明确部门范围，企业财务看所属企业事项并仍需账套授权才能移交。管理组织并不自动获得员工原件或审批权。

会计资料位于独立 `accounting` schema，浏览器只能通过后端 API 访问。每次业务操作均校验数据库中的当前身份和授权，PostgreSQL RLS 再限制范围。切换事务所或退出登录立即清理前端资料；后台读取和写入重新检查授权。

## 票据识别与记账建议

1. 部署管理员在新的 `.env.accounting` 中配置 `ACCOUNTING_AI_BASE_URL`、后端密钥、视觉模型及记账模型 ID，再重启后端。接口、限制及兼容性见 [供应商接入说明](docs/AI_PROVIDER_SETUP.md)。默认不设置供应商，不提供假识别结果。
2. 企业管理者在该企业的“企业处理设置”中明确开启票据与模型处理。开启后，获授权人员可将本企业的原件和业务证据发送到所配置的服务；其他企业设置独立保留。
3. 员工或授权审批人点击附件识别，核对页码、转录原文、金额、税额、交易双方和字段引用。系统交叉核对业务事项、票据及人工关联的同账套流水；异常集中进入“票据核对异常”。企业财务或会计复核者记录处理依据，申请人不能自行消除异常。
4. 财务移交后，在凭证原件面板生成结构化分录建议。系统校验当前科目、金额、借贷、证据范围和草稿版本后才允许采用；采用只更新草稿，会计独立审核后方可导出。已关联的银行流水具有防重复计入保护。

附件以私有字节提供，图像去上传元数据并缩放；PDF 在隔离进程中完整处理，最多 6 页，超限、损坏、加密或超时交人工处理。供应商结果不自动审批或导出，未知税额不会填零，不自动切换供应商。处理记录保存模型、提示版本、原件摘要、输入版本及用量，资料或权限改变后重新检查。单次处理 HTTP 契约见 [第四阶段接口](docs/STAGE4_API.md)；后台队列的恢复与重试边界见 [第五阶段接口与部署](docs/STAGE5_API.md)。

## 持久后台票据处理

已上传的附件可按企业提交识别批次；每批最多 100 个附件，提交时整体检查事项归属、当前版本和处理权限。任务与进度保存在业务数据库，浏览器关闭后继续执行。任务列表只汇总登录者当前可见的事项，不向员工披露同批其他人的票据或任务数量。

本地 SQLite 演示默认启动嵌入式 worker；设置 `ACCOUNTING_QUEUE_EMBEDDED_WORKER=0` 可停用。PostgreSQL 试点使用独立 worker 账号和进程，API 保持此开关为 `0`。先运行显式数据库迁移，再按 [第五阶段部署说明](docs/STAGE5_API.md) 执行 `provision-worker-login`，把新受限连接填入 `.env.accounting` 的 `ACCOUNTING_WORKER_DATABASE_URL`，运行：

```powershell
.\.venv\Scripts\python.exe scripts/run_accounting_worker.py --env-file .env.accounting
```

worker 与 API 连接同一业务数据库，并使用同一持久私有附件目录。默认最多并行处理 2 件，企业队列轮转领取工作；可配置为 1 件。领取和结果提交使用租约与条件更新，过期 worker 不能覆盖新的执行结果。worker 每次外发原件和发布结果前重新检查当前权限、企业处理开关和事项状态；撤权或凭证已审核后终止尚未完成的处理。

供应商明确返回繁忙或限流时，在有界次数内延后重试；已发送但超时、断网或进程中断的任务标记为待人工确认，不盲目重发可能已收费的请求。重启后，尚未发送的任务恢复排队，已经保存识别结果的任务恢复进度回执，避免再次请求供应商。人工重试使用新的幂等键并保留执行历史。队列成功仅表示已得到结构化识别结果，字段异常仍进入人工处理，不自动消除异常、审批、记账或导出。

## 企业运行与模型费用

“费用与运行监控”集中展示本企业队列、识别失败、待处理异常、worker 心跳、模型用量与费用记录。事务所管理者、企业 owner/admin 和企业财务可查看运行概览；该权限不授予未移交员工原件。普通员工、部门审批人或仅获账套复核权限的账号仍使用其原有事项与账套入口。

部署管理员按供应商实际配置填写 `.env.accounting` 的四个 `ACCOUNTING_AI_*_CNY_PER_MILLION` 费率，API 与 worker 保持一致。单位为每百万输入/输出 token 的人民币价格，最多六位小数；默认留空，不内置供应商报价，不自动汇率换算。费用按返回用量和已保存费率计算为估算，不代表已经核对供应商账单。供应商未报告用量的请求保留为不确定费用，不按零元处理。

企业管理者可设置月额度及单次 OCR、分录建议的预留额，启用时三项必须大于零。在调用模型前，系统用短数据库事务预留额度，容量不足或启用额度但费率缺失时拒绝发送。已发送但费用不确定的请求保留预留额；管理者填写依据后核定金额并留下版本记录。关闭额度限制保留原有工作流与用量追踪，不等于关闭企业模型处理开关。

失败频率、长期待处理异常、队列等待和 worker 心跳异常生成站内告警。企业财务可记录知晓原因；知晓不会自动清除故障、票据异常或费用占用。模型费用核定和预算修改限管理者操作，仍须独立会计复核后才可导出凭证。接口、阈值和计费边界见 [第六阶段运行与费用说明](docs/STAGE6_API.md)。

## 首轮工作流

第三阶段新增“业务事项”入口，支持 **员工报销、采购/费用、日常收支** 三个模板。员工保存草稿、上传原件后提交，部门确认、财务核验并移交同企业开放账套，会计查看来源与提交快照后独立复核。退回重提保留版本和原因，创建与移交重试去重。完整配置顺序见 [第三阶段试点操作](docs/STAGE3_PILOT.md)。

附件私有保存为服务端随机键，下载重新验证当前权限及原件哈希。生产需显式设置 `ACCOUNTING_ATTACHMENT_ROOT` 的持久目录并与数据库一起备份，当前不是 Supabase Storage。默认本地演示为 `nexus_backend/private-attachments/`；本地模式可切换四个虚构身份走通闭环，真实模式使用各自账号。

原有银行流水入口继续支持：

1. 在事务所工作台选择或创建账套，通过 CSV 导入人民币流水。
2. 生成凭证建议，查看原始来源、规则依据与待处理问题。
3. 补充凭据引用、修改科目与分录，人工核对后审核。
4. 选择已审核凭证，导出通用 CSV，保留导出收据。

来源与草稿分开保存；同账套重复导入不会增加来源。同一外部 ID 内容变化将拒绝整批导入。金额以字符串输入、整数分存储，审核时校验借贷平衡和来源金额。已审核凭证不可继续编辑。

导出的通用 CSV **不表示已在外部财务系统入账**。凭据引用和模型识别也不代表附件真实性已经核验。第十阶段已加入同企业、同开放期间的应付辅助核销，支持部分付款、合并付款和精确尾差分摊；跨期收付、未收款业务新模板、税务申报、期初余额、冲销、结转及正式总账尚未实现。示例科目需由会计专家按目标客户群确认后才能用于真实业务。

## 集中复核、补件与企业规则

“跨企业批量复核”按当前会计账套权限筛选，先预览版本、证据及异常，再明确人工确认；每个账套原子提交，跨账套返回逐账套结果。异常与补件可指派负责人并设置期限，员工只看发给本人的公开请求。接受补件后更新事实版本，明确替代的旧原件仍可追溯但不重复计入当前核对；原审批提交快照保留。

会计审核将真实来源及最终分录保存为企业审核样例。修正可形成待发布规则，经已审正反例、当前科目和辅助项评估，再由会计说明理由并显式发布。后台先使用本账套已发布规则或模板，采用到草稿后仍须独立审核。接口与数据库边界见 [第八阶段接口](docs/STAGE8_API.md)、[数据库说明](docs/STAGE8_DATABASE.md)。

## 流水匹配与交付回执

在账套打开“流水与业务匹配”，选择已经移交的已付款事项，核对同账套候选与原件，确认一个或多个流水的合计全额对应一个事项。关联不依赖模型开关；被关联流水不得另行审核导出。流水上的未关闭异常、补件或相似交易待核验继续阻止相关业务凭证审核和新导出。

真实试点导入须固定使用来源标识、脱敏银行账号标识及银行原始稳定交易编号。CSV 可增加 `stable_transaction_id` 列，未填时使用 `external_id`。同企业、同事务所的稳定身份不能在不同账套重复导入；同账号相似流水保留，须会计说明独立交易依据。账号名称是会计配置的标识，系统不能自行识别同一物理账号的不同别名；旧格式仍按原账套外部编号去重，不能替代新身份配置。

“导入回执核验”保存与原 CSV 一致的不可变导出清单，接受客户软件导出的中性 JSON/CSV 回执，逐项比较企业、账套、期间、币种、金额、分录与辅助项。缺字段、部分接收、未知结果或重复外部凭证号留给人工处理；说明差异不修改冻结凭证，也不自动重发。显示核验一致只表示**人工提供的回执内容与清单一致**，不能证明第三方系统已独立确认过账。接口见 [第九阶段说明](docs/STAGE9_API.md)。

## 从 Nexus 底座迁移

初始工作目录仅包含旧项目根配置，源码和 Git 元数据未复制完整。本轮从相邻原项目恢复了 Git 历史，保留上游地址；未修改原项目，也没有向远端推送。旧业务源码没有重新引入运行目录，可从 Git 历史按需提取。

48 个旧根文件（包括旧环境、部署和验收配置）保存在被 Git 忽略的 `.legacy-snapshot/root-20261011/`。该目录可能含原环境凭据，**不要上传、打包发布或提交**。新前端只从 `config/` 读取环境文件；后端不自动读取旧 `.env`。原用户工具配置未改动。

保留 React / TypeScript / Vite 的技术栈，并适配原工具的权限策略概念。完整组织系统、模型网关和 AgentGraph 尚未迁入：它们依赖旧平台运行时，需要审查和解耦。CRM、HR、OA、仪器行业场景、支付和通用流程设计器不进入会计产品默认运行链路。

## 第十阶段：纠错、月结与持续企业配置

账套新增“长期账套与主数据”“月结预检”“人工效率”“财务软件接入”入口，员工事项及会计工作台提供事实修订，银行候选提供重复来源隔离。后台继续生成未审草稿；关键事实修订、别名和规则发布、核销撤销及最终凭证审核保持明确人工确认。

- **事实纠错与重复隔离**：未审事项经另一名会计复核后追加替代来源和草稿，保留原审批、原件及历史 ID；已审核或已导出记录仅提出调整建议，尚不能以备注完成调整。确认重复时保留主来源、隔离未审副本，不隐藏已审核凭证。
- **长期账套与企业主数据**：长期 ID 连接独立月份，旧账套不按公司自动合并。新期成员由管理人明确选择，规则只复制公式为待评估候选；新期真实审核样例评估后仍须显式发布。往来方、项目和银行账户保留稳定 ID，别名经独立复核后才参与解析，原始名称不改写。
- **月结与同期应付清偿**：预检检查有效凭证、资料、任务、补件、银行匹配、修订和完整交付回执；会计确认资料完整性、复核当前快照后才锁期。同期部分或合并付款单独清偿应付款，原业务和银行凭证分别复核，避免再次计入费用。未完整分配的银行收付仍须人工处理。
- **可测量运行与恢复**：监控按变化企业分批刷新，保留公平巡检、事务与锁等待观测；人工计时只记录明确确认的活跃工作，不把开着页面的时间全部计入。数据库和私有原件须一起备份、一起恢复。本机已完成两份新 PostgreSQL 库及一份虚构原件的备份恢复演练，真实试点环境仍需验证。
- **T+ 接入底座**：版本和部署方式尚未确认，目前只保存中性参考文件、版本化映射和冻结交付意图。中性文件不是 T+ 原生格式，不自动创建凭证或期初余额；真实发送保持关闭，外部导入及认证回执留待客户实际版本适配。

操作与边界见 [第十阶段 API](docs/STAGE10_API.md)、[数据库与权限](docs/STAGE10_DATABASE.md)、[同期辅助核销](docs/STAGE10_SETTLEMENTS.md)、[T+ 文件底座](docs/STAGE10_FINANCIAL_BRIDGE.md)、[监控与人工效率](docs/STAGE10_OPERATIONS_EFFICIENCY.md)。真实供应商、真实 Supabase、客户 T+ 导入和完整真实月份尚未通过试点验收；一名会计管理 200–500 家仍是需要测量证明的目标。

## 第十一阶段：减少重复操作并测量自动化

- 在「跨企业批量复核」选择待办后，可以准备同类复核包；按同一企业、期间、稳定往来方、处理依据版本和分录结构集中查看金额、税额、日期与证据差异。所选包先形成独立预览，真人确认后仍逐笔核验，导出另行执行。
- 「后台分录任务 → 续跑配置与耗时」提供默认关闭的企业策略。管理员启用后，符合条件的发送前阻断解除或独立补件关闭会有界续跑；原执行人失权、人工改稿、取消、已审核或外发结果未知仍需人工处置。恢复依据和阶段耗时持久保存，跨 worker 可汇总。
- 「审核样例与规则」增加稳定往来方、已审核别名、同语义候选去重、适用范围冲突及实际命中后的分录修改统计。规则继续经过评估及人工发布，客户样例不跨企业混用。
- 账套新增「试点评测」：从已审核业务和原件建立标准，由另一名复核人员确认，再回放当前规则、模板或指定存量模型/OCR 版本。按月份和业务类型展示已测项一致、差异、未覆盖及失效；未采集工时不置零，不发起新的模型调用或改动账务。

全库两件、每企业一件的模型并发和共享写协调锁保持现状；本阶段增加观测与恢复能力，尚未证明 200–500 家生产容量。第十一阶段 SQL 为 PG055–058 / SQLite040–043，历史迁移保持不变。
